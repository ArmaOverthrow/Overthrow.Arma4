**Found by:** core epic discovery (`/discover-feature core/player-manager`, 2026-08-02).

`OVT_PlayerManagerComponent`'s `m_mPersistentIDs`/`m_mPlayerIDs` maps are deliberately never cleared on disconnect (comment at `OVT_PlayerManagerComponent.c:371` — kept for reconnect), but nothing invalidates the **runtime** side of the mapping either. Consequences:

1. `GetPlayerIDFromPersistentID(persId)` returns the departed player's stale runtime ID. `OVT_EconomyManagerComponent.TakePlayerMoneyPersistentId` (L923-926) checks `if(playerId > -1)` and then `StreamPlayerMoney(playerId)` — streaming a broadcast against a dead ID.
2. Runtime player IDs are session-scoped and **can be reused by a later joiner**. If a new player gets a departed player's runtime ID before any re-`SetupPlayer` fixes the maps, persistent-ID→runtime-ID lookups resolve to the *wrong live player* (money streams, controller lookups, notifications).

`SetupPlayer` already warns on remap ("may indicate player duplication in hosted multiplayer mode", L230-238) — the warning exists because this shape of confusion has been seen.

**Fix shape:** on disconnect, either remove the runtime→persistent entry and set the persistent→runtime entry to `-1` (records in `m_mPlayers` stay for reconnect), or route all post-disconnect streaming through "is this runtime ID still connected + still mapped to this persistent ID" checks. Relates to BUG-015 (both are disconnect-lifecycle state bugs).
