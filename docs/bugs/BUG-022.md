**Found by:** economy epic discovery (`/discover-feature economy/real-estate`, 2026-08-02).

The warehouse block of `OVT_RealEstateManagerComponent`'s JIP payload writes one count and loops a different one (`OVT_RealEstateManagerComponent.c:762-767`):

```c
writer.WriteInt(data.inventory.Count());
for(int ii; ii<m_aWarehouses.Count(); ii++)      // should be data.inventory.Count()
{
    writer.WriteString(data.inventory.GetKey(ii));
    writer.WriteInt(data.inventory.GetElement(ii));
}
```

The reader mirrors the mismatch (`:799-805`):

```c
if (!reader.ReadInt(ownedlength)) return false;
for(int ii; ii<length; ii++)                     // should be ownedlength; 'length' is the warehouse count
```

(`ownedlength` is read and never used.) Writer and reader disagree whenever `inventory.Count() != m_aWarehouses.Count()`, and with more warehouses than item types in a given inventory the writer indexes `GetKey(ii)` out of range.

**Impact:** because `RplSave`/`RplLoad` is a positional binary stream, the first mismatch desyncs **everything after it** in the component's payload for the joining client — corrupt warehouse inventories at best, a garbage stream at worst. Any server with zero or 2+ warehouses (i.e. almost any real campaign) is affected; the accidental working case is exactly one warehouse whose item-type count happens to equal one. JIP is uncovered by the autotest suite (needs two client processes), which is why this has survived — flagging for priority manual MP testing after the fix.
