**Found by:** occupying epic discovery (`/discover-feature occupying/core` + `occupying/qrf`, 2026-08-02).

Two client→server RPCs in `OVT_PlayerCommsComponent` mutate the epic's most consequential state with zero server-side validation:

1. **`RpcAsk_StartBaseCapture(vector loc)`** (`OVT_PlayerCommsComponent.c:110-118`) — accepts an arbitrary vector from any client and starts a base QRF at the nearest base. No proximity check, no "is the base actually enemy-held" check, no alive check, no rate limit, and no server-side `m_bQRFActive` guard (the only guard is `m_CurrentQRF` inside `StartBaseQRF`, which silently drops the request). The legitimate gate lives entirely client-side in `OVT_CaptureBaseAction.CanBeShownScript`.
2. **`RpcAsk_InstantCaptureBase(vector loc, int playerId)`** (`OVT_PlayerCommsComponent.c:120-149`) — a shipped, unauthenticated **instant base ownership flip** that bypasses the QRF entirely. The `playerId` parameter is accepted but never used or verified, and the RPC is not `#ifdef`-gated to debug builds — only its *legitimate invocation* is behind `DiagMenu.GetValue(254)` (`OVT_OverthrowGameMode.c:541-547`), which is a client-side check. Any modified client can flip any base at any time.

Fix shape: server-side validation in both `RpcAsk_` handlers — caller proximity to the target base, base faction check, caller alive/faction check, and a rate limit/cooldown for `StartBaseCapture`; `InstantCaptureBase` should be compiled out of release builds (or gated on a server-verified admin/debug flag), matching how the economy epic's client-authority bugs (BUG-020…022) are being handled.

**Impact:** multiplayer integrity — the two highest-authority mutations in the occupying epic (starting battles, transferring base ownership) are open to any crafted client. Same exploit class as the economy epic's client-authoritative money/real-estate mutations.
