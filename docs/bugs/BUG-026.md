**Found by:** occupying epic discovery (`/discover-feature occupying/core`, 2026-08-02).

`OVT_OccupyingFactionManager.CheckUpdate()` (the 6-hourly strategic spend, `OVT_OccupyingFactionManager.c:1005-1140`) has three defects in one function:

1. **Dead per-base allocation** (`:1063`): `int perBase = Math.Floor((float)toSpend / sortedBases.Count());` is computed and **never used**. Each base is instead handed the *entire* remaining reserve — `base.SpendResources(m_iResources, m_iThreat)` (`:1072`) — so the highest-threat base drains everything and lower-priority bases get whatever crumbs its upgrade allocations happened to leave.
2. **`toSpend` never decremented** (`:1050`, `:1079-1081`): the guard `if(toSpend <= 0) break;` can never fire, so the evident "spend only 80% of new income" intent (`toSpend = floor(newResources * 0.8)`) is unimplemented; the loop is bounded only by `m_iResources` hitting 0.
3. **Divide-by-zero** (`:1063`): `sortedBases.Count()` is 0 once the resistance holds every base — reached on every 6-hour tick in the endgame.

Compounding: `OVT_BaseControllerComponent.SpendResources()` (`:281-312`) has its own dead clamp — `int allocate` is computed and clamped to remaining resources (`:294-301`) then discarded; `SpendToAllocation(threat)` recomputes from the attribute, so a single upgrade can overspend the manager's pool (tracked with the base-upgrades accounting cluster in BUG-029's context).

Fix shape: pass `perBase` (or a decremented running budget) into `SpendResources`, decrement `toSpend`, and guard `sortedBases.Count() == 0`. The arithmetic is a prime world-free Logic-tier test candidate — prove the fix by asserting a two-base split before/after.

**Impact:** the occupying faction's build-out behavior is nearly unrelated to its authored difficulty tuning — one fortress base, starved everything else — and the endgame tick risks a VM error every 6 in-game hours once the map is liberated.
