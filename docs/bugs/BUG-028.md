**Found by:** occupying epic discovery (`/discover-feature occupying/deployments`, 2026-08-02).

`OVT_DeploymentManager.CleanupDestroyedDeployments()` (`OVT_DeploymentManager.c:824-835`) removes dead entity IDs from `m_aActiveDeployments` **only** — it never touches the per-faction lists in `m_mFactionDeployments`. But the creation gate reads the leaking list:

- `EvaluateFactionDeployments` (`:186`) checks `factionDeployments.Count() >= m_iMaxDeploymentsPerFaction` (default 100) against `m_mFactionDeployments`.

Every deployment that ends (multi-town patrols self-delete on route completion via `DestroyDeployment`; condition-fail deletions; any entity loss) leaves a stale ID behind. Over a long campaign the occupying faction's list monotonically grows to 100, after which `EvaluateFactionDeployments` bails on every 30 s cycle **forever** — no town patrols, no vehicle patrols, no error, no log. The self-deleting multi-town vehicle patrols are the main driver.

Fix shape: prune `m_mFactionDeployments` in `CleanupDestroyedDeployments()` (or unregister from both indexes in `UnregisterDeployment` — check which path `DestroyDeployment` takes), and count only live entities at the gate as a belt-and-braces. A Logic/Init-tier test can prove the leak by registering + destroying a deployment and asserting the faction count returns to 0.

**Impact:** the deployment system has a built-in expiry date — long/persistent campaigns (the mod's core premise) silently lose all deployment-driven AI presence, including the town patrols that drive `OVT_PatrolHarassmentStabilityModifier`.
