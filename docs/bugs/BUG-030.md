**Found by:** occupying epic discovery (`/discover-feature occupying/base-upgrades`, 2026-08-02).

`OVT_BaseUpgradeCheckpoints` falls through every persistence path at once:

1. **Compositions aren't entity-tracked.** `SpawnCheckpoint` spawns via `OVT_Global.SpawnEntityPrefabMatrix`, not `OVT_SlottedBaseUpgrade.SpawnInSlot` — so unlike bunkers/ammo caches/MG nests it never gets `OVT_PersistenceTracking.Track()`, and vanilla persistence doesn't restore the physical checkpoint.
2. **No `Serialize()` override.** It inherits `OVT_BasePatrolUpgrade`'s serializer, which records only the guard groups — so on load the *guards* respawn but the checkpoint structures they were guarding don't exist.
3. **The slots come back filled.** `m_aSlotsFilled` (which checkpoints inserted into when spawning) is restored by `ApplyPersistedBaseSlots` → `InitBaseControllers` (`OVT_OccupyingFactionManager.c:633-639`), so the road slots are marked occupied by structures that no longer exist — the upgrade can never rebuild them. Net result after one save/load: guards standing on empty roads, forever.

Related same-file defect: the large-checkpoint branch **spends before checking** — `Checkpoints.c:16-19` deducts 60 resources and fills the slot *before* null-checking `m_SpawnedCheckpoint` (the medium branch at `:35` does check), so a failed spawn burns resources and permanently blocks that slot even within a session.

Fix shape: route checkpoint compositions through `SpawnInSlot` (getting tracking + slot bookkeeping for free), or write a proper `Serialize`/`Deserialize` pair that respawns them; either way, only mark the slot filled after a successful spawn.

**Impact:** every save/load cycle strips the occupying faction's road checkpoints island-wide and leaks their slots; one of the OF's most visible presence mechanics quietly disappears from continued campaigns.
