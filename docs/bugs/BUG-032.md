**Found by:** skills epic discovery (`/discover-feature skills/core`, 2026-08-02).

The only affordability/cap check in the skill-purchase chain is client-side (`OVT_CharacterSheetContext.BuySkill()`, `OVT_CharacterSheetContext.c:162-172`). The server seam forwards unconditionally:

```c
// OVT_PlayerCommsComponent.c:99-103
[RplRpc(RplChannel.Reliable, RplRcver.Server)]
protected void RpcAsk_BuySkill(int playerId, string key)
{
    OVT_Global.GetSkills().AddSkillLevel(playerId, key);
}
```

`AddSkillLevel` (`OVT_SkillManagerComponent.c:92-108`) validates nothing: not that the *sender* is `playerId` (it's caller-supplied — any client can level **any player's** skills), not that the player has a point to spend, and not that `newlevel` is within the skill's configured levels.

Two failure modes:

1. **Exploit:** a crafted RPC grants arbitrary skill levels to any player for free — max Trade discount, `IllegalImports`, guaranteed Diplomacy conversions.
2. **Server crash:** `DoInvokeSkillData` (`:119`) and `DoInvokeSkillSpawn` (`:137`) index `skill.m_aLevels[newlevel-1]` with **no bounds check** — the `if(!levelCfg) return;` on the next line is dead code because the out-of-range index throws first. Buying a 6th level of a 5-level skill (or spamming the RPC) is an engine exception on the server. Also unguarded: `GetSkill(key)` returning null for an unknown key (`:118`), and `OVT_PlayerData.Get(playerId)` returning null (`:94`).

Fix shape: validate in `AddSkillLevel` (single choke point) — resolve the sender's playerId from the RPC context rather than trusting the argument, require `(GetLevel()-1) - CountSkills() > 0`, require `GetSkill(key)` non-null, and require `newlevel <= skill.m_aLevels.Count()`. The bounds/null logic is a Logic-tier test candidate once extracted from the RPC path.

**Impact:** multiplayer integrity (free/foreign skill levelling) plus a remotely triggerable server crash. SP/listen-host unaffected in practice (client checks gate the honest path).
