**Found by:** skills epic discovery (`/discover-feature skills/core`, 2026-08-02).

`AddSkillLevel` treats "apply local spawn effects" and "broadcast to clients" as mutually exclusive:

```c
// OVT_SkillManagerComponent.c:102-107
if(SCR_PlayerController.GetLocalPlayerId() == playerId)
{
    DoInvokeSkillSpawn(playerId,key,newlevel);
}else{
    Rpc(RpcDo_SetPlayerSkill, playerId, key, newlevel);
}
```

When the buying player **is** the listen-server host, the local-player branch runs and `RpcDo_SetPlayerSkill` is never sent — so every remote client's copy of the host's `player.skills` map stays stale for the whole session (until a JIP/reconnect rebuilds it from `RplSave`). Anything a remote client derives from another player's skill data shows the host at their old levels.

On a dedicated server `GetLocalPlayerId()` never matches, so the broadcast always fires and the bug is invisible — which is presumably why it survived.

Fix shape: broadcast unconditionally and let the RPC's existing local-player branch (`RpcDo_SetPlayerSkill`, `:306-317`) handle the owning client's effects — i.e. `Rpc(...)` always, plus the local `DoInvokeSkillSpawn` only when host-is-buyer (the RPC does not execute on its sender).

**Impact:** multiplayer state desync in listen-server (player-hosted) sessions only. Low blast radius today (skill data is mostly consumed by its owner) but it silently violates the "all clients hold all players' records" replication contract that the character sheet and any future skill-visibility UI rely on.
