**Found by:** skills epic discovery (`/discover-feature skills/core`, 2026-08-02).

`OVT_SkillManagerComponent.OnPlayerDataLoaded()` dereferences `GetSkill()`'s result without a null check:

```c
// OVT_SkillManagerComponent.c:74-76
OVT_SkillConfig skill = GetSkill(key);
int level = player.skills.GetElement(t);
for(int i = 0; i < level && i < skill.m_aLevels.Count(); i++)   // null deref if key unknown
```

The **persistence path defends against exactly this**: `ApplyPersistedSkills()` (`OVT_PlayerManagerComponent.c:183-214`) validates every saved key against the live config and drops unknown ones with a WARNING (`:206-210`) — the guard exists because of this dereference.

The **JIP path has no such filter**: `RplLoad()` (`OVT_PlayerManagerComponent.c:634-676`) reads (key, level) pairs off the wire and calls `OVT_Global.GetSkills().OnPlayerDataLoaded(player, persId)` directly at `:673`. A joining client whose `overthrowSkills.conf` doesn't contain a key the server sent (version-skewed mod, server-side rebalance that renamed a skill, or a modded server with extra skills) null-derefs during join — per player record in the payload.

Secondary asymmetry at the same call site: the JIP path also skips `ResetSkillEffects()` (persistence path calls it at `:169` immediately before the invoke). Harmless today because all shipped effects assign or are idempotent, but it's the same latent stacking hazard the reset was introduced to prevent — the first accumulating effect anyone writes becomes a JIP-only double-apply bug.

Fix shape: make `GetSkill()` null-safety the callee's job — skip-and-warn unknown keys inside `OnPlayerDataLoaded` (mirroring `ApplyPersistedSkills`) — and call `player.ResetSkillEffects()` at the top of the replay for symmetry. That fixes both entry points at the single choke point.

**Impact:** join-time client crash whenever client and server skill configs disagree; today that requires version skew, but any future server-side skill rebalance triggers it fleet-wide until clients update.
