**Found by:** jobs epic discovery (`/discover-feature jobs/core`, 2026-08-02).

`OVT_JobManagerComponent.DeclineJob()` handles the two job kinds asymmetrically, and neither path informs other clients:

- **Non-public jobs** are removed from the server's `m_aJobs` outright — with no `RpcDo_RemoveJob`, so every other client keeps the dead record forever (it's filtered from their menus only because they don't own it, but it still sits in their arrays and can shadow future `RpcDo_UpdateJob` matches — see BUG-038's identity mismatch).
- **Public jobs** append the decliner's persistent ID to `job.declined` server-side. The declined list is only ever replicated in the JIP `RplSave`/`RplLoad` full-board sync, so the declining player's *other* clients and any UI relying on replicated state stay stale; the comment at `OVT_JobManagerComponent.c:150-151` acknowledges the skip as intentional.

The decliner's own client mutates its local copy in the UI path, which masks the problem in single-player and for the acting client — the divergence is server↔other-clients.

Fix shape: `DeclineJob()` should broadcast — `RpcDo_RemoveJob` for the non-public removal, and a small `RpcDo_DeclineJob(jobIndex, townId, baseId, playerId)` (or reuse of the update RPC carrying the declined list) for the public case. Cheap, reliable-channel, and it closes the only mutation on the board that doesn't replicate.

**Impact:** replicated job boards drift from the server's board on every decline; combined with the jobs menu never refreshing reactively, players act on jobs that no longer exist in that state.
