**Found by:** jobs epic discovery (`/discover-feature jobs/core`, 2026-08-02).

Several condition/stage classes assume context that config authoring or timing can violate, and none guard against it. All of these run inside the manager's 10 s `CheckUpdate()` tick, so a null deref kills the server-side job loop:

1. **Town-dereferencing conditions crash on base-only jobs.** `OVT_RandomJobCondition.ShouldStart()` and `OVT_TownHasDealerJobCondition.ShouldStart()` dereference the `town` parameter unconditionally. `OVT_JobManagerComponent.JobShouldStart()` passes `town = null` for `m_bBaseOnly` configs — any modder composing either condition into a base job gets a VM null deref on the first offer tick. (`OVT_TownSupportJobCondition` and the range conditions have the same exposure via `town`/`base` branches to a lesser degree.)
2. **`OVT_FindRandomHouseJobStage.OnStart()`** never null-checks `GetRandomUnownedHouseInTown()` — a town where every house is player-owned returns null and the stage derefs it.
3. **`OVT_GetShopLocationJobStage.OnStart()`** indexes `m_mTownShops[townID][0]` and the resolved `RplComponent` with no guards. The corresponding condition (`IsNearestTownWithShop`) validated shop existence **at offer time**; by the time the accepted job reaches this stage the shop registry can have changed (JIP re-registration bugs in the economy epic make this non-theoretical).

Fix shape: null-guard `town`/`base` at the top of every condition's `ShouldStart` (return false — "condition not met" is the safe default and matches the base class); make the two location stages return false-with-warning when their lookup fails so `StartJob()`'s existing all-stages-skipped unwind path cleans up, or fail the job gracefully rather than deref.

**Impact:** today's shipped configs don't hit path 1, but paths 2–3 are reachable in normal campaigns (fully player-owned towns; shop registry churn), and path 1 is a landmine for every job author the authoring guide invites in.
