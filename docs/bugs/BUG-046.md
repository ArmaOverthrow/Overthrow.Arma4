**Found by:** resistance epic discovery (`/discover-feature resistance/core`, 2026-08-02).

**Duplication fall-throughs.** `DeployFOB` (`OVT_ResistanceFactionManager.c:414-496`) and `UndeployFOB` (`:498-559`) spawn the counterpart entity **before** checking preconditions. If `playerId == -1`, the player controller is missing, or `transfer.IsAvailable()` is false — reachable at will by starting any other container transfer first — the method just returns:

- Deploy: truck **and** deployed FOB both left in-world (FOB unregistered).
- Undeploy: registered deployed FOB left standing plus a physics-frozen truck already removed from `m_aVehicles`.

**Ghost records.** `UnregisterFOB` (`:893-897`) → `RpcDo_RemoveFOB` (`:1092-1106`) matches `fob.location == pos` with exact equality, comparing the freshly spawned truck's origin against the deployed entity's origin captured at registration (`:878`); any physics settling in between leaves a permanent phantom FOB record (map icon, fast-travel target). `RpcDo_SetPriorityFOB` (`:1120`) already shows the correct shape (10 m tolerance).

Related in the same flow: the completion-handler unsubscribes at `:1518/:1565/:1606/:1648` cast the manager's owner to `OVT_OverthrowController` — always fails (owner is the game mode) — so stale handlers accumulate on player transfer invokers, and the single shared op-state members (`m_pCurrentUndeployedFOB` etc., `:87-93`) mean a re-fired stale handler can run cleanup against the wrong entities.

**Impact:** vehicle/cargo duplication exploit, broken world state, phantom FOBs, and wrong-entity deletion risk under concurrent deploy/undeploy.

Fix shape: validate all preconditions before spawning and abort with a notification; match unregistration by persistentId or distance tolerance; resolve the controller from the stored playerId for unsubscription and move op state into per-operation context objects.
