**Found by:** resistance epic discovery (`/discover-feature resistance/building`, 2026-08-02).

**EntityID across the network.** The removal RPC ships a client-local `EntityID` (`OVT_PlaceContext.c:733`, `OVT_BuildContext.c:749`, `OVT_PlayerCommsComponent.c:687-696`) which the server resolves against **its** world (`OVT_ResistanceFactionManager.c:722`). EntityIDs don't match across machines — the repo's own "use RplId, never EntityID across the network" rule — so on a dedicated server removal deletes nothing (or the wrong entity). The correct pattern already exists in the same file: `RemoveCamp` (`:1141`) uses RplId.

**Ownership never replicates.** `OVT_PlaceableComponent`/`OVT_BuildableComponent` owner UID is set server-only (`:623/:692`) with no RplProp, so the client-side permission check `CanRemoveItem` (`OVT_PlaceContext.c:688-700`, `OVT_BuildContext.c:704-716`) compares against `""` — non-officer clients can't even highlight their own items to attempt removal. The "#OVT-ItemRemoved" toast shows optimistically regardless.

**Impact:** the entire removal feature is non-functional for regular clients on dedicated servers, with a wrong-entity-deletion hazard where IDs coincidentally resolve.

Fix shape: send the target's RplId (mirroring `RemoveCamp`); replicate owner UID on the marker components or move the permission check server-side; show the toast on server confirmation.
