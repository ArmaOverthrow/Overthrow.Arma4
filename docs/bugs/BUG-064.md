**Found by:** towns epic discovery (`/discover-feature towns/support` + `towns/core`, 2026-08-02).

Three related accounting gaps around `OVT_TownData.support`:

1. **No upper clamp.** `AddSupport` (`OVT_TownManagerComponent.c:1221-1228`) never clamps to `population`; `SupportPercentage()` (`:39-44`) has no upper clamp either (test-pinned: 150/50 → 300%). A Diplomacy-5 player (100% conversion) in a 12-pop village can convert 20 respawning civilians (see BUG-063's client-local performed flag) → support 20, 167%. Every percentage consumer then misbehaves: flip/QRF gates fire on meaningless values, `m_iMaxSupportPercentage` deployment gates reject, OF threat scoring inflates.
2. **Silent failure on draw-down.** `TakeSupportersFromNearestTown` (`:1190-1200`) returns void and silently does nothing when `support < num || population < num`. Callers (`OVT_ResistanceFactionManager.c:760/775/790` — garrisons; tent recruiting) never check: recruiting a 6-man garrison from a town with 5 supporters costs **nothing**. The single-recruit path pre-checks client-side (`OVT_RecruitFromTentAction.c:39`) — a TOCTOU gap in MP.
3. **Population-0 ERROR spam.** `RecalculateSupport` passes `max = town.population`; the support system's guard (`OVT_TownSupportModifierSystem.c:32-37`, added in `a4fb997`) prints `LogLevel.ERROR` + a dump — every 70 s, forever, for any town whose population is or reaches 0 (reachable via #2 taking population down, or legacy towns with no recognised houses).

**Fix shape:** clamp in `AddSupport` (and `RecalculateSupport` already clamps to max — the direct mutators are the gap); make `TakeSupportersFromNearestTown` return bool and have callers refuse/charge accordingly; downgrade the population-0 path to a debounced warning or skip.
