**Found during:** authoring the `overthrow-ui-patterns` skill and its conflict checker (2026-08-04). Found by static analysis of the input config, not by play-testing — none of these are reproduced yet.

Thirteen `Action`s in `Configs/System/chimeraInputCommon.conf` share a physical input with another action **listed in the same `ActionContext`**. The engine fires both listeners, so one key or pad press performs two behaviours.

The shared cause is that Overthrow menu verbs were bound onto inputs the base game already reserves for menu navigation. From the vanilla config (`/mnt/n/Projects/Arma 4/ArmaReforger/Configs/System/chimeraInputCommon.conf`):

| Vanilla action | Keyboard | Gamepad |
|---|---|---|
| `MenuUp` / `MenuDown` | `KC_UP`/`KC_DOWN`, **`KC_W`/`KC_S`** | `pad_up`/`pad_down`, left stick |
| `MenuLeft` / `MenuRight` | `KC_LEFT`/`KC_RIGHT`, **`KC_A`/`KC_D`** | `pad_left`/`pad_right`, left stick |
| `MenuSelect` | `KC_RETURN` | `a` |
| `MenuBack` | `KC_ESCAPE` | `b` |

Every Overthrow menu context lists those nav actions (it must, or a gamepad cannot move inside the screen), so `W A S D`, the d-pad, `a` and `b` are all spent before a screen adds its own verbs.

## Why the Resistance menu is the high-priority one

`OVT_ResistanceMenuContext.SendMoney()` (`Scripts/Game/UI/Context/OVT_ResistanceMenuContext.c:240-256`) and `SendFunds()` (`:226-238`) transfer money to the player selected in the spin box with **no confirmation dialog** — they clamp the slider amount to the balance, bail if it is `<= 0`, and call the server directly.

Both are bound to the d-pad's horizontal axis, which is also `MenuLeft`/`MenuRight` in that context. A controller player navigating the Resistance menu left or right therefore also fires a transfer of whatever the amount slider currently reads, to whoever the spin box currently shows. `SendFunds` is officer-gated; `SendMoney` is available to every player.

Contrast `OverthrowRecruitsDismiss`, which collides with `MenuRight` on `KC_D` but routes through a `DISMISS_RECRUIT` confirmation dialog (`OVT_RecruitsContext.DismissRecruit()`, `:365-376`) — annoying, not destructive. The Resistance pair has no such gate.

## Detection

```bash
python3 .claude/skills/overthrow-ui-patterns/scripts/check-input-conflicts.py
```

Parses the mod and base-game configs, resolves which vanilla `Menu*` actions each context pulled in, and reports same-context collisions. All 13 are currently recorded in the script's `BASELINE` set so that a *newly introduced* collision exits 1 instead of drowning in known noise — they print as `BASE`, which is a known bug, not a pass. The script also flags `BASELINE` entries that stop colliding, so fixes cannot rot into stale waivers.

## Fix shape

Rebind the Overthrow side, not the vanilla side. `a`/`b` and the d-pad belong to navigation; menu verbs belong on `x`/`y` and the shoulders:

- **Resistance:** this screen carries **four** verbs — `OverthrowMakeOfficer` (`x`), `OverthrowDonateFunds` (`y`), `OverthrowSendFunds` (`pad_left`), `OverthrowSendMoney` (`pad_right`) — and only two free face buttons, which is why the last two ended up on the d-pad. Both free face buttons are already taken, so the two transfer actions need `shoulder_left` / `shoulder_right`, or the screen needs a mode toggle so fewer verbs are live at once (`OVT_ShopContext`'s Buy/Sell modes are the in-repo precedent; a hidden `SCR_InputButtonComponent` also refuses its keybind, which is what makes that safe). Independently worth considering: a confirmation dialog on a no-undo money transfer, matching `DISMISS_RECRUIT`.
- **Verbs on `a`:** `OverthrowJobsAccept`, `OverthrowLoadoutsApply`, `OverthrowStartGame` should generally be deleted rather than rebound — `MenuSelect` already activates the focused button, so the dedicated action is redundant on a pad. Confirm the button is reachable by focus first.
- **`OverthrowJobsDecline` on `b`:** same reasoning inverted — `b` is Back. Move to `x`/`y`.
- **`pad_up` ShowOnMap** (Jobs, Recruits): move to a shoulder or a free face button.
- **`KC_S` / `KC_D`:** `OverthrowShopSell` and `OverthrowRecruitsDismiss` need non-WASD letters.
- **`pad_down` open actions** (Main menu, Vehicle menu): these are the toggle-open bindings appearing inside their own menu's context. Lowest impact; verify whether the open action needs to be in the menu's own context at all.

Each screen is independently fixable. When one is fixed, delete its entry from `BASELINE` in the checker — the script will tell you if you missed one.

## Verification owed

Static analysis only. Every fix needs a controller in the Workbench: open the screen, press the rebound input, confirm exactly one thing happens, and confirm d-pad/stick navigation still moves focus. Input config is not covered by `compile-check.sh` or the test suites.
