## Symptom

Applying a saved loadout restores equipped items (weapon, and the clothing/backpack entities themselves) but **everything stored inside a uniform, vest or backpack is lost**. Observed on a dedicated server 2026-08-05 when a player's logout gear snapshot was applied to a fresh character: they received only the rifle they were carrying, with empty clothing and an empty backpack.

Server log (one line per lost container):

```
[OVT_LoadoutManagerComponent] Container {1A65EADE4B08583E}Prefabs/Characters/Uniforms/Pants_Suit_01/Pants_Suit_01_black_V1.et has no InventoryStorageManagerComponent for spawned item insertion
[OVT_LoadoutManagerComponent] Container {AC298BA8A7D27007}Prefabs/Items/Equipment/Backpacks/Backpack_Medical_Soviet_NoCross_01.et has no InventoryStorageManagerComponent for spawned item insertion
```

## Root cause

`OVT_LoadoutManagerComponent.ApplyNestedItemsSpawnToUniversalStorage()` (~line 1650) spawns each nested item and then looks for an `InventoryStorageManagerComponent` **on the container entity** in order to insert it:

```c
InventoryStorageManagerComponent containerStorageManager =
    InventoryStorageManagerComponent.Cast(containerEntity.FindComponent(InventoryStorageManagerComponent));
if (!containerStorageManager)
{
    Print(... "has no InventoryStorageManagerComponent for spawned item insertion" ...);
    SCR_EntityHelper.DeleteEntityAndChildren(nestedItemEntity);   // <-- item destroyed here
    continue;
}
```

Clothing and backpacks do not carry an `InventoryStorageManagerComponent` and are not supposed to — that component belongs to the **character** (or vehicle) that owns the inventory. Containers carry a storage component (`UniversalInventoryStorageComponent` / `BaseInventoryStorageComponent`) instead. So the lookup always fails for exactly the containers that matter, and every nested item is spawned and then immediately deleted.

This is the same class of mistake as the ammo-box VME fixed earlier in `SCR_InventoryStorageManagerComponent`: treating the character-side manager as if it lived on the container.

## Suggested fix

Insert through the **target character's** `InventoryStorageManagerComponent`, targeting the container's own storage component:

`characterStorageManager.TryInsertItemInStorage(nestedItem, containerStorage, slotIndex)`

The container's `UniversalInventoryStorageComponent` is already resolved by the caller (`ApplyNestedItemsSpawn`) and passed in, so only the *manager* used to perform the insert needs to change. The character is not currently threaded down to this method and will need to be (or the storage manager passed alongside it).

## Scope — not limited to persistence

This affects **ordinary saved loadouts**, not just the logout gear snapshot: any player loading a loadout at an equipment box gets clothing and a backpack with nothing in them. It is pre-existing and independent of the vanilla-persistence migration.

## Verification

Add a case to the loadout coverage that saves a loadout from a character with an identifiable item inside a backpack, applies it to a fresh character, and asserts the nested item is present — proving it can fail first (it fails today).

## Fix applied (2026-08-05)

**The suggested fix was taken as written**: the owning character's storage manager is threaded down to the nested-item insert, and the container's own `UniversalInventoryStorageComponent` is the target.

`Scripts/Game/GameMode/Managers/OVT_LoadoutManagerComponent.c`:
- `ApplyNestedItemsSpawn()` takes a new `ownerStorageManager` parameter — the manager of the entity that *owns* the container.
- `ApplyNestedItemsSpawnToUniversalStorage()` takes it too and inserts through it (`ownerStorageManager.TryInsertItemInStorage(nestedItem, universalStorage, slotIndex)`). The container-side manager lookup, and the `DeleteEntityAndChildren` that followed it, are gone. A null owner manager now skips the contents with a warning instead of destroying them.
- Call sites: `ApplyLoadoutItem()` passes the character's manager (the container is already inside the character's inventory by then). Recursion inside the universal-storage path keeps the same owner (a pouch inside a backpack is still in the character's tree); recursion inside the storage-manager path passes the container's own manager, which is correct for entities that really do have one (vehicles, characters).

This is vanilla's own idiom — `SCR_IdentityManagerComponent.c:552` inserts a spawned item into a **worn jacket's** storage through the *character's* manager — and Overthrow's own `OVT_SpawnLogic.OnCharacterCreated()` already stocks starting items into clothing exactly this way. The box-based apply path (`ApplyNestedItemsToUniversalStorage`) was never affected: it already moved items through the *box's* manager.

**Coverage:** `OVT_TEST_Init_Loadout_NestedItemsSurviveApply` (Init tier). Dresses a source character, puts a starting item inside a worn container, saves the loadout, applies it to a **second** freshly spawned character, and asserts the item is inside that target's container storage — asserting the extraction half separately first so the case cannot pass vacuously. No prefab is hard-coded: the container comes from what the character wears (falling back to the first civilian-loadout choice with a universal storage) and the item from the difficulty config's starting items. Storage *purpose* masks are deliberately not used to classify anything (the ordinals and flag bits diverge).

**Proven able to fail:** with the fix reverted the case reports
`{…}Handgun_M9.et is not inside the applied container {1A65EADE4B08583E}…Pants_Suit_01_black_V1.et - the container came back EMPTY`,
and the run log carries the bug's own line verbatim — `Container {1A65EADE4B08583E}…Pants_Suit_01_black_V1.et has no InventoryStorageManagerComponent for spawned item insertion`, the same prefab as the dedicated-server report.

**Verified:** compile clean (5908 files). Fast **32/32**, All **60/60** (the new case is the +1).

**Still owed — play-test, not automatable here:** apply a saved loadout at an equipment box and confirm clothing/backpack contents come across (the box path is separate code and was never broken, but the equipment-box flow is the user-visible one); and a dedicated-server logout/rejoin where the stored body is *not* recoverable, so the logout gear snapshot fires and must now return a full kit rather than just the rifle.
