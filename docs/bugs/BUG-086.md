## Summary

A player who logs out and returns later gets a **fresh civilian character with none of their gear**, and their locked vehicles come back rebuilt with **contents lost**. Root-caused over five dedicated-server play-tests (2026-08-04/05). The finding invalidates the assumption the whole player/vehicle restore design rested on:

> **`PersistenceSystem.Save()` + `StopTracking(entity, removeData: false)` + delete keeps the stored record for a SHORT window only. It is not durable. No server restart is required to lose it.**

**Goal for the fix (user):** 100% restoration after an offline period of *any* length (days/weeks), across any number of server restarts. **Applies equally to player bodies and to locked vehicles — both should use the same mechanism.**

## The decisive measurement

In-session, **no restart**: log in → add items → log out → wait 10 minutes → log back in.

```
[Overthrow] Vehicle 019fd02e-4dbe-8a32-… could not be read back from storage - rebuilt … (contents lost)
[Overthrow] Persistence answered NOT_FOUND for player 2's stored body - spawning a fresh one
```

Both ids were minted milliseconds apart at the same disconnect (`…4dbe` vehicle, `…4dc3` body), both released by identical code, **both records gone 10 minutes later**. The vehicle only reappeared because of the rebuild-from-registry fallback added earlier; the body has no working equivalent (its fallback is the gear snapshot, crippled by BUG-085).

10 minutes is also the autosave interval, so **a save point pruning untracked-but-kept records is the prime suspect** — unconfirmed, and the fix below does not depend on confirming it.

| Body re-matched onto the AI config (`SelfSpawn 0`) | **Not it.** Body's config is shared by only 3 records in the save; the AI config group would be hundreds. |
| `SelfSpawn 1` override not deployed | **Not it.** `OVT_TEST_Init_Persistence_PlayerCharacterConfigSelfSpawns` reads the config the engine actually matched to a live player body and asserts it self-spawns — passes. |
| `m_Persistence` null making vanilla cleanup destructive | **Not it.** Assigned in `SCR_SpawnLogic.OnInit` independently of `SetupPersistenceCollections()`. |
| `m_eDisconnectCharacterBehaviour` = DELETE | **Not it.** Unset in the prefab → defaults to SAVE. |
| Possession re-match (`OnPlayerEntityChanged_S` → `ReloadConfig(previousEntity)`) | **Unreachable** in Overthrow — `EmitPlayerEntityChange_S` only fires from spawn request/handler components (absent; server logs `SCR_FreeSpawnRequestComponent could not find SCR_FreeSpawnHandlerComponent!`) and from `SCR_ReconnectComponent` (not on our game mode). An override exists as a harmless safety net. |

Two **real but secondary** effects were found and fixed on the way; keep both:
1. Player-character config was `SelfSpawn 0` — a record whose config does not self-spawn is dropped at load outright. Fixed by overriding `{64ECE6462993EA13}` with `SelfSpawn 1` in the `Player` group of `Configs/Systems/Persistence/Overthrow.conf` (vanilla does the same in `Mission.conf:18-24`; Overthrow inherits `Common.conf`, which does not).
2. Vanilla's `SCR_PlayerReconnectData.RemoveUnusedCharacters()` (`SCR_ReconnectSerializer.c:60-79`) fires 60 s after persistence reaches ACTIVE and deletes every stored player character nobody has claimed. Proven by timed tests: fast rejoin → `restored from their stored body, gear intact`; restart + several minutes → `could not be given their stored body`.

## Why vanilla does not have this problem

`SCR_ReconnectComponent` (`scripts/Game/GameMode/Components/SCR_ReconnectComponent.c`) **never serializes the character**. It keeps the **live entity** in `SCR_ReconnectData.m_ReservedEntity`:

- `m_iReconnectTime` default **120 s**, overridden on dedicated servers by `operating.slotReservationTimeout` (`SCR_DSConfig`, read in `EOnInit`).
- `StoreData()` (`:150`) just captures `GetPlayerControlledEntity(playerId)` — **it does not hide it, move it, or deactivate it**. The body stands visibly where the player dropped.
- `HandlePlayerReconnect()` → `ApplyData()` (`:190`) → `playerController.SetInitialMainEntity(character)` + faction reapply + `EmitPlayerEntityChange_S`.
- `HandleDataExpiery()` (`:176`) → `OnPlayerEntityCleanup_S` + `RplComponent.DeleteRplEntity`.
- Only engages for `RplKickCauseGroup.REPLICATION` disconnects, **not** clean quits.

So in vanilla Conflict a player gone >120 s genuinely returns to a fresh spawn. Vanilla's `Save`+`StopTracking(keepData)` idiom is for carrying an entity across a **save/load boundary**, not as a long-lived in-session store. Overthrow adopted it for a purpose it was never designed for.

**Overthrow does not have `SCR_ReconnectComponent` on its game mode** (grep: zero occurrences).

## Agreed design — reservation model with an Overthrow-length timeout

Keep the disconnected player's character **alive and tracked**, hidden, indefinitely (or for a very long configurable period).

1. **`OVT_OverthrowGameMode.OnPlayerDisconnected()`** (~`:790-820`): stop deleting the body. Do **not** `Untrack`. Leave it tracked so it serializes normally.
2. **Hide and deactivate it**, leaving the transform untouched (its own transform is what makes "return where you logged out" free):
   - `body.ClearFlags(EntityFlags.VISIBLE | EntityFlags.TRACEABLE)` — the engine's documented idiom, and the generated proto's own example uses a player entity (`IEntity.c:419`); vanilla uses the same pair in `SCR_FlagComponent.c:56-64`.
   - `body.ClearFlags(EntityFlags.ACTIVE)` to stop it simulating. Also disable the character controller / AI ticking if anything still runs.
3. **On reconnect**: restore the flags and hand the same entity over (`SetInitialMainEntity` + Overthrow's existing handover), *before* any persistence request. No serialization involved → perfect fidelity, guaranteed.
4. **Across restarts** the chain is already proven working: tracked live entity at save time → vanilla character serializers write it → `SelfSpawn 1` instantiates it at load → the `FindById` fast path already in `OVT_SpawnLogic.RequestPersistedPlayerBody()` adopts it (observed 19:20 test: `Player 1 restored from their stored body, gear intact`). Re-hide it on load until claimed.
5. **DESIGN DECISION AGREED WITH USER:** a hidden body is **not lootable** while its owner is offline. Vanilla's 120 s window leaves it lootable; over a two-week absence that would make an offline player a free supply crate.
6. **Expiry policy:** none required for correctness, but consider reaping bodies whose owner has not returned in a very long time, or capping one per player. Cost is one dormant, invisible, non-simulating character per offline player — negligible for the tens-of-players servers Overthrow targets.

### 7. VEHICLES USE THE SAME MECHANISM — BUT ONLY LOCKED ONES (user decisions, 2026-08-05)

Do **not** keep the despawn-and-rebuild approach for locked vehicles. `OVT_VehicleManagerComponent.ReleaseVehicle()` currently does the identical lossy `Save` + `Untrack(keepData)` + delete, which is why a returning owner's car is rebuilt with **contents lost** — the same defect wearing a different hat, not a separate limitation. Hide and deactivate in place instead (same flags), leave it tracked, unhide when the owner returns. Cargo, fuel and damage then survive by construction because the entity is never destroyed.

**LOCK STATE IS THE GATE, and this rule must be preserved:**

- **Unlocked = public.** An unlocked vehicle belongs to the whole resistance and must **stay visible and usable** while its owner is offline. Never hide it.
- **Locked = private.** Only locked vehicles are hidden, and the purpose is server load, not ownership enforcement.

The existing code already draws this line and the fix must not flatten it: `DespawnPlayerLockedVehicles()` is locked-only by name, and `InitialVehicleCleanup()` gates on `!isOnline && ownerComp.IsLocked()`. Swap the despawn for hide/deactivate on exactly those paths.

**LOCK STATE CANNOT CHANGE WHILE THE OWNER IS OFFLINE (user, 2026-08-05), so the hide decision made at disconnect stays correct for the whole absence — no re-evaluation hook is needed.** The ownership model is:

- Only the **owner** may lock or unlock a vehicle.
- Ownership **never changes** once set.
- An **unowned** vehicle takes the first player to sit in the driver's seat as its owner, permanently.

**CAVEAT — the server does not currently enforce any of this: see BUG-087.** `OVT_PlayerCommsComponent.RpcAsk_SetVehicleLock` (`:328-335`) applies the lock with no ownership check, no sender resolution and no null guards, so today any client can lock or unlock any vehicle. **BUG-087 should land before or with this work**, because the "locked stays hidden, unlocked stays public" split is only safe once lock state is genuinely owner-controlled. Also verify `ClaimUnownedVehicle` (`:337`) refuses to re-claim a vehicle that already has an owner.

**Pre-existing gap worth fixing in passing:** in `InitialVehicleCleanup()`, an **offline owner's UNLOCKED** vehicle hits neither branch (`if (!isOnline && locked)` … `else if (isOnline)`), so it is never registered and falls out of manager tracking entirely.

Other touch points: `RespawnPlayerVehicles()` / `RequestPersistedVehicle()` — unhide instead of spawn-request, keeping the `FindById` fast path for the post-restart case. `OVT_PersistedPlayerVehicle` (registry: prefab/transform/owner/lock) stays as the **last-resort** rebuild path only.

## Required clean-up as part of this change

- **DELETE `OVT_PlayerManagerComponent.InitialPlayerBodyCleanup()`** (added 2026-08-05, scheduled 8 s after init). It save-and-releases offline bodies — precisely the lossy path being abandoned — and would actively destroy the preserved body on every load.
- **Neutralise `SCR_PlayerReconnectData`.** Its sweep only records players who were **online when the save was taken**, so it bites when a server is stopped with players connected. It is a conf-declared `PersistentState` inherited from vanilla `Common.conf`; needs overriding/removing in `Overthrow.conf`, or the body must be made invisible to `FindById` at that moment.
- Keep the `SelfSpawn 1` override and both `FindById` fast paths (`OVT_SpawnLogic.RequestPersistedPlayerBody`, `OVT_VehicleManagerComponent.RequestPersistedVehicle`) — still correct and load-bearing.

## Same root cause elsewhere

- **Recruits** (`OFFLINE_DESPAWN_TIME = 600`): a recruit released and asked for later answers NOT_FOUND and falls back to a fresh civilian body, losing gear. Currently documented as an accepted limitation; it is really this bug, and the same reservation model applies.
- **BUG-085** (loadout apply destroys items inside clothing/backpacks) remains worth fixing so the gear snapshot is a faithful last-resort fallback — but with this fix it stops being on the critical path.
