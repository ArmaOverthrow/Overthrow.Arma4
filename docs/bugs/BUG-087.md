## Symptom

The design rule is: **only a vehicle's owner may lock or unlock it**, and ownership never changes once set (an unowned vehicle takes the first player to sit in the driver's seat as its owner, permanently). The server does not enforce any of this for lock state.

## The hole

`Scripts/Game/Components/Player/OVT_PlayerCommsComponent.c:328-335`

```c
[RplRpc(RplChannel.Reliable, RplRcver.Server)]
void RpcAsk_SetVehicleLock(RplId vehicle, bool locked)
{
    RplComponent rpl = RplComponent.Cast(Replication.FindItem(vehicle));
    IEntity entity = rpl.GetEntity();
    OVT_PlayerOwnerComponent playerOwner = OVT_ComponentFinder<OVT_PlayerOwnerComponent>.Find(entity);
    if(playerOwner) playerOwner.SetLocked(locked);
}
```

There is **no ownership check, no sender resolution and no proximity check**. The RPC does not even carry a player id, so unlike its neighbours in this file it never calls `ResolveSenderPlayerId()`. Any client can send any vehicle's `RplId` and set its lock state.

Also missing a null guard: `Replication.FindItem()` and `rpl.GetEntity()` are dereferenced unchecked, so a bogus or stale `RplId` is a remote VM-error vector — the same class the placeable/buildable index guards were added for.

## Impact

- **Unlock anyone's vehicle** and take it, defeating vehicle ownership entirely.
- **Lock other players' (or public/unlocked resistance) vehicles**, denying their use.
- Remote VME via a crafted or stale `RplId`.

Belongs to the BUG-025 client-trust family that `core/controller-migration` exists to retire; worth fixing before then because it is trivially exploitable.

## Fix

Resolve the sender server-side and require ownership:

- Resolve the calling player (`ResolveSenderPlayerId`) → persistent uid.
- Require `playerOwner.GetPlayerOwnerUid() == callerUid`; reject otherwise.
- Null-guard the `RplComponent` / entity lookups before dereferencing.
- Consider a proximity check, consistent with other validated actions.

Note the related entry point `ClaimUnownedVehicle` (`:337`) implements the "first driver claims an unowned vehicle" half — verify it refuses to re-claim a vehicle that already has an owner, since the stated rule is that ownership never changes once set.

## Why it surfaced

Found while writing up **BUG-086**, which relies on lock state being stable while a vehicle's owner is offline (only locked vehicles get hidden; unlocked ones stay public and usable). That assumption is only safe once this is enforced.


---

**CLOSED 2026-08-08.** `RpcAsk_SetVehicleLock` now resolves the caller server-side and refuses a lock change from anyone who is not the vehicle's owner (`OVT_PlayerCommsComponent.c:333-350`), so BUG-086's "locked stays reserved, unlocked stays public" split rests on owner-controlled state as intended.
