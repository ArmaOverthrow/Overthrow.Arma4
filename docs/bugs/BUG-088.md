**Reported by:** user play-test on a dedicated server (2026-08-06), plus GitHub issue **#147** ("Groups/recruits not working on Dedicated Server", open since Overthrow 1.3.33 / Reforger 1.6.0.119).

## Symptom

On a dedicated server (and, by the same mechanism, any hosted session — anything with replication running):

- Pressing the AI-commanding key (`~`) reports **"Commanding is only available to group leaders."**
- The player has **no faction assigned at all** (confirmed in admin mode).
- The player has **no group indicator**; a recruited civilian keeps his own indicator (green FIA, "Non-Combatant(s)") and stays in his original civilian group (e.g. `Bnza 251`) instead of joining the player.
- The vanilla Group Menu lists a single foreign-faction group; **Create new group** and **Join group** do nothing.
- Identical whether the recruit was just recruited or respawned after a reconnect.

Works in solo, which is what hid it: with no replication session the dropped RPCs below execute locally.

## Root cause

Two server-side calls to vanilla **client-request wrappers**. Each is a thin `Rpc(…)` of an `RplRcver.Server` handler, written to be called *by the owning client*; Overthrow calls both from server code, where the request never reaches the authority's assignment path — silently, since neither return value is checked.

**1. The faction is never assigned.** `OVT_SpawnLogic.SetCivilianFaction()` called
`SCR_PlayerFactionAffiliationComponent.RequestFaction()`, so `SetFaction_S()` never ran. This is the head of the chain: `CreateAndJoinGroup()` reads `factionManager.GetPlayerFaction(playerId)` and **returns early when it is null**, so the player's group is never even created.

**2. The player never joins the group.** `OVT_SpawnLogic.CreateAndJoinGroup()` called
`SCR_PlayerControllerGroupComponent.RequestJoinGroup()`. Even with a faction present, the group would be created empty and leaderless.

**Which failure mode inside the wrapper — not fully pinned down, and it does not change the fix.** Two candidates, both bypassed by calling the server-side entry point directly:
- the `Rpc()` never loops back when the caller *is* the authority (the reason vanilla calls `RPC_AskJoinGroup(…)` directly inside `RpcAsk_CreateGroupWithData`); **or**
- `RequestFaction()` bailed at its very first line — `SCR_SpawnLockComponent.TryLock()` fails and it returns false without attempting anything, printing *"Caught request on locked player!"* at `LogLevel.DEBUG`. Overthrow's spawn path is custom and does not drive vanilla's request/unlock cycle, so a stale request lock is plausible.

Note vanilla's own `SCR_GroupsManagerComponent.RejoinPlayer()` calls `RequestJoinGroup()` from the server, which argues *for* the loopback existing — hence the honest uncertainty. **Cheap discriminator:** grep the dedicated-server log (run with `-logLevel debug`) for `Caught request on locked player`.

Everything else follows from an empty/absent group, because group membership resolves *through* the faction (`SCR_GroupsManagerComponent.GetPlayerGroup()` → `GetPlayableGroupsByFaction(playerFaction)`):

- `IsPlayerLeaderOwnGroup()` is false → `SCR_CommandingManagerComponent` refuses commanding.
- `OVT_RecruitManagerComponent.AddRecruitToPlayerGroup()` bails at its `groupId == -1` / `GetLeaderID() != playerId` guards (silently, before this fix) → the recruit is never moved into the player's slave group.
- Group Menu: `CanCreateNewGroup()` returns false while an empty group of the faction exists (`TryFindEmptyGroup`), which is why **Create new group** is inert.

## Fix (applied)

Use vanilla's own server-side entry points — the same ones vanilla calls from its own server code:

- `Scripts/Game/Respawn/Logic/OVT_SpawnLogic.c` — `SetCivilianFaction()` now calls `factionComponent.SetFaction_S(playerFaction)` when `Replication.IsServer()` (as `SCR_ReconnectComponent` and the faction-affiliation persistence serializer do), and skips the call entirely when the affiliation already matches.
- `Scripts/Game/Respawn/Logic/OVT_SpawnLogic.c` — `CreateAndJoinGroup()` now calls `groupController.RPC_AskJoinGroup(groupID)` directly when on the server (exactly what `SCR_PlayerControllerGroupComponent.RpcAsk_CreateGroupWithData` does), which joins the player, triggers `CheckForLeader` → leader, and tells the owning client via `RPC_DoChangeGroupID`.
- `Scripts/Game/GameMode/Managers/OVT_RecruitManagerComponent.c` — `AddRecruitToPlayerGroup()` now calls `groupController.AddAIToSlaveGroup(recruitEntity, group)` on the server instead of broadcasting `RpcDo_AddRecruitToGroup` to every client with a 6 s pre-delay and a 10 × 2 s entity-resolution ladder so the *owning client* could ask the server to do the same thing. The dead client-side path (`DelayedRpcAddRecruitToGroup`, `RpcDo_AddRecruitToGroup`, `RpcDo_AddRecruitToGroupWithRetry`) is removed. Its silent early-returns now log a warning naming which guard failed.
