## Summary

`OVT_ProgressInfo.SubscribeToController` attempts its controller lookup **once** and gives up if the controller is not yet assigned. `OVT_OverthrowController.RpcDo_NotifyOwnerAssignment` is asynchronous, so this is a race: if the HUD info-display wins it, the subscription is never made and **base transfer / capture progress UI is dead for the whole session** — until the player respawns and the display is re-created.

## Expected

Transfer-progress UI appears whenever a transfer is in progress, every session.

## Actual (predicted from code reading — not yet play-test confirmed)

Intermittently absent. Because it depends on a startup race, it would be flaky and load-dependent: more likely on a slow machine, a busy server, or a JIP connect. Easy to misread as "the transfer system is broken sometimes".

## How it was found

Found while implementing `new-player-experience/tutorial-system` Phase 5. The tutorial HUD overlay hit the same async-controller race and handles it with a bounded retry (60 attempts × 1 s). `OVT_ProgressInfo` was read as the model for the subscribe/unsubscribe lifecycle, and the single-attempt gap showed up by comparison.

The same race has now been hit **three times** in this feature, which suggests it is a systemic pattern rather than a one-off:

- `OVT_TutorialComponent` PLAYER_SPAWNED push — fixed with a bounded retry (10 × 500 ms).
- `OVT_TutorialInfo` HUD subscription — fixed with a bounded retry (60 × 1 s).
- `OVT_ProgressInfo` — **not fixed, this bug.**

## Suggested fix

Give `SubscribeToController` the same bounded `CallLater` retry the tutorial surfaces use, with a silent give-up. Consider factoring the retry into one shared helper, since three separate call sites now need it.

## Verification needed

Confirm the symptom first — this is a code-reading prediction, not an observed failure:

1. Start a transfer/capture immediately after spawning in, on a slow load or a dedicated server, and see whether the progress UI ever appears.
2. Repeat after waiting a while post-spawn — it should work reliably.
3. Check whether respawning restores it (that would confirm the display is re-created and re-subscribes).
