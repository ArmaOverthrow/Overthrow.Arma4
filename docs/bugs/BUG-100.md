## Summary

Community report: selling in quick succession takes the items but appears to skip the payment.

The sell path has no client-side request throttle. `OVT_ShopContext.RequestSell` (`:1359`) validates mode/shop/resource/quantity and fires immediately:

```
transactions.SellItems(m_Shop, m_SelectedResource, quantity);
```

Nothing tracks whether a previous request is still outstanding, and `SellAll` sends `m_iSelectedQuantity` — the count **this menu last observed**, which on a remote client is stale until the deleted items replicate away (the code acknowledges this at `:1399-1401` and schedules a late re-read).

So a double click sends two requests carrying the same quantity. Server-side each `RpcAsk_SellItems` re-scans the character's containers and `ExecuteSell` re-derives every price, crediting only what it managed to delete — so the *second* request typically finds nothing and returns `soldCount = 0`.

The visible result is that `OnSellResult` (`:1380`) fires twice and the second one wins the toast:

```
if(soldCount > 0)        ShowMessage("#OVT-Shop_SoldItems", ...)
else if(skippedCount>0)  ShowMessage("#OVT-Shop_SkippedItems", ...)
else                     ShowMessage("#OVT-Shop_SoldNothing", 0, "")
```

The player sees their items disappear and "sold nothing" — indistinguishable from a lost payment.

## Expected

One click, one sale, one result. A second click while a sale is in flight does nothing.

## Actual

Rapid clicks produce extra no-op requests whose results overwrite the real one. Whether money was actually lost has not been proven — see below.

## Root cause

No request/response pairing on the client. The menu treats a fire-and-forget RPC as if it were synchronous, and treats every reply as authoritative for the current display regardless of which request produced it.

## Suggested fix

The reporter's own suggestion is the right one and is cheap:

1. Set an `m_bSellInFlight` flag in `RequestSell`, clear it in `OnSellResult`, and disable/dim the Sell and Sell All buttons while it is set.
2. Add a timeout so a dropped reply cannot wedge the button permanently (the RPC is Reliable, but the display path is not guaranteed — see BUG-090 for a case where the reply never arrives at all).
3. Optionally carry a request sequence number through `SellItems` → `RpcDo_SellResult` so a stale reply can be discarded rather than shown.

Note that on a **listen-server host** the sell result RPC is never delivered at all (BUG-090), so the in-flight flag must not depend on it exclusively — the host path calls `RpcDo_SellResult` directly today (`SendSellResult`, `:583-591`), which is fine, but the timeout matters.

## How it was found

Community report ("If items are sold in quick succession, the items will be taken from the player's inventory, but payments may be skipped. Suggestion: disable the sell button until the payment is complete."). Traced through `OVT_ShopContext.RequestSell` → `OVT_ShopTransactionComponent.RpcAsk_SellItems` → `ExecuteSell`.

## Open question — is money actually lost?

The server path looks sound: `ExecuteSell` credits exactly what `TryDeleteItem` accepted, in the same loop, and returns 0 without paying if nothing sold. The most likely explanation for the report is therefore the overwritten toast, not a lost credit.

But `InventoryStorageManagerComponent.TryDeleteItem` is not instantaneous, and two requests landing in adjacent server frames can both enumerate an entity whose deletion is already queued. That would produce a *double* credit rather than a missing one — worth instrumenting either way, because it is an exploit in the opposite direction.

## Verification needed

1. Note the exact balance, then click Sell rapidly ~10 times on a stack — compare the balance delta against `unit price × items actually removed`. This is the measurement that settles the open question.
2. Watch the toast sequence: the report is reproduced if a "sold N for $X" is replaced by "sold nothing".
3. Repeat on a dedicated server with a remote client (latency widens the window) and on a listen host.
4. Confirm the money **did** arrive by reopening the menu, in case the HUD ticker misled the reporter — BUG-097 makes the ticker unreliable in its own right.
