## Summary

The client builds the import list from every shop's inventory rules but **ignores the faction include flags** those rules carry:

`Scripts/Game/UI/Context/OVT_PortContext.c:111-127` (`CollectImportables`)
```
foreach(OVT_ShopInventoryConfig shop : m_Economy.m_ShopConfig.m_aShopConfigs)
{
    if(shop.type == OVT_ShopType.SHOP_VEHICLE) continue;
    foreach(OVT_ShopInventoryItem item : shop.m_aInventoryItems)
    {
        m_Economy.FindInventoryItems(item.m_eItemType, item.m_eItemMode, item.m_sFind, entries);
        ...   // every entry inserted; m_bIncludeOccupyingFactionItems is never consulted
    }
}
```

The server rejects exactly those items:

`Scripts/Game/Components/Player/OVT_PlayerCommsComponent.c:786` (`RpcAsk_ImportToVehicle`)
```
if(economy.ItemIsFromFaction(id, OVT_Global.GetConfig().GetOccupyingFactionIndex())) return;
```

`return`, with no notification. The client gets nothing back at all.

The reported case fits precisely: the general store rule `m_eItemType EQUIPMENT / m_sFind "Watch_"` (`Configs/System/ShopConfig.conf`) matches every faction's wristwatch, so with USSR occupying, the Soviet watch is listed by `CollectImportables` and then silently dropped by the RPC. The same will be true of **every** occupying-faction item the shop rules match — the reporter's "not yet tested other Soviet items" should be expected to fail too.

## Expected

Either the item is not offered, or attempting to buy it says why.

## Actual

The item appears in the import menu, the click does nothing, no message, no charge, no delivery.

## Root cause

Two independent membership rules for one list: the menu's (all catalogue entries matching the shop rules) and the server's (same, minus occupying-faction items). The server's is correct — the client's is a superset.

## Suggested fix

Both halves are worth doing:

1. **Filter the client list.** In `CollectImportables`, apply the same faction gate the RPC applies — skip any prefab where `ItemIsFromFaction(id, occupyingFactionIndex)` — unless the player holds `IllegalImports`, which already takes the other branch (`:100-119`) and legitimately widens the list.
2. **Stop failing silently.** `RpcAsk_ImportToVehicle` has ten bare `return` paths. At minimum the faction rejection, the permission rejection and the catalogue rejection should send a notification, the way `PlaceItem` sends `CannotAfford`. A silent RPC is indistinguishable from a dropped packet, which is what makes this look like a broken button rather than a rule.

The ideal shape is the one `OVT_ShopSellRules` already uses in the shop menu: one predicate consulted by both the UI (to grey the row and name the reason) and the server (to authorise). Worth considering while fixing.

## How it was found

Community report ("(With USSR as occupying faction) Soviet wristwatch is visible in import menu, but buying it does not work. Not yet tested other Soviet items."). Traced from the port context's list builder to the server RPC's faction gate.

## Verification needed

1. Start a campaign with USSR occupying, reach a port with import permission, and try to import the Soviet wristwatch — expect nothing to happen.
2. Import a US or FIA watch at the same port — expect it to work, which isolates the fault to the faction gate.
3. Try any other occupying-faction item the shop rules match (backpacks, headwear via the clothes rules, which do set `m_bIncludeOccupyingFactionItems 0`) — confirms the scope.
4. Repeat with a player holding `IllegalImports` — that branch uses `GetAllNonOccupyingFactionItems`, so it should already be consistent with the server.
