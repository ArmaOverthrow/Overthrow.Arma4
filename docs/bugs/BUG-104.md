## Symptom

Workbench SP, 2026-08-08: start a game, save, restart, choose **Continue** → the player's money reads **$0**.

Reported against `playthrough004/savepoint000`. The save is not at fault — decoding its WorldState blob shows the player record present and correct:

```
$type OVT_PersistedPlayer
persistentId  d13d3018-3b6a-461e-af2d-9e8ee5c4fddf
name          Aaron Static
money         0x000186A0   = 100000
initialized   1
```

The restore worked too. The continue session's log shows the record being applied and the body coming back:

```
[Overthrow] Restoring a started campaign from the save point
[Overthrow] Preparing returning player: d13d3018-3b6a-461e-af2d-9e8ee5c4fddf
[Overthrow] Player 1 restored from their stored body, gear intact
```

## Root cause

**`SetupPlayer()` never runs on the load path, so the session ID maps are empty for the whole continued session.**

`OVT_PlayerManagerComponent.SetupPlayer()` — which writes `m_mPersistentIDs` / `m_mPlayerIDs`, sets `OVT_PlayerData.id`, and spawns the player's `OVT_OverthrowController` — is called from exactly one place: `OVT_SpawnLogic.DoSpawn_S`, which runs when a player **connects**.

Loading a save point does not make anyone connect: it **replaces the world**. The player manager and its maps are brand new, while the `DoSpawn_S` that mapped the player ran in the world instance that was just discarded. The player stays connected across the transition, so nothing re-runs it. `OVT_OverthrowGameMode.PrepareConnectedPlayers()` went straight to `FinalizePlayerPreparation()` on the strength of a comment that was only true for the fresh-start path:

```c
// SetupPlayer was already called in DoSpawn_S, so just finalize (home, officer, etc.)
```

The money display is simply the first thing anyone notices. The HUD composes two calls — `GetPersistentIDFromPlayerID(runtimeId)` then `GetPlayerMoney(persistentId)` (`OVT_EconomyInfo.c:66,318`) — and the first answers `""`, so `GetPlayer("")` is null and the getter returns 0.

Log evidence from the same session, both consistent with an empty map and neither previously connected to the money report:

```
14:48:15.113  Setting up player: d13d3018-… with playerId: 1     <- the PRE-Continue world only
14:48:20.972  [Overthrow] Player 1 joined group 1000 before they had a persistent id - no recruits moved
```

and no `Created controller entity for player 1` after the reload at all.

**Scope is the whole session, not just the balance.** Every `playerId` → `persistentId` lookup misses (shop transactions, ownership checks, group/recruit handling), and the player has no `OVT_OverthrowController`, so client→server operations that ride it are dead.

**Why MP never showed it:** a dedicated server continues at boot, *before* anyone connects, so joining players go through `OnPlayerAuditSuccess_S` → `DoSpawn_S` → `SetupPlayer` normally. Only a session where the player is already connected when the load happens — SP/listen host pressing Continue — hits it.

## Fix

`OVT_OverthrowGameMode.PrepareConnectedPlayers()` re-establishes the mapping when it is missing, before finalizing:

```c
if (m_PlayerManager && m_PlayerManager.GetPersistentIDFromPlayerID(playerId) == "")
{
    Print("[Overthrow] Player " + playerId + " has no session ID mapping (continued campaign) - running SetupPlayer");
    m_PlayerManager.SetupPlayer(playerId, playerUid);
}
```

Idempotent: on the new-game path `DoSpawn_S` already made the mapping and this is skipped. It is keyed on the mapping (not on `m_aInitializedPlayers`) and sits **above** the finalized-check, because the mapping is more fundamental than finalization — a player who is somehow finalized but unmapped still needs it. `SetupPlayer` also spawns the missing controller.

## Coverage

`OVT_TEST_Campaign_ContinuePlayerIdMapping` (Campaign tier, All group 67 → **68**). Puts a probe balance on the live record, asserts it reads back through the mapping, drops the mapping with `ClearPlayerIdMappings()` (the same public API the disconnect path uses — a real continue is a world transition and would restart the autotest harness), **asserts the $0 symptom reproduces**, then calls `PrepareConnectedPlayers()` and asserts the mapping, the reverse mapping and the balance all come back — and that the balance was not re-granted as if the player were new.

Campaign tier on purpose: `PrepareConnectedPlayers()` finalizes any player not yet finalized (home, starting car, starting cash), and only in a started campaign is the local player already finalized, so the case can provoke nothing but the repair. The case asserts that precondition rather than trusting it.

**Proven able to fail** — with the fix removed:

```
PrepareConnectedPlayers() did NOT restore the session ID mapping for playerId 1
(got '', expected 'd13d3018-3b6a-461e-af2d-9e8ee5c4fddf').
```

**Verified:** compile clean (5924 files), All **68/68**.
