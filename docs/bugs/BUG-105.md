## How this was found

Source verification during `new-player-experience/field-manual` authoring. That feature documented only what it could read in the source, and refused to write "prices rise smoothly as the town runs low" because the code does not do that. Play-testing would be unlikely to surface it: the symptom is a price that is *slightly* wrong in a way nobody has a baseline for.

## Symptom

The shipped design, the shipped tutorial tip and the feature's own docs all describe shop prices as moving with how well stocked the town is. In practice the town-stock term contributes **exactly +10% whenever stock is below the ceiling, and exactly +0% at or above it**. There is no gradient. A town with 1 unit left and a town with `max_stock - 1` units left price the item identically.

The shipped `economy-first-buy` tutorial tip promises the curve in as many words (`Language/localization_Overthrow.st:10102`):

> "Shops buy and sell almost anything, and **their prices move with the town they are in**."

The feature docs record the intended maths as a continuous term, `docs/features/economy/market/implementation.md:61`:

```
GetSellPrice(id, pos)  = price + (1 - stock/maxStock)*price*0.1        (scarcity, ≤+10%)
```

Code and shipped help text therefore disagree.

## Root cause

`OVT_EconomyManagerComponent.GetSellPrice`, `Scripts/Game/GameMode/Managers/OVT_EconomyManagerComponent.c:537-556`:

```c
int stock_level = GetTownStock(townID, id);
int max_stock = GetTownMaxStock(townID, id);
float distance_to_port = DistanceToNearestPort(pos);
price = Math.Round(price + ((1 - (stock_level / max_stock)) * (price * 0.1)) + (price * distance_to_port * 0.0001));
```

`stock_level` (`:547`) and `max_stock` (`:548`) are both `int`, and both getters return `int` (`:584`, `:602`). `stock_level / max_stock` is therefore **integer division**, which yields `0` for any stock below max and `1` at max (and >1 only if stock somehow exceeds max). The bracket collapses to:

| stock vs max | `stock_level / max_stock` | scarcity term |
|---|---|---|
| below max | `0` | `(1 - 0) * price * 0.1` = **+10%** |
| at or above max | `1` (or more) | `(1 - 1) * price * 0.1` = **+0%** (negative above max) |

The port-distance term on the same line is unaffected: `distance_to_port` is a `float` (`:549`), so `price * distance_to_port * 0.0001` evaluates in floating point as intended.

The `if(price < 0) price = 1;` guard at `:551` means an over-stocked town cannot drive the price negative, which is probably why this has never produced a visible defect report.

Scope: `GetSellPrice` is the base of the whole price cascade, so `GetBuyPrice` and `GetShopBuyPrice` inherit the step.

## Fix (proposed)

Cast one operand so the division evaluates in floating point:

```c
price = Math.Round(price + ((1 - (stock_level / (float)max_stock)) * (price * 0.1)) + (price * distance_to_port * 0.0001));
```

Guard `max_stock == 0` first if that state is reachable (an item a town does not trade), since the float path turns a currently-harmless integer division into a division by zero.

**This is a gameplay change, not a docs change.** Every shop price in a stocked town moves by up to 10% the moment it lands, in both directions depending on the town. It needs a gameplay owner's sign-off and probably a balance pass, which is why the field-manual feature documented the vague-but-true "how well stocked the surrounding town is" and quantified nothing.

## Notes

If the intent is in fact a step and not a curve, then the fix is the opposite one: leave the code and correct `docs/features/economy/market/implementation.md:61` and the tutorial string. Either way the two currently contradict each other.

## Resolution finding (2026-08-09) — diagnosis disproven at runtime

The defect this bug describes **does not exist at runtime**. A new Campaign-tier case (`OVT_TEST_Campaign_Economy_ScarcityPriceGradient`, `Scripts/Game/Tests/TestSuites/Campaign/OVT_TEST_Campaign_Economy.c`) seeded a synthetic $1,000 item into a registered shop at town stock 1 / 50 / 100 of max 101 and read `GetSellPrice` at the shop's position — **with the original `stock_level / max_stock` line unchanged**:

```
Scarcity gradient at max stock 101: price 1116 -> 1067 -> 1018 across stock 1/50/100
```

That is exactly the float-division curve (`1000 + (1 − s/101)·100 + ~17 port term`), not the predicted +10%/+0% step. The measurement is trustworthy on two counts, from a second run with the scarcity coefficient mutated `0.1 → 0.0`: the prices moved to `1017 = 1017` (proving the harness compiles the current source, not a stale build) and the case went red (proving the case can fail — the proven-red record for the new test).

**Why the source-read diagnosis was wrong:** EnforceScript's `int / int` does not universally truncate like C. In this expression — nested inside arithmetic containing float operands (`price * 0.1`) — the division evaluates fractionally. Contrast BUG-024, where `57 / 15` in a pure-int context genuinely truncated to 3 and was proven red by mutation: the truncation depends on the enclosing expression's type context. The C assumption was checked against the wrong language.

**What shipped anyway (behaviour-identical):**
- The division is now written `(float)stock_level / max_stock` (`OVT_EconomyManagerComponent.c:551`), matching the `(float)town.stability / 100` idiom two functions down — so the correctness no longer rides on an undocumented promotion rule that a sibling expression (BUG-024's) demonstrably did not follow, plus a defensive `max_stock < 1` clamp.
- The regression test above, which pins the gradient against any future engine/compiler change in division semantics.

**Consequences:** code, tutorial string and `docs/features/economy/market/implementation.md:61` all agree (the curve is real); no gameplay change occurred, so no balance sign-off is needed; the "step" framing in any report that cites this bug (the Sell All exploit report) needs its mechanism reworded — the overstock price collapse is smooth, not stepped, but still unbounded below and clamped at $1, so the exploit consequences stand.

Recommend closing as **invalid (diagnosis disproven)** with the explicitness hardening + test retained.
