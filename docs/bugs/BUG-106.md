## How this was found

Source verification during `new-player-experience/field-manual` authoring. The wiki claimed camps "cannot be placed too close to enemy bases"; the sweep went looking for the check that enforces it and found the branch is dead. The wiki line was removed rather than kept, because it described intent and not behaviour. Play-testing would not surface this as a bug: a player who successfully places a camp next to a base has no reason to think they should not have been able to.

## Symptom

The Camp placeable is configured to require distance from **both** other camps and occupying-faction bases. Only the camp-to-camp rule is enforced. A player can place a camp directly beside an occupying base, while a **Mobile FOB** deployed in the same spot is refused with `#OVT-TooCloseBase`.

## Root cause

`Configs/Resistance/placeables.conf` sets both flags on Camp (`:30` is `m_sName "Camp"`):

```
38:   m_bAwayFromCamps 1
39:   m_bAwayFromBases 1
```

`OVT_PlaceContext.CanPlace`, `Scripts/Game/UI/Context/OVT_PlaceContext.c:247-294`, evaluates the flags as a **chain of mutually exclusive branches, each ending in `return true`**:

```c
if(placeable.m_bAwayFromCamps)
{
    OVT_CampData camp = m_Resistance.GetNearestCampData(pos);
    if(camp)
    {
        dist = vector.Distance(camp.location, pos);
        if(dist < 100) // 100m minimum distance from other camps
        {
            reason = "#OVT-TooCloseCamp";
            return false;
        }
    }

    return true;          // <-- :280, short-circuits everything below
}

if(placeable.m_bAwayFromBases)   // :283, unreachable for anything with m_bAwayFromCamps set
{
    ...
}
```

Camp is the only placeable in `placeables.conf` that sets `m_bAwayFromBases` at all, and it also sets `m_bAwayFromCamps`, so **the base-distance branch at `:283-294` has no reachable caller**. (A second copy of the same base check exists inside the `m_bAwayFromTownsBases` branch at `:309-317` and inside the duplicated `m_bAwayFromBases` block at `:346-358`; neither is reached by Camp either.)

**The server does not close the gap.** `OVT_ResistanceFactionManager.PlaceItem`, `Scripts/Game/GameMode/Managers/Factions/OVT_ResistanceFactionManager.c:661-696`, re-validates client indices, funds, and a 50 m proximity-to-player bound, and then re-runs **only** the item-limit check:

```c
// Re-check item limits (the client menu check is advisory only)
if(!placeable.m_bIgnoreLocation)
{
    OVT_ItemLimitChecker limits = new OVT_ItemLimitChecker();
    string reason;
    if(!limits.CanPlaceItem(pos, persId, reason)) return null;
}
```

It never calls `CanPlace`, so no placement rule other than item limits is server-enforced.

## Contrast: the Mobile FOB path does enforce it

`OVT_ResistanceFactionManager.DeployFOB:466-497` checks every base server-side and refuses:

```c
foreach(OVT_BaseData base : occupyingFaction.m_Bases)
{
    float distance = vector.Distance(base.location, fobPos);
    float restrictedDistance = config.m_Difficulty.baseCloseRange + FOB_DEPLOY_BASE_BUFFER;
    if(distance < restrictedDistance) { ...SendTextNotification("TooCloseBase", playerId); return; }
}
```

So two resistance structures with apparently equivalent intent behave differently in the same spot.

## Fix (proposed)

**This is a design question first.** Is the base exclusion meant to apply to camps at all, or was `m_bAwayFromBases 1` added to the Camp config speculatively?

If it is meant to apply, the code fix is small: make the flags additive rather than exclusive, i.e. drop the early `return true` at `:280` (and at `:293`, `:343`, `:357`) and let each flag contribute a veto, with a single `return true` at the end of `CanPlace`. That changes where camps may legally go, and existing camps already placed inside `baseRange` would become non-conforming (nothing removes them, but the player could not rebuild one there).

If it is not meant to apply, remove `m_bAwayFromBases 1` from the Camp entry so the config stops asserting a rule that does not exist.

Either way, the placement rules should probably be re-checked in `PlaceItem` rather than trusted from the client menu, in line with the guards that were already added there.
