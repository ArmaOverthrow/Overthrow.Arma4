## How this was found

Source verification during `new-player-experience/field-manual` authoring. The wiki claimed officer templates were "available to all resistance members"; the sweep went looking for the code that widens the listing to other players and found none. The wiki claim was replaced with a Known Limitation block describing what actually ships, rather than deleted or left standing. Play-testing would surface this only if two players in the same session compared their equipment-box lists.

## Symptom

An officer saves a loadout as a faction-wide template. It is stored, flagged, persisted and replicated correctly. **No other player ever sees it.** The template appears in exactly one list: the officer's own, indistinguishable from their personal loadouts.

## Root cause

Two halves that never meet.

**Save side sets the flag, keyed under the officer.** `OVT_LoadoutManagerComponent.SaveOfficerTemplate`, `Scripts/Game/GameMode/Managers/OVT_LoadoutManagerComponent.c:338-351`:

```c
void SaveOfficerTemplate(string playerId, string loadoutName, IEntity sourceEntity, string description = "")
{
    ...
    if (!OVT_Global.GetResistanceFaction().IsOfficer(playerIdInt))
    {
        Print(... "is not an officer, cannot save officer template" ..., LogLevel.WARNING);
        return;
    }

    SaveLoadout(playerId, loadoutName, sourceEntity, description, true);
}
```

The final `true` is `isOfficerTemplate`, and it does reach storage (`m_bIsOfficerTemplate` is written at `:2239`, serialised at `:2171`, restored at `:940`, and declared on `OVT_PlayerLoadout.c:19`). But the record is keyed under **the officer's own persistent id** in `m_mLoadoutIdMapping`, in the `playerId_loadoutName` format.

**List side never reads the flag.** `GetAvailableLoadouts`, `:1031-1062`, is the only lister the equipment-box UI calls (`OVT_LoadoutsContext.c:109`):

```c
array<string> GetAvailableLoadouts(string playerId)
{
    array<string> loadoutNames = new array<string>();

    // Add player's personal loadouts from cache
    for (int i = 0; i < m_mLoadoutIdMapping.Count(); i++)
    {
        string key = m_mLoadoutIdMapping.GetKey(i);
        ...
        string keyPlayerId = keyParts[0];
        if (keyPlayerId == playerId)
        {
            ...
            loadoutNames.Insert(loadoutName);
        }
    }

    return loadoutNames;
}
```

`m_bIsOfficerTemplate` is never consulted, and the walk never widens past the exact-key match. So the flag is write-only from the player's point of view: it costs save bytes and RPC bandwidth and changes nothing anyone can see.

**The delete path compounds it.** `OVT_LoadoutsContext.DeleteLoadout`, `Scripts/Game/UI/Context/OVT_LoadoutsContext.c:331-345`:

```c
comms.DeleteLoadout(m_sPlayerID, m_SelectedLoadoutName, false); // Assume personal loadout for now
```

The literal `false` and the comment mean the UI cannot delete an officer template even for the officer who owns it, if the manager routes deletes by that flag.

## The documentation consequence (was open question 16)

The wiki's `getting-started` page still carries the disproved claim, under "Loadout Manager System":

> "**Officer Templates**: Officers can create faction-wide loadout templates"

and lists "**Team coordination** through shared officer templates" as a benefit. The `loadout-manager` page now carries a Known Limitation block saying the opposite. **The two wiki pages contradict each other today**, and that will remain true until this bug is resolved one way or the other.

Deliberately not fixed as a standalone docs edit, because the correct wording depends on the answer here:

- If faction-wide sharing gets finished, the `getting-started` sentence becomes true and needs no edit; the `loadout-manager` Known Limitation block comes out.
- If it is abandoned, both pages should say templates are personal to the officer who saved them.

**One sentence to change either way, once this is decided.**

## Fix (proposed)

**This is a design question: is faction-wide template sharing unfinished or abandoned?**

If unfinished, wiring it up is two changes, both gameplay:

1. A second branch in `GetAvailableLoadouts` that also keeps keys whose record has `m_bIsOfficerTemplate` set, regardless of `keyPlayerId`. Name collisions between a player's own loadout and a template with the same name need a rule, since the return type is a bare `array<string>` of names with no owner attached; the UI's apply and delete paths both re-derive the key from the name, so a collision would silently target the wrong record.
2. An owner-aware delete: `OVT_LoadoutsContext.c:340` must pass the real flag and the real owner instead of `false`, and the manager must refuse a non-officer deleting a template.

If abandoned, remove `SaveOfficerTemplate`, the `m_bIsOfficerTemplate` field and its serialisation, so the save format stops carrying a flag nothing reads.
