## How this was found

Source verification during `new-player-experience/field-manual` authoring. Both help surfaces needed to say what happens when the occupying faction discovers a camp; the sweep followed the target from discovery to arrival and found the arrival handler has no case for camps or FOBs. The manual therefore says the occupying faction "sends troops out towards them" and stops there, which is literally true and deliberately incomplete.

## Symptom

The occupying faction discovers a resistance camp or FOB, marks it as an `ATTACK` target, pays reserve resources to dispatch a special-ops team, and the team walks to the location. **On arrival it does nothing and the target is cleared.** The structure is untouched. The resources are gone.

Because the target is dropped rather than completed-with-effect, the same camp is re-discovered on the next `UpdateKnownTargets()` pass and can be paid for again.

## Root cause

Three sites, all consistent with each other except the last.

**Discovery marks camps and FOBs as attack targets.** `OVT_OccupyingFactionManager.UpdateKnownTargets`, `Scripts/Game/GameMode/Managers/Factions/OVT_OccupyingFactionManager.c:1261-1359`:

```c
foreach(OVT_FOBData fob : resistance.m_FOBs)          // :1316
{
    if(!IsKnownTarget(fob.location))
    {
        OVT_TargetData target = new OVT_TargetData();
        target.location = fob.location;
        target.type = OVT_TargetType.FOB;
        target.order = OVT_OrderType.ATTACK;
        m_aKnownTargets.Insert(target);
    }
}
```

with the equivalent `OVT_TargetType.CAMP` block at `:1266-1276` (and again, duplicated, at `:1328-1338`; the base block is likewise duplicated at `:1278` and `:1340`. `IsKnownTarget` makes the duplication harmless but it is clearly unintended).

**Dispatch spends resources.** `UpdateSpecops`, `:1233-1259`, iterates the same target list with no type filter:

```c
foreach(OVT_TargetData target : m_aKnownTargets)
{
    if(target.completed) continue;
    ...
    if(upgrade && !upgrade.HasTarget())
    {
        m_iResources -= upgrade.SetTarget(target);   // :1247 - the cost is paid here
    }
    ...
}
```

**Arrival handles only two of the four types.** `OVT_BaseUpgradeSpecops.OnUpdate`, `Scripts/Game/Controllers/OccupyingFaction/BaseUpgrades/OVT_BaseUpgradeSpecops.c:34-78`:

```c
if(vector.Distance(aigroup.GetOrigin(), m_CurrentTarget.location) < 20)
{
    //Group has arrived
    //To-Do: Destroy stuff if needed          <-- :37, literal, in the shipped source
    bool inrange = OVT_Global.PlayerInRange(m_CurrentTarget.location, 200);
    if(m_CurrentTarget.type == OVT_TargetType.BASE)          // :39
    {
        ... StartBaseQRF ...
    }else if(m_CurrentTarget.type == OVT_TargetType.BROADCAST_TOWER)   // :52
    {
        ... capture timer, ChangeRadioTowerControl ...
    }else if(!inrange){                                       // :72
        //Remove target and wait for new orders
        m_CurrentTarget.completed = true;
        m_CurrentTarget = null;
        return;
    }
}
```

A `CAMP` or `FOB` target falls through both handled branches into `else if(!inrange)` and is simply discarded. The `//To-Do: Destroy stuff if needed` comment is the original author saying exactly this.

Note the `!inrange` condition: if a player *is* within 200 m, even the discard does not run, and the team sits at the target indefinitely holding an upgrade slot.

## Fix (proposed)

**This is a design question: is a camp or FOB supposed to be destroyable by the AI?**

If yes, `OnUpdate` needs a `CAMP`/`FOB` branch that does something (delete the camp record via `OVT_ResistanceFactionManager`, destroy the placed entity, notify the owning player) and marks the target `completed` so it is not re-paid for.

If no, the cheap correct fix is at the other end: stop marking camps and FOBs as `ATTACK` targets in `UpdateKnownTargets` (or make `UpdateSpecops` skip target types the specops upgrade cannot service), so no resources are spent. That is a behaviour change too, since the patrol-towards-your-camp behaviour players may already read as intentional pressure would disappear.

Whichever way it goes, the `else if(!inrange)` fallthrough is worth tightening independently: a target type nobody handles should be logged, not silently swallowed.

## Resolution (closed 2026-08-20 — obsolete, system removed)

`OVT_BaseUpgradeSpecops` and the whole `Scripts/Game/Components/BaseUpgrades/` tree were deleted by `virtualization/base-defense-migration` (2026-08-18); `UpdateSpecops()` and the ATTACK dispatch are gone with them. `UpdateKnownTargets()` / `m_aKnownTargets` survive **only** to feed the spatial threat score (`GetThreatByLocation`, where CAMP now has a weight), so a discovered camp or FOB no longer costs the occupying faction anything — the defect as written cannot occur.

What remains is a **doctrine gap, not a bug**: nothing reacts to a discovered camp/FOB at all. That is recorded as a candidate plan ("raid a discovered camp/FOB") for `occupying/objectives`, whose modular registry is where such a reaction belongs. Closed with `occupying/base-upgrades` (retired).
