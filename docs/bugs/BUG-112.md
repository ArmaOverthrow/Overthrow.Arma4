## How this was found

Source verification during `new-player-experience/field-manual` authoring. The manual set out to describe what each wanted level means and what raises you to it, and could not: two of the five levels have no escalation path. The old wiki text papered over it with a promise ("aircraft will set level 5 if aircraft are added"), which was removed rather than kept as a forward commitment. Play-testing cannot surface this as a bug, only as a player never seeing the fifth star and having no way to know whether that is the system or their own play.

## Symptom

The HUD renders a five-star wanted meter. **The fifth star can never light.** The first star lights only while a wanted level is decaying back to zero, never as the result of anything the player does.

## Root cause

**Nothing in the codebase sets 5, and nothing sets 1 as an escalation.** Every call site, from a repo-wide grep of `SetBaseWantedLevel(` / `SetWantedLevel(`:

| Site | Level |
|---|---|
| `SCR_AIConfigComponent.c:17` | 2 |
| `SCR_CharacterDamageManagerComponent.c:29,35` (any damage) | 2 |
| `SCR_CharacterDamageManagerComponent.c:71,77` (any kill) | 3 |
| `SCR_CharacterDamageManagerComponent.c:123,129` (vehicle collateral) | 3 |
| `OVT_PlayerWantedComponent.c:286,300,362,528,538,566` | 2 |
| `OVT_PlayerWantedComponent.c:779` (`newLevel`, computed) | 2 or 4 |
| `OVT_PlayerWantedComponent.c:228`, `OVT_OverthrowGameMode.c:1122` | 0 (clear) |
| `OVT_PlayerWantedComponent.c:551` (decay) | `m_iWantedLevel - 1` |

The one dynamically computed value, `newLevel` in the visibility scan, is only ever assigned `2` (`:714`, `:723`) or `4` (`:735`, `:753`). It is initialised from the current level at `:681` and applied at `:779`, so it cannot exceed 4 either.

`SetBaseWantedLevel` only ever raises (`:67`, `if(m_iWantedLevel < level)`), so **4 is the hard ceiling of the system**. Level 1 is reachable only through the decay step at `:551`, `SetWantedLevel(m_iWantedLevel - 1)`, on the way down from 2 to 0. Both the escalation timer branch (`:72-77`) and the decay timer branch (`:553-558`) already special-case level 1 with `wantedOneTimeout`, so a distinct short-tail level 1 is clearly intentional as a decay state.

The HUD draws five regardless. `OVT_WantedInfo.UpdateWantedLevel`, `Scripts/Game/UI/HUD/OVT_WantedInfo.c:56-74`:

```c
int i;
for(i=0; i<m_Wanted.GetWantedLevel(); i++){
    Widget w = m_wRoot.FindWidget("Frame0.WantedLevel.Star" + i);
    if(w) w.SetVisible(true);
}

for(; i<5; i++){
    Widget w = m_wRoot.FindWidget("Frame0.WantedLevel.Star" + i);
    if(w) w.SetVisible(false);
}
```

The `5` is a literal and `Star4` is presumably present in the layout, permanently hidden.

## Fix (proposed)

**This is a design question: is the fifth star dead UI, or is a trigger missing?**

Either:

- **A trigger is missing.** Decide what earns level 5 (the removed wiki text suggested aircraft; a sustained level-4 pursuit, or an attack on a base, are other candidates) and add it. This is a gameplay design task, not a code fix.
- **The fifth star is dead UI.** Drop the meter to four stars: change the `5` in `OVT_WantedInfo.c:70` to a named constant matching the real ceiling and remove `Star4` from the layout. Cosmetic and safe.

Do not "fix" this by clamping or by widening the range without a decision; the meter's maximum is a statement to the player about how much trouble is possible, and it should match the system.
