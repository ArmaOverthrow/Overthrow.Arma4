## How this was found

Source verification during `new-player-experience/field-manual` authoring. The recruit data model advertises a training mechanic, so the sweep went looking for it in order to document it, and found the flag has no producer and no consumer. It was deliberately left undocumented on both help surfaces rather than described as a feature that does not exist. Play-testing cannot surface this at all: the symptom is bytes in a save file and a field on the wire, both invisible.

## Symptom

`OVT_RecruitData` carries a training state that is fully plumbed through persistence and replication, and is **never true and never consulted**. Nothing sets it, nothing branches on it, no UI shows it. It is either an unshipped feature or dead weight in the save format and in every recruit RPC.

## Root cause

The fields are declared with documentation comments that describe a real mechanic, `Scripts/Game/Data/OVT_RecruitData.c:25-29`:

```c
//! Whether the recruit is currently in training
bool m_bIsTraining = false;

//! Game time when training will be complete
float m_fTrainingCompleteTime = 0;
```

A repo-wide grep for `m_bIsTraining` / `m_fTrainingCompleteTime` returns **eleven hits and not one of them is a write of `true` or a read that affects behaviour**:

| Site | What it does |
|---|---|
| `OVT_RecruitData.c:26,29` | Declaration, initialised `false` / `0` |
| `OVT_RecruitManagerSerializer.c:128-129` | Save: `record.isTraining = recruit.m_bIsTraining` |
| `OVT_RecruitManagerComponent.c:363-364` | Load: `recruit.m_bIsTraining = record.isTraining` |
| `OVT_RecruitManagerComponent.c:2032-2033` | Wire write: `writer.WriteBool(recruit.m_bIsTraining)` |
| `OVT_RecruitManagerComponent.c:2113-2114` | Wire read: `recruit.m_bIsTraining = isTraining` |
| `OVT_RecruitManagerComponent.c:2305,2309` | `RpcDo_RecruitCreated` initialises both to `false` / `0` |

The only paths that can put a `true` into `m_bIsTraining` are the load and wire-read paths, which can only reproduce a value some earlier session put there, and no earlier session can have, because there is no setter. The state is provably unreachable.

`m_fTrainingCompleteTime` is likewise never compared against game time, so even if the flag were set, nothing would ever clear it.

## Fix (proposed)

**This is a design question: was recruit training abandoned, or is it still planned?**

- **If planned**, this is a placeholder and the fix is the feature: a way to start training (presumably a client→server request on `OVT_OverthrowController`, per the current convention, not `OVT_PlayerCommsComponent`), a tick that compares `m_fTrainingCompleteTime` against game time and applies whatever training grants, a UI affordance, and a rule for what a recruit in training may and may not do. That is a feature, not a bugfix, and wants its own plan.
- **If abandoned**, remove both fields, their two serializer lines and their two wire lines. The wire saving is negligible (one bool plus one float per recruit per sync) but the save-format entry is a permanent obligation: it will need reading forever, and every future maintainer who greps the recruit model will lose the same half hour this sweep did.

Removing it is the cheaper of the two and reversible; the field can come back with the feature.
