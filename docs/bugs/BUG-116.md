## How this was found

Player report from the live dedicated server, with two console logs supplied: `console_before.log` (session 2026-08-08 09:19:14 → 14:04:57 UTC, ended by a clean shutdown) and `console_after.log` (the next session, 14:29:41 →). Both sessions load the same `playthrough000`.

**Then `savepoint108` was supplied and decoded** (`meta-info.json` + `WorldState/*.blob`, 856,425 B). The decode **eliminated the first prime suspect** — see *What savepoint108 says*. The report below keeps the log evidence unchanged, because it is what it always was, and replaces the causal half.

## What savepoint108 says — and what it eliminates

`savepoint108` is the shutdown save of the *before* session: `meta-info.json` gives `m_eType: 8` (SHUTDOWN), `m_iSavedAtUnix: 1786197894` = **2026-08-08 14:04:54 UTC**, `m_iSavePointNr: 108`, `m_iPlaythroughNr: 0`, `m_sGameVersion: "1.7.0.54"`, playtime 151,914 s. It is the newest save point the 14:29 session could have started from.

### Format notes (so this is reproducible)

`WorldState/<uuid>.blob` is one `BlobBundler` bundle. Layout: `u8 version` then, per collection, `u32 nameLen | name | u32 | u32 | u32 | u32(0)` followed by that collection's records. Persistence ids are stored as **raw 16 bytes, big-endian, byte-aligned** (v8 per `PersistenceIdUtils.Generate`: 48-bit ms timestamp, version nibble `8`, variant `10`, BI subvariant 1). Prefab references are 8-byte resource GUIDs stored **little-endian**. Overthrow's own scripted payloads inside the game-mode record are written to a **bit-packed** sub-stream, so its strings turn up at arbitrary bit offsets — the scan therefore has to run all 8 alignments (decoder: `tools/decode-savepoint.py`).

Sections present, with byte sizes:

| collection | bytes | ids |
|---|---:|---:|
| System | 44,307 | 31 |
| Character | 220,760 | 540 |
| Vehicle | 66,711 | 104 |
| AIGroup | 6,205 | 64 |
| AIWaypoint | 261,114 | 2,838 |
| Structure | 1,543 | 4 |
| Overthrow | 255,780 | 518 |

`Player`, `Item`, `Turret`, `Storage` and `Misc` have no section. For `Item` that is correct and expected: vanilla's `Item.conf` leaves `StorageRoot` false and `ParentHandling` at `ACCEPT`, so an item in a container is only ever written as a **nested child of its parent's record**, never as a root record.

## Mechanism (revised)

`PersistenceSystem.SetId` documents the rule: *"Will fail if the id is already in use."* On load, the first record to claim an id instantiates; every later claimant is rejected and its item is not restored into its container.

### A save point is a full snapshot — measured, not assumed

Three independent samples, all with every collection section present and comparable record counts:

| sample | ids | bytes |
|---|---:|---:|
| server `playthrough000/savepoint004` (2026-08-04, archived in `.tmp`) | 1,028 | 215,187 |
| local Workbench `OVT-Campaign-Test/playthrough004/savepoint000` | 946 | 194,619 |
| …the very next one, `savepoint001` | 944 | 175,854 |
| server `playthrough000/savepoint108` | 4,027 | 856,425 |

Two **consecutive** save points of the same playthrough hold 946 and 944 records. That is not a base plus a delta; each save point is the whole world. The API agrees — `SaveGameManager.Load(notnull SaveGame)` takes exactly one save point — and there is no other on-disk store: `.save/<app_user>/` holds only `game/<mission>/playthroughNNN/savepointNNN/{meta-info.json,WorldState/*.blob}` plus tiny `sessions/*.json` session lists.

**So the load consumes one snapshot, and that snapshot must itself have contained the duplicates. savepoint108 does not. The 14:29 session therefore did not load savepoint108.**

### ELIMINATED 2026-08-09 by local experiment: overwrite accumulation

The hypothesis below was **tested and is wrong**. On a local `tools/launch-server.sh` run with `m_fAutosaveInterval` temporarily at 30 s, the same AUTO save point was overwritten **13 times**; the resulting blob has 94 ids appearing more than once, of which only **5** are same-section repeats — the rest are legitimate cross-references (an AIGroup record listing its member Characters, AIGroup↔AIWaypoint, the System reference list pointing at a Vehicle). `RequestSavePointOverwrite` replaces cleanly.

Also eliminated in the same run: **save-point selection is sound.** The loader took `savepoint003` (most recently written, 319 KB, current world) over the higher-numbered but two-day-stale `savepoint004` (47 KB) — so it picks by write time, not by save-point number, and "reset to an earlier state" is not a wrong-save-point problem.

**What the experiment did find is filed as BUG-118:** every restart adds ~490 permanent records (+473 Character, +16 AIGroup, +16 AIWaypoint on an *idle* world) and removes none, because `SelfSpawn 0` records can never be instantiated and therefore never deleted, while Overthrow rebuilds the same garrisons fresh each boot. That is the accumulating store this bug's stale copies would live in, and it is now the leading environment for the cause — but it is not by itself an explanation, because those AI records cannot self-spawn and so cannot claim an id at load.

**Still not reproduced locally, and the negatives are now substantial.** Zero `already existing id` across **eight** restart cycles of the same playthrough, including:

- items sitting in a placed ammo box across a restart — clean;
- **part of a stack moved from the box into a vehicle**, two autosaves, restart — clean, and all 17 bandage records survived in both containers;
- six further idle cycles taking the save from 555 KB / 2,934 records to **1,149,738 B**, i.e. past the reporting server's 856 KB / 4,027 — clean.

So neither *items changing container* nor *save size and age* is sufficient on its own, and BUG-118's accumulation is not the trigger. Player-character records held flat at 2 across all eight cycles, which independently confirms the withdrawn theory below stays withdrawn on this world.

**The untried transition is an item changing owner through a body** — death and looting — which is the only path that can leave an item's parent record orphaned while the item lives on somewhere else, and the only `SelfSpawn 1` character config in the campaign is the player's (`OVT_SpawnLogic` deliberately overrides vanilla's `ReloadConfig` so an abandoned body keeps it). The reporting server's ammo box lost a map, a radio and binoculars — personal kit, not crate stock — which fits that path.

**Also worth noting as a difference from the rig:** every colliding prefab on the reporting server is from a mod (`Overthrow-BritishForces`, ACE) — Bren, FAL, L42A1, Schermuly, No80, MK6 helmets, ACE epinephrine. Neither mod is available locally (`N:\Projects\Arma 4` has no BritishForces or ACE source), so replaying `savepoint108` faithfully is not possible: its records would reference prefabs that cannot resolve, and an entity that never spawns cannot claim an id.

#### Overwritten save points accumulate

savepoint107 and savepoint108 were both created fresh, by `RequestSavePoint` — and 108 is clean. Overthrow's *autosave* does not create; it calls **`RequestSavePointOverwrite(latestAuto)`** (`OVT_PersistenceManagerComponent.c:239-308`) to keep the save list bounded, and it does so repeatedly into the same slot: in the before session it wrote `savepoint098` **six times** between 09:59 and 10:49, `097` three times, and later `104`, `105`, `106`. The blob filename is a deterministic id derived from the bundle name (`00e63bef-…`, subvariant 2 per `PersistenceIdUtils.FromString`), so every overwrite targets the same file.

If an overwrite **merges into** the existing bundle rather than replacing it, an overwritten save point accumulates one copy of each record per overwrite — and everything observed follows:

- a save point that was never overwritten (108) is clean; ✔ measured
- a save point overwritten *N* times yields *N*−1 rejections per item; the **oldest** copy wins, which is literally *"resetting the inventory back to an earlier state from hours before"*;
- **older items collide more than newer ones**, because they were present for more of the overwrites — and that is exactly the observed profile: Bren/Schermuly/No80 (minted 13:28–13:34 on 08-08) give 95/13 ≈ 8, 49/6 ≈ 9, 33/7 ≈ 5, while FieldDressing UK (08-07 / 08-08 11:07) gives 135/10 ≈ 14;
- the count grows session over session, because the same numbered slot keeps being overwritten.

The remaining gap in this account is which save point the 14:29 session actually loaded — 107 and 108 were the two newest and both were fresh writes. That is the thing the next artifact has to settle.

</details>

### Still standing: the store nothing prunes

`OVT_OverthrowGameMode.HandleOnGameModeEndSaveData()` (`:690-699`) drops vanilla's `PersistenceSystem.ClearStorage(PersistenceSessionStorage)` and `SaveGameManager.Purge()` (`SCR_BaseGameMode.c:723-747`), keeping only `SetSavingAllowed(false)`. That override is *necessary* — vanilla wipes the playthrough on every dedicated restart, which would delete the campaign — but it means the storage every collection is bound to (`Storage "{62488048AF9D8A55}"`) is scratch to vanilla and permanent to Overthrow, and nothing has ever pruned it. **BUG-118 is the measured consequence** (+490 immortal records per restart), and it is the environment in which a stale item record could survive long enough to collide with a live one. It does not by itself explain a collision, because the records it accumulates are `SelfSpawn 0` and cannot claim an id at load — so something else still has to instantiate the stale copy.

> Caveat, stated because it matters: the engine's disposition of a rejected instance is not visible in the log, and the message is native (no `"already existing id"` string exists anywhere in the Reforger scripts). `PersistenceSystem.HandleDelete`'s own doc lists *"Deserialize failure that was configured not to be tolerated"* as a deletion reason, and the observable symptom is exactly "the item is not there", so the inference is that the rejected copy is dropped. It is an inference.

## Withdrawn: the unclaimed-player-body theory

Recorded because the underlying observation is still real and probably still a bug, just not *this* one.

Overthrow disables vanilla's unclaimed-player-character sweep (`Scripts/Game/Modded/SCR_PlayerReconnectData.c:37-44`) and replaces only its hiding half — `OVT_PlayerManagerComponent.ReserveOfflinePlayerBodies()` (`:119`) touches a body only if its id is the **current** `m_sBodyPersistenceId` of a known offline player. Vanilla's `RemoveUnusedCharacters()` also `Clear()`s `m_aPlayerCharacters`, and the serializer only ever inserts (`SCR_ReconnectSerializer.c:78,101`), so with the sweep disabled that set is append-only. Both logs print **17 known, 5 recognised** on a server with ~6 players, and `Overthrow.conf:70-72` gives the player-character config `SelfSpawn 1`, so every surviving player-body record is instantiated on every load.

The blob does not support this as the cause of the item loss: the rejected ids live in the Overthrow and Vehicle sections, not the Character section, and none is duplicated. **File the unclaimed-body accumulation separately** if it holds up — 12 unrecognised, unhidden, permanently re-saved bodies is its own problem, and `m_aPlayerCharacters` growing without bound is a second.

## Instrumentation shipped (2026-08-09) — status in-progress

Five player-driven reproductions all came back clean (see above), so rather than a sixth guess this
ships a diagnostic and waits for the affected server to speak.

**`Scripts/Game/Modded/SCR_PersistenceSystem.c`** (new, compile clean at 5,926 files) hooks two
scripted events on the persistence system:

- **`HandleDelete`** — raised for every entity the system destroys, and vanilla's own doc lists
  *"Deserialize failure that was configured not to be tolerated"* among its reasons. So a rejected
  item passes through it, still attached to the storage it was being restored into. For each one it
  records the prefab and walks up the hierarchy to the nearest ancestor with a persistent id.
- **`OnAfterLoad`** — prints the per-load summary: total destroyed, a tally **per container id**, and
  a tally per prefab. Silent when nothing is wrong, so healthy servers pay nothing.

This answers the two things the engine's native error line does not:

1. **whether a rejected item is really destroyed** — until now an inference from the player's
   symptom, flagged as such in *Mechanism* above;
2. **which container it was being restored into** — half of the duplicated pair, and the half no
   artifact has ever supplied.

What it cannot see is the rejected id itself: assignment has already failed by deletion time, so
`GetId()` answers null. The id is in the engine's own line — pair the two by prefab and by order,
since both sequences are emitted in the same load in the same order.

**A note against a plausible-but-useless design:** a *save-time* walk of live containers looking for
an item under two parents would never fire. The duplication is in the save, not in the world; a live
inventory is always self-consistent. The deletion hook is the only place the fault is observable
from script.

## Lead: `RequestSpawn` against a record whose instance is already live

Measured 2026-08-09, incidentally, while BUG-118 was being fixed. A load-time orphan sweep that
called `RequestSpawn` collection-wide (since removed — see the NOTE block in
`OVT_PersistenceManagerComponent`) produced **1,194 `already existing id` errors in one boot**, the
first local reproduction of this bug's signature. Its cause is known exactly: the request touched a
record whose instance was already live, and the engine retried the collision several times a second
without ever completing.

That makes **"some path is requesting a spawn for a record that is already instantiated"** the
strongest surviving hypothesis, and Overthrow calls `RequestSpawn` in exactly three production
places — recruit bodies (`OVT_RecruitManagerComponent`), player bodies (`OVT_SpawnLogic`) and player
vehicles (`OVT_VehicleManagerComponent`). All three had `FindById` fast paths added under BUG-086
*precisely because* "the body is already in the world", which is the same failure mode caught once
already.

The shape does not match perfectly and that must not be glossed over: the sweep's rejections were on
the **character itself**, whereas the server rejects **only items, never the container**. So this is
a lead, not the answer. The instrumentation above is what distinguishes them — if the loss is
concentrated under one container id, that container is what something is re-requesting.

## Fix (proposed — do not apply before the remaining save points are read)

Sketch only; the real fix depends on which of the two replay sources it is.

1. **If overwrites accumulate:** stop overwriting. `AutoSave()`'s use of `RequestSavePointOverwrite` (`OVT_PersistenceManagerComponent.c:239-308`) exists only to bound the save list, copying vanilla's own UI idiom (`SCR_SaveSessionToolbarAction.c:75`) — but vanilla overwrites a slot a handful of times from a menu, not every 600 s forever on a server that never stops. Creating a fresh save point each time and deleting the oldest gets the same bound with an operation that is demonstrably clean, and the engine already rotates the window itself. This is a small, well-scoped change and it is where I would start.
2. **If it is the session storage:** vanilla prunes it at game-mode end and Overthrow cannot (it would delete the campaign), so Overthrow needs its own bounded prune — drop records for ids no live tracked instance owns — rather than leaving a store that only ever grows. Reinstating vanilla's `ClearStorage` is *not* an option; the `HandleOnGameModeEndSaveData()` override (`:690-699`) exists for a good reason and its header explains it.
3. **Make the failure loud, either way.** The engine reports it as `DEFAULT (E)` with no mod context, which is why hundreds of these scrolled past for at least three sessions unnoticed. A count in `OnAfterLoad` (`[Overthrow] N stored items could not be restored — duplicate ids`) would have surfaced this on day one, and is worth doing regardless of the root cause.
4. **Repair path for existing saves.** The 08-07 ids have already survived several restarts and will keep colliding forever. Whatever the fix, live campaigns need a one-off pass that removes the losing records, or the servers stay broken.
5. **Separately, and independent of this bug:** superseded player bodies are never retired (see *Withdrawn*) — 17 known / 5 recognised — and `m_aPlayerCharacters` grows without bound. Worth its own report.

## Test coverage note

Nothing in the current spine can catch this. `OVT_TEST_PersistenceRoundTripSuite` round-trips *inside one session*; a duplicate id needs two records that disagree about who owns an item, which is only produced across a restart boundary. A case worth adding once the producer is known: give a tracked container an item, force a second record to claim that item's id, load, and assert the container still holds it — proven able to fail by removing whichever guard the fix adds.

## 2026-08-10: SOLVED for the reported loss — arsenal boxes never save their contents (measured, reproduced, root-caused)

The owner supplied a complete artifact set for a FRESH campaign (started 2026-08-09 17:30): five
session logs and savepoints 018–030 (`.tmp/BUG-116/`), plus the report *"Prior to restarting, this
box contained 50 sniper mags, 100 MG mags, 50 flares, 200 FAL mags, 50 smoke grenades, 100 pistol
mags, and 50 grenades. If I try to restock the items and restart the server, they just disappear
again."*

### What the artifacts show

- Sessions 1–3 load clean; session 4 (20:39) throws **732** `already existing id`, session 5 (20:59)
  **117**, and the saves session 5 wrote are structurally clean (System refs 77 → 4, Overthrow-region
  ids 384 → 296) — the corruption **self-heals over two restarts** as the losing records are
  destroyed and purged, then reappears with player activity.
- **508 of session 4's 576 distinct rejected ids exist in NO savepoint supplied** — verified as raw
  bytes at all 8 bit alignments, as ASCII, and in three byte-order transforms. The colliding copies
  are not lying around as extra full records in the loaded save.
- The admin (player "Snowy Fox") uses the **Game Master editor**, spawning `E_ArsenalBox_US/USSR/
  FIA/CIV/UK` at 19:10–19:16 and again at 20:54 — the "weapons box" and the med/equipment boxes ARE
  GM-spawned **arsenal boxes**. The System-section reference entries (77 of them, ↔ Overthrow-region
  entries) are vanilla's editable-entity (GM) registry.
- Record framing decoded: every record (root or nested child) is `id(16B, BE) | 8b 00 00 00 |
  8-byte per-prefab tag | flags | bit-packed payload`. Section headers carry the true root count —
  savepoint023's Overthrow section holds **88 roots**, not 384; the rest are nested children.

### Local reproduction — first ever, and it needed no collision at all

`tools/launch-server.sh` testworld, two boots (temporary hook, since deleted):

1. Spawn `E_ArsenalBox_US`, spawn six vanilla `PaperMap_01_folded` free in the world, insert them
   into the box via its own `InventoryStorageManagerComponent.TryInsertItem`, save.
   **Every map was already tracked at spawn** (`IsTracked` true immediately — see *Why*, below).
2. Restart. **The box restores; it contains 0 items. Zero errors anywhere.** The savepoint holds the
   box record but *not one* of the six map ids and not one extra PaperMap GUID — the items were
   written NOWHERE.

**Why items are all tracked:** `Prefabs/Items/Core/Item_Base.et` — ancestor of essentially every
inventory item — carries the native `Persistence` component, so every item entity registers with
the persistence system at spawn. That is normal and by design (nested children are written with
their ids inside their container's record — it is where the rejected-id population comes from).

**Why the arsenal box loses everything:** the box's matched config is vanilla
`Configs/Systems/Persistence/Configuration/Storage/Arsenal.conf`, whose serializers are
`SCR_ArsenalComponentSerializer` + `FactionAffiliationComponentSerializer` — **no
`BaseInventoryStorageComponentSerializer`**. In vanilla an arsenal's stock is virtual, so its
physical inventory is deliberately not saved. Anything a player deposits in a GM-spawned arsenal
box therefore exists in no record at all: the item's own root write is suppressed (it has a storage
parent, `ParentHandling` ACCEPT), and the box never serializes its contents. Silent, total,
every restart — exactly the owner's report.

### Control experiment — real storage is fine

The identical two-boot run with Overthrow's placeable ammo box (`OVT_AmmoBox_Placed`, matched by
the OVT placeable config which includes `BaseInventoryStorageComponentSerializer`): **all six maps
round-trip with identical ids. Clean.** Vehicles and `StorageBox.conf`-family crates
(`AmmoBox_Base` descendants) carry the storage serializer too. This is also why every earlier
local reproduction with placed ammo boxes came back clean.
