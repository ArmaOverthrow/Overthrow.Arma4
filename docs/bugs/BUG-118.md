## How this was found

Split out of the BUG-116 investigation. Reproduced **locally and deterministically** on `tools/launch-server.sh` while trying to reproduce BUG-116's symptom; it is a different, simpler defect that happens to be measurable in a single restart, and it is almost certainly the reason the reporting server's save grew 4× in four days.

## Symptom

A campaign's save grows without bound across restarts. Nothing the players do is required — an **idle** server that boots, sits for 100 seconds and saves adds ~490 records that will never be removed.

## Reproduction (local, ~4 minutes, no client needed)

1. `Prefabs/GameMode/OVT_OverthrowGameMode.et` → `OVT_PersistenceManagerComponent { m_fAutosaveInterval 30 }` (only to make the loop fast; the defect is interval-independent).
2. `tools/launch-server.sh --scenario testworld --profile OverthrowDS --timeout 100` — it continues the existing playthrough and autosaves.
3. Copy the newest save point's `WorldState/*.blob`.
4. Repeat step 2. Copy the blob again.
5. Diff the two. Use `tools/decode-savepoint.py diff <old> <new>`.

## Root cause

Three things are individually reasonable and collectively unbounded:

1. **AI characters, groups and waypoints are tracked.** `Character_Base.et:41` and `Prefabs/AI/Groups/Group_Base.et` carry the native `Persistence` component, so every garrison soldier, patrol and waypoint Overthrow spawns is registered and written into the save.
2. **They are scoped out with `SelfSpawn 0`** — `Configs/Systems/Persistence/Overthrow.conf`, the `AI` group, overriding vanilla's `{64EACAC5BFDB31EC}`, `{654CB71C1CF2147B}`, `{65DA8623029D589E}`, `{655514594CC39853}`. That override is correct and deliberate (decision v2-5: Overthrow rebuilds this AI itself, so self-spawning it would double every garrison). But it means **no entity is ever instantiated for those records**, so nothing can ever be deleted, and `SelfDelete` — which only fires when a *tracked instance* is destroyed — never gets the chance.
3. **Overthrow rebuilds the same AI on every boot.** `InitBaseControllers()` → `SpawnGarrisons()` / `BuyPatrol()` / `CheckRadioTowers()` spawn fresh entities with **fresh ids**, which are tracked and written as new records alongside the old ones.

So each boot writes a new generation of garrison records and orphans the previous one, permanently.

**Why nothing prunes them:** vanilla treats `PersistenceSessionStorage` as scratch for the session and wipes it at game-mode end (`SCR_BaseGameMode.HandleOnGameModeEndSaveData`, `:723-747` — `ClearStorage(PersistenceSessionStorage)` + `Purge`). Overthrow overrides that method (`OVT_OverthrowGameMode.c:690-699`) and keeps only the `SetSavingAllowed(false)` half. **That override is necessary and must stay** — vanilla's version deletes the whole playthrough on every dedicated restart — but it removes the only thing that has ever cleaned this storage, and nothing replaced it.

## Impact

- **Unbounded save growth.** 4× in four days on the reporting server, and the rate scales with restart frequency, not with player activity.
- **Load time.** That server's `Game::LoadEntities` took **11.56 s** at 4,027 records; the cost is linear in dead records.
- **Memory and save duration** grow with it — the shutdown save on the busy server took ~150 ms, but it is on the same curve.
- **It is probably the substrate for BUG-116.** A store that only ever accumulates is where stale copies of item records live, and BUG-116's collisions are stale item records claiming ids that live containers also claim. BUG-116 is not yet root-caused; this is the leading environment for it.

## Fix (proposed)

The shape is "prune what Overthrow knows it will rebuild", and there are two places to do it:

1. **At the source — do not persist what is rebuilt.** The cleanest fix is for these entities never to enter the store at all, which means untracking rather than scoping the *spawn* out: `StopTracking(entity, removeData: true)` on garrison/patrol characters, groups and waypoints at spawn time, or removing the `Persistence` component from the prefabs Overthrow spawns. `SelfSpawn 0` answers "don't bring it back"; it does not answer "don't keep it".
2. **At the sweep — prune orphans on load.** Once persistence reaches ACTIVE, any record in the AI collections has no live instance by definition (they cannot self-spawn), so it can be dropped wholesale. This is the cheaper change and it also repairs existing saves, which option 1 does not.

Both need care around the one AI-character record that legitimately outlives its entity: **recruit bodies**, which `OVT_RecruitManagerComponent` deliberately keeps and asks for again by id (`RequestSpawn` against the `Character` collection). Any prune must exclude ids held in `OVT_RecruitData.m_sBodyPersistenceId`, and any player-body ids in `OVT_PlayerData.m_sBodyPersistenceId`.

## Test coverage note

Assertable in the test world without a restart, which is unusual for a persistence defect and worth taking: spawn a garrison, take a save point, count records in the AI collections, then re-run the manager's spawn path and assert the count did **not** double. Proving it can fail is trivial — the current code fails it.

## Fix (implemented 2026-08-09)

**Shipped: option 1 only — untrack at the source.** Every entity Overthrow rebuilds from manager
state is released from persistence tracking at spawn, so it never writes a record:

- `Scripts/Game/Modded/SCR_AIGroup.c` (new) — the chokepoint for all three AI kinds: the group
  entity (`EOnInit`), every member the group spawns from its own prefab list
  (`AddAIEntityToGroup` — recruits and players enter groups through `AddAgent` paths and are
  untouched), and prefab-defined waypoints (`AddWaypointsDynamic`).
- `OVT_Global.SpawnEntityPrefab`/`SpawnEntityPrefabMatrix` — any spawned `AIWaypoint` is untracked
  (covers every config waypoint helper, incl. the three that bypass `SpawnWaypoint`).
- `OVT_TownController.SpawnGunDealer` — the dealer is a lone character prefab outside the group
  chokepoint.
- `OVT_PersistenceManagerComponent.UntrackTransient()` + a retry queue — **load-bearing timing**:
  native lazy registration lands frames after spawn, so a bare `StopTracking()` at spawn has
  nothing to act on; the queue releases each entity once `IsTracked()` turns true (return values
  of Start/StopTracking are not trusted). Expiring entities log their class name as a leak
  tripwire.

**Measured on the bug's own repro** (idle TestWorld restarts, blob decoded before/after):
pre-fix +492 brand-new ids and ~+71 KB per cycle; post-fix **0 ids minted during the session
reach the save** across two consecutive cycles, blob flat (1.49 MB → 1.46 MB). Autosaves and the
shutdown save all complete.

**Option 2 (prune orphans on load) was built, measured, and REMOVED** — the proposal in this bug
does not survive contact with the engine:
- A collection-wide `RequestSpawn` that touches a record whose instance is live (self-spawned
  player bodies/corpses in `Character`) retries `Attempted to deserialize meta data for an
  already existing id` several times per second **forever**; the request never completes and
  every subsequent save is wedged behind it (measured: 1,194 retries across 4 live ids, autosave
  and shutdown save both lost). Exclude lists cannot cover corpse ids, which are not enumerable
  from script.
- Even on `AIGroup`/`AIWaypoint` (no live stored instances possible), the request never invoked
  its callback in any clean run — nothing was ever pruned through it.

**Residual, accepted:** orphans already in old saves stay there — bounded dead weight that no
longer grows (this playthrough's ~8,500 records; the reporting server's ~4,000). A server owner
who wants the load-time cost back can only start a fresh playthrough. The full reasoning lives in
a comment block in `OVT_PersistenceManagerComponent.c`.

**Test:** `OVT_TEST_Init_Persistence_TransientAINotTracked` (Init tier, All 71 → 72) — spawns an
occupying-faction group + patrol waypoint the way garrisons get them, asserts group/members/
waypoint end untracked while a directly spawned control character IS tracked (the control keeps
the case from passing vacuously in a world where lazy registration never ran). Proven able to
fail: with the member untrack disabled it reports "member 0 of the spawned group is still
persistence-tracked".

## Fix verification (2026-08-09)

The spawn-side untracking fix (`Scripts/Game/Modded/SCR_AIGroup.c` +
`OVT_PersistenceManagerComponent.UntrackTransient`) was measured on the same TestWorld playthrough
the defect was found on, starting from an already-bloated 1,457,344 B / 8,505-record save.
Compile clean (5,926 files). Ten restart cycles.

| | before fix | after fix |
|---|---:|---:|
| records added per restart | **+492** | **+32** |
| AIGroup records in the save | 519 | **0** |
| AIWaypoint growth per restart | +16 | **0** |
| duplicate-id errors on load | 0 | 0 |

**Two of the three collections are completely fixed**, and the fix also cleaned up the 519 existing
orphaned AIGroup records rather than merely stopping new ones.

### Residual: 32 Character records per restart, 0 removed

Isolated with a single clean cycle (`tools/decode-savepoint.py diff`):

```
collection    old    new   delta
Character    8357   8389     +32
AIGroup         0      0      +0
AIWaypoint    530    530      +0
added: 32   removed: 0
```

Decoding one of the leaked records shows `m_rStoreName` = **`{64EACAC5BFDB31EC}`**, the AI-character
persistence config — and a `SCR_CharacterInventoryStorageComponent` with populated `slots`, so each
one drags its inventory's child records along with it.

So some AI characters still reach the store without passing the `SCR_AIGroup.AddAIEntityToGroup`
chokepoint. Town civilians are not the cause (`OVT_TownController.SpawnCivilian` spawns an
`SCR_AIGroup`, so its members do pass through it) and the gun dealer is already handled explicitly.
The remaining candidates are characters added to a group by a path other than the group's own
prefab spawning — the `AddAgent` / `RequestAddAIAgent` route the fix deliberately excludes to
protect recruits and player bodies.

**Not closed.** A 94% reduction and the AIGroup/AIWaypoint half fully solved, but the bug's claim —
unbounded growth — still literally holds at 32 records per restart, and each carries an inventory.
Worth finishing rather than closing: the diagnosis is now exact and the measurement takes 90 seconds
(`tools/launch-server.sh --scenario testworld --profile OverthrowDS --timeout 100`, then
`tools/decode-savepoint.py diff`).

## Residual root-caused and FIXED (2026-08-09, second pass)

The 32 records were **one AI character plus its entire nested kit** (weapon, grenade, clothing,
every magazine and bandage — ~31 child records), minted in a single burst seconds after boot at a
centimetre-identical position every cycle. Decoding named the record's prefab:
`Character_USSR_Rifleman_Variant_1.et` — a **variant** of vanilla's `Character_USSR_Randomized`
"random soldier".

**The bypass:** `SCR_AIGroup.SpawnGroupMember` spawns members through
`game.c:90 SpawnEntityPrefabEx(res, randomizeEditableVariant: true)`, which resolves
`SCR_EditableEntityComponentClass.GetRandomVariant()` and spawns the *variant* prefab. This one
character then joined its group through its own AI activation rather than `AddAIEntityToGroup`
(vanilla `AddAgent`'s own comment: *"Add to group only if some other system... wasn't faster"*), so
the fix's member chokepoint never saw it. A temporary pre-save census (enumerate live characters,
print the tracked ones) was what isolated it — no tracked USSR character passed through
`UntrackTransient` at all, which killed every "untrack failed" theory and left "never hooked".

**Fix:** `modded SCR_AIGroup.OnAgentAdded` — fires for **every** agent that enters **any** group,
whatever spawned it — untracks the agent's character unless it is (a) player-controlled at join
time (every vanilla player join path hands over the controlled entity), or (b) a recruit
(`OVT_RecruitManagerComponent.GetRecruitFromEntity` — the entity→recruit mapping is established
before the group add on all three flows: `AddRecruit`, `AttachRecruitBody`, and the
existing-entity re-add). Also closed while hunting: `OVT_SpawnFactionCharacterJobStage` and
`OVT_SpawnCivilianJobStage` spawn lone job-target characters that are rebuilt by stage replay on
every restore — both now untrack their spawn.

**Verified:** compile clean, Fast 39 / All 72 green, and two measured restart cycles on the same
bloated TestWorld playthrough came back **`added: 0  removed: 0`, byte-identical blob
(1,486,725 B → 1,486,725 B)**. A restart now writes literally nothing new. The census diagnostic
showed zero tracked occupying-faction characters at save time (only the two reserved player bodies
and a corpse, all legitimate).

**Play-test check worth doing (recruit protection):** dismiss/despawn a recruit, restart, respawn
it — gear should still come back (the `OnAgentAdded` exclusion is what protects recruit bodies,
and no automated case covers a recruit joining a group).
