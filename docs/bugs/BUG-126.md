> Filed from the `/discover-feature resistance/fob` code investigation (2026-08-09). Evidence is source-level; not yet reproduced at runtime.

## Symptom

With zero FOBs deployed (the normal early-game state), positions near the world origin (map corner) are treated as "near an FOB":

- `OVT_MapContext.c:121-123`: fast travel legal within `MAX_FOB_TRAVEL_DIS = 40` m of origin.
- `OVT_BuildContext.c:332-334`: `m_bBuildAtFOB` buildables placeable within `MAX_FOB_BUILD_DIS = 100` m of origin (same shape in `OVT_PlaceContext`).

On Everon the origin corner is open water, so the practical impact is map-dependent — but the defect travels to every terrain, and a coastal origin makes it a real teleport/build anomaly.

## Root cause

`OVT_ResistanceFactionManager.GetNearestFOB` (`Scripts/Game/GameMode/Managers/Factions/OVT_ResistanceFactionManager.c:1169-1182`) initialises its result to the zero vector and returns it unchanged when `m_FOBs` is empty (or when nothing beats the initial "nearest" seed). Callers then do a plain distance check against the returned vector with no "was anything found?" signal.

## Fix (proposed)

Give the query an explicit not-found contract — return `false`/null via `GetNearestFOBData` (which callers can null-check) or an `out` success flag — and update the three call sites (map fast-travel gate, build context, place context). A Logic-tier test can pin the empty-registry behaviour (the `resistance/core` doc already lists "empty-registry null/zero-vector behaviour" as a test candidate).

## Notes

- `GetNearestCamp`-family helpers share the seed-vector shape; audit them in the same pass.
- Filed against `resistance/fob` because the FOB query is the exploitable surface; the fix touches `towns/map-info`'s fast-travel gate too (its doc already notes the zero-vector default).
