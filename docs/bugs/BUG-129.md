## How this was found

Community report (2026-08-09): *"Bought and set up a FOB truck. After a couple of hours, the truck and its tent disappeared, though the FOB was still active. I found the truck back by the car shop where I'd bought it. Drove it back and set it up again — judging from the map markers, there were now technically two FOBs on this same spot. This morning I restarted the server; the truck was a wreck. Despite the state of the truck, the FOB is still active, and both markers are still on the map."*

Investigated 2026-08-09. **Every leg of the report reproduces from source, and the two key events are captured verbatim in production logs already in the repo** (`.tmp/logs/console_before.log` / `console_after.log` — the same session logs BUG-116 was filed from).

The mod owner's initial hypothesis — a locked deployed FOB was grabbed by the locked-vehicle-on-logout cleanup — is **half right**: the disconnect→reconnect flow is the trigger and the deployed FOB is indeed fully in scope for that system (no FOB exclusion exists anywhere). But that system only *hides an entity in place* — it cannot move anything to a car shop. The mover is an adjacent defect in the same component: a **ghost vehicle registration**.

## Symptom chain (each leg → code path)

1. **"Truck and tent disappeared, FOB still active"** — owner logged out with a locked vehicle: `OVT_VehicleManagerComponent.OnPlayerDisconnected` (`:511-522`) starts a 60 s timer (`OFFLINE_VEHICLE_DESPAWN_TIME`, `:83`); `DespawnPlayerLockedVehicles` (`:598-621`) → `OVT_PersistenceReservation.Reserve` (`OVT_PersistenceReservation.c:66-85`) clears `VISIBLE|TRACEABLE|ACTIVE`. The deployed FOB (truck body + tent + net + flag are one entity's prefab children) vanishes visually **in place**; the `OVT_FOBData` record and its map icon are untouched. The deployed FOB qualifies because it inherits `Wheeled_Base.et` → carries `OVT_PlayerOwnerComponent` and the lock/unlock door actions (`Vehicle_Base.et:4-30`) — a player *can* lock it, and **no cleanup path excludes FOBs** (verified: zero prefab/component/"FOB" checks in any despawn path).
2. **"Found the truck back by the car shop"** — the proven core defect. `OnFOBDeploymentComplete` (`OVT_ResistanceFactionManager.c:1814-1850`) deletes the truck (`:1825`, which also drops its persistence record — `OVT_PersistenceTracking.c:186-190`) but **never removes it from `m_mPlayerVehicleIds`/`m_mVehicleRecords`** (`DropVehicleRegistration` is `protected`, `OVT_VehicleManagerComponent.c:1193` — no caller *can* do the right thing). On the owner's next connect: `RespawnPlayerVehicles` (`:714-757`) → no live instance → `RequestPersistedVehicle` (`:768-848`) → persistence answers `NOT_FOUND` → **`RebuildVehicleFromRecord` (`:1145-1187`) spawns `record.prefab` at `record.position`** — the truck's record, frozen at the shop parking spot where `CaptureVehicleRecord` (`:1038-1067`) wrote it at purchase (`SyncVehicleRecords:1086-1088` refreshes positions only while the vehicle exists, and only at save time). The rebuilt truck also spawns **unlocked**.
   **Logged:** `console_before.log:1024` (`Requesting stored vehicle …`) → `:1038` (`could not be read back from storage - rebuilt {E6A31A5A6EA0AF04}…/OverthrowMobileFOB.et at its last parked position … (contents lost)`), 12 s after that player connected.
3. **"Technically two FOBs on this same spot"** — `RegisterFOB` (`:1106-1121`) is a bare insert with **no proximity/duplicate check** (deploy validation `:483-512` guards only enemy bases/towers), each record minting a fresh `persistentId`; `OVT_MapIcons.c:664-691` draws one icon per record. Both records persist forever (`ApplyPersistedResistance:281-297` matches by id). `UnregisterFOB`/`RpcDo_RemoveFOB` (`:1322-1341`) removes only the *single nearest* record within 10 m on a successful undeploy — the second overlapping record is a permanent orphan icon + fast-travel anchor (same leak family as BUG-121).
4. **"After restart the truck was a wreck"** — the deployed FOB is `RigidBody { Static 1 }` (`OverthrowMobileFOBDeployed.et:4-6`); a **dynamic** body spawned interpenetrating a static one takes the full depenetration impulse. The rebuilt ghost truck (or the next self-spawned vehicle) is the projectile. Wreck state then **persists** via `HitZoneContainerComponentSerializer { WholeHierarchy 1 }` (`Overthrow.conf:96-98`).
   **Logged:** `console_before.log:1124-1131` — 7 min after the ghost rebuild, the deployed FOB at `<6719.38, 88.52, 5655.38>` (5.6 m from that player's home, `:1025`) renders `M923A1_wreck.xob`; `console_after.log:731-732` → `:1334-1341` — next session it self-spawns already wrecked, 3.9 s after load, before any player connected.
5. **"FOB still active, both markers still there"** — FOB records are pure data with no link to any entity; nothing reconciles a record against a missing/wrecked deployed FOB.

## Root causes (in fix-priority order)

- **A. Ghost registration on every deploy** (also on undeploy and vehicle *upgrade*): every deliberate deletion of a registered vehicle — `OnFOBDeploymentComplete:1824`, `OnFOBDeploymentError:1871`, `OnFOBCollectionComplete:1725`, `OnFOBCollectionError:1776`, `OnUpgradeTransferComplete:413`, `OnUpgradeTransferError:427` — leaves its registration alive, and `RebuildVehicleFromRecord` cannot distinguish "record lost" from "vehicle deliberately consumed".
- **B. No FOB identity anywhere**: nothing on `OverthrowMobileFOBDeployed.et` marks it as an FOB (`OVT_ResistanceFOBControllerComponent` lives only on the static flag prefabs), so no cleanup path *could* exclude it today.
- **C. `RegisterFOB` accepts duplicates** at the same position.
- **D. `RebuildVehicleFromRecord` spawns blind** at a stored transform — no clearance check.
- **E. Restart wipes runtime ownership**: `OVT_RplOwnerManagerComponent.m_mOwners` is memory-only and never repopulated server-side after load (`ApplyPersistedVehicles:1101-1123` and `InitialVehicleCleanup:1323-1375` don't call `SetOwnerPersistentId`), so `DeployFOB:528` reads `""` for any pre-restart truck → the deployed FOB spawns **unowned**: unprotected from the garbage system (`SCR_GarbageSystem.c:12-17` requires a non-empty owner), invisible to re-indexing, claimable by anyone. This is an alternative "it disappeared" path that needs no lock at all. *Log discriminator for which path a given report hit: presence/absence of `[Overthrow] Registered player vehicle <id> for <uid>` right after the deploy.*

## Proposed fix (for review — no changes made)

1. **Make `DropVehicleRegistration` public (or add `UnregisterPlayerVehicle`) and call it at all six deliberate-deletion sites** (A). Kills the ghost rebuild outright; single highest-value change.
2. **Per the owner's direction, exclude FOBs from vehicle lifecycle systems entirely** — an FOB truck / deployed FOB should remain in the world always. Add an identity check (compare against `m_pMobileFOBPrefab`/`m_pMobileFOBDeployedPrefab` from config, or add a marker component to both prefabs — B) and skip FOBs in `DespawnPlayerLockedVehicles:613`, `InitialVehicleCleanup:1357` and `RebuildVehicleFromRecord`. Note the reservation system is *non-destructive* (hide-in-place), so this exclusion alone would not have prevented the shop-teleport — (1) is still required.
3. **Duplicate guard in `RegisterFOB`** (refuse or replace a record within ~10 m) and ideally an "FOB already here" deploy validation (C) — also prevents the orphan-marker end state.
4. **Clearance check in `RebuildVehicleFromRecord`** before spawning at a stored transform (D).
5. **Restore `m_mOwners` server-side in `InitialVehicleCleanup`** (`:1351` already holds the uid — call `SetOwnerPersistentId` alongside `RegisterPlayerVehicle`) (E).
6. Recovery for already-poisoned saves: a one-shot reconcile that drops FOB records with no deployed-FOB entity within tolerance, or an admin command — needs design (same caveat as BUG-121).

## Fix implemented (2026-08-09) — all five knobs; pending play-test

**`Scripts/Game/GameMode/Managers/OVT_VehicleManagerComponent.c`:**
- New public `UnregisterVehicle(vehicle)` — retires a registration before a deliberate deletion: removes the id from `m_aVehicles`, `m_mSpawnedVehicles`, `m_mVehicleRecords` and **every** player's id list (an ownership change can leave one id in two lists). Called from the upgrade completion + error handlers here, and the four FOB sites below.
- New `IsMobileFOB(vehicle)` / `IsMobileFOBPrefab(prefab)` — identity via the config prefab pair (`m_pMobileFOBPrefab`/`m_pMobileFOBDeployedPrefab`), no string matching.
- **FOB exclusion (the owner's directive — FOBs remain in the world always):** `HasLockedVehicles` (no timer when the only locked vehicle is an FOB), `DespawnPlayerLockedVehicles` and `InitialVehicleCleanup` all skip FOBs; they are still indexed, never reserved.
- `RebuildVehicleFromRecord` refuses to rebuild either FOB prefab and returns false so the caller drops the registration — **this is the heal for already-poisoned saves**: the existing ghost truck registration on the reporter's server dies the next time its owner connects, instead of re-materialising a truck.
- `RebuildVehicleFromRecord` clearance check: if another `Vehicle` overlaps the recorded spot (3 m sphere), rebuild at the nearest parking spot (parking type derived from the prefab's economy registration) or kerb within 30 m; if neither exists, keep the registration and retry on the next connect. No more dynamic body spawned inside a parked one.
- `InitialVehicleCleanup` now repairs the RplId-keyed ownership maps after a load (`SetOwnerPersistentId`, guarded on the RplComponent) — a pre-restart truck no longer deploys into an unowned, garbage-collectable FOB.

**`Scripts/Game/GameMode/Managers/Factions/OVT_ResistanceFactionManager.c`:**
- All four FOB deletion sites (`OnFOBDeploymentComplete/Error`, `OnFOBCollectionComplete/Error`) call `UnregisterVehicle` before `DeleteEntityAndChildren` — kills the ghost at its source.
- `RegisterFOB` duplicate guard: a registration within 10 m of an existing record (the wire-matching tolerance) reuses that record, updating its owner — no second marker, and re-deploying onto an orphaned record adopts it instead of stacking.

**Verification:** compile-check clean. New Campaign-tier case `OVT_TEST_Campaign_FOB_RegisterDuplicateGuard` (two registrations 5 m apart must produce one record; restores campaign state) — **proven red** by mutating the guard tolerance `< 10 → < 0` ("second registration 5 m away minted a duplicate record"), then green restored. Full All group **73/73 green**.

**Play-test still owed (not automatable):** deploy an FOB, lock it, log out ≥60 s, log back in — the deployed FOB must remain visible throughout and no truck may appear at the vehicle shop; restart the server with a deployed FOB — it must come back intact with one map marker. On the reporter's existing save: the ghost truck registration will be dropped (logged as `Registration … is a mobile FOB … dropping it`) on the owner's next connect; the second orphan marker and the wrecked FOB are pre-existing state this fix does not retroactively repair (an admin cleanup or record edit is the recovery — see BUG-121's caveat).

## Notes

- **Do not** "fix" this by untracking vehicles from persistence: the BUG-118 retry-queue machinery is deliberately AI-only, and `RequestSpawn` against a live instance wedges saves (`OVT_PersistenceManagerComponent.c` NOTE block).
- Cross-references: **BUG-116** (its load log contains the same `OverthrowMobileFOBDeployed.et` creation line; a rebuilt ghost's "(contents lost)" is also an item-loss source worth folding into that investigation), **BUG-118** (nothing prunes stale records — the store ghosts live in), **BUG-121** (orphan FOB records, different trigger), **BUG-122** (upgrade path shares the registration-leak sites).
- Evidence: `.tmp/logs/console_before.log:966-978, 1024-1038, 1124-1131`; `console_after.log:716-732, 1334-1355` (the rebuilt ghost truck's new id `019fe0ac-f60e-870a` persists into the next session).
