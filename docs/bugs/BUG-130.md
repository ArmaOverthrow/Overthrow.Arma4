> Filed from a live-server player report (2026-08-09), root-caused by code investigation. The
> mechanism is the recruit half of **BUG-086** (closed), which measured the defect for player
> bodies and locked vehicles, fixed those two with the reservation model, and explicitly deferred
> recruits: *"Currently documented as an accepted limitation; it is really this bug, and the same
> reservation model applies."* No bug tracked that leftover until this one.

## Symptom

> Player report: recruits respawn after a server restart without the gear they had prior to restart.

The recruit record (name, XP, level, skills) survives; the body does not — the recruit comes back
as the fresh recruit prefab in civilian clothes. On a live server with overnight restarts this is
the *normal* outcome for any player who was offline more than ~10–20 minutes before the restart,
not a corner case.

## Root cause

Gear lives only on the recruit's **body**; the record carries a pointer to the body's persistence
id (`OVT_RecruitData.m_sBodyPersistenceId`). The failure chain:

1. `OFFLINE_DESPAWN_TIME` (600 s) after the owner disconnects, `DespawnPlayerRecruits` →
   `ReleaseRecruitBody` (`Scripts/Game/GameMode/Managers/OVT_RecruitManagerComponent.c:1369`)
   does `Save()` + `StopTracking(entity, removeData: false)` + delete — vanilla's
   "despawn but do not forget" idiom.
2. **That idiom is not durable.** BUG-086's decisive measurement (2026-08-05, in-session, no
   restart): two records released by identical code were both gone 10 minutes later — prime
   suspect a save point pruning untracked-but-kept records. The governing rule recorded in the
   persistence epic: *"Nothing may depend on a record outliving its entity."* Recruit bodies
   still do.
3. When the owner returns, `RequestPersistedRecruitBody` (`:1069`) asks for the dead record →
   NOT_FOUND (or no answer → 15 s watchdog), the body id is **cleared** (`:1181`, `:1233`) and
   `SpawnFreshRecruitBody` (`:1247`) builds the recruit prefab in civilian clothes. Its own doc
   comment names this as "where the old gear-resets-to-civilian behaviour lives".

The one recruit path verified green (SP persistence play-test 2026-08-03, "recruits with gear")
is recruits standing next to an **online** owner at shutdown — those bodies are live and tracked,
so the shutdown save carries them and the request-by-id works. Checklist item 18 (reconnect after
the 10-minute despawn) reconnected inside the short window where the released record still
exists, so it never exercised the loss either. The broken case is precisely a released record
older than roughly one autosave interval — the standard state of every recruit on a server that
restarts while owners are asleep.

## Fix (proposed)

Extend **BUG-086's reservation model** to recruit bodies, as BUG-086 itself prescribed: on the
offline despawn, do not save-and-release — keep the body alive, **tracked**, hidden and
deactivated in place (`OVT_PersistenceReservation` flags idiom), and hand the same entity back on
the owner's return. Fidelity is then by construction (the entity is never destroyed in-session),
and across restarts the body is a live tracked character at save time, which is the already-green
path.

- Cost: up to `MAX_RECRUITS_PER_PLAYER` (16) dormant, invisible, non-simulating characters per
  offline player — same order as the shipped player/vehicle reservations.
- The `RequestSpawn`-by-id path stays as the **post-restart** route (the reserved body is live at
  save time, so after a load it self-… does *not* self-spawn: the AI character config is
  `SelfSpawn 0`. Verify at implementation time whether a reserved recruit body needs the same
  treatment player bodies got (`SelfSpawn 1` scoped config), or whether request-by-id against a
  record whose entity was live at save time keeps working — that half is the verified-green part
  today.
- Keep `SpawnFreshRecruitBody` as the last-resort fallback; a recruit is never lost, only
  downgraded — but after this fix the downgrade should be log-worthy, not routine.

## Verification path (before and after fixing)

The 90-second local loop from the persistence-forensics skill settles it without a client:

1. Arm a recruit distinctively, disconnect the owner, wait out the despawn
   (`Despawned recruit: <id> (stored body <uuid>)`) plus one autosave.
2. `tools/decode-savepoint.py` the newest blob — is the body record still present?  (Expected
   today: no.)
3. Restart via `tools/launch-server.sh`, rejoin, confirm `spawning a fresh one` vs
   `restored from its stored body, gear intact` in the console.

## Fix (implemented 2026-08-09)

The reservation model, exactly as BUG-086 prescribed, in `OVT_RecruitManagerComponent`:

- **`ReserveRecruitBody()`** replaces `ReleaseRecruitBody()` (which is deleted): the body stays
  alive, TRACKED and hidden in place (`OVT_PersistenceReservation.Reserve`), its AI agent is
  deactivated first, the entity→recruit mapping is kept (it is what lets the return path find the
  body, what keeps `SyncRecruitPositions` refreshing its id, and what keeps the BUG-118
  `OnAgentAdded` exclusion protecting it), and the body id is materialised onto the record.
- **`UnreserveRecruitBody()`**: releases the flags and reactivates the AI; idempotent on a body
  that was never reserved, so the quick-reconnect case runs through it unchanged.
- **`DespawnPlayerRecruits`** (now public — the persistence tier's seam) reserves instead of
  releasing; **`RespawnPlayerRecruits`**'s existing-entity branch wakes the body before re-adding
  it to the group; **`OnRecruitBodySpawned`**'s owner-left-mid-flight branch reserves the
  just-arrived body in place instead of releasing it.
- The post-restart path is unchanged and is the always-green one: a reserved body is a live
  tracked character at save time, serializes fully, and `RequestPersistedRecruitBody` asks for it
  by id when the owner returns. The fresh-prefab fallback remains as last resort only.

**Test:** `OVT_TEST_Persistence_RecruitDespawnReservesBody` (Persistence tier — All 75): spawns a
character from the recruit prefab, recruits it via public `AddRecruit()`, waits for lazy
registration, despawns via public `DespawnPlayerRecruits()`, then asserts the body still exists,
is still tracked, is reserved, the record holds a non-empty body id, and the recruit is offline.
**Proven able to fail:** with `ReserveRecruitBody` temporarily reverted to the old
Save/Untrack/delete sequence it reports *"The body entity was destroyed … that is the
save-and-release path BUG-086 proved loses the gear within minutes"*; restored, green.
Fast 40/40 and All 75/75 green.

**Runtime-verified 2026-08-09 (user play-test, local dedicated server on the working tree,
testworld):** recruit a civilian, equip them, disconnect; at 10:00 both recruits logged
`Despawned recruit: <id> (reserved body <uuid>)` with non-empty UUIDs; autosaves carried the
reserved bodies; server restarted; on rejoin both logged `Requesting stored body <uuid>` →
`restored from its stored body, gear intact`, no fallback lines, and the user confirmed in-game
that both recruits kept all their equipment. Closed.

## Test coverage note

The in-session half is assertable in the test world: despawn a recruit via the manager API, then
(simulating the pruning) assert the respawn path's fallback is NOT taken while the record exists.
The actual durability failure needs the restart boundary, which the autotest harness cannot cross
(`SaveGameManager.Load` restarts the harness) — the decode-savepoint loop above is the gate for
that half, as it was for BUG-086/104/116.
