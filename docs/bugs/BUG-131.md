> Filed from the BUG-130 investigation (2026-08-09). Evidence is source-level; not yet reproduced
> at runtime. **Not the cause of the live-server gear-loss report** (the BUG-118 fix, commit
> `9ae7b492`, postdates it) — this is a regression risk in unreleased code, filed so it is caught
> before it ships and so BUG-130's verification is not confounded by it.

## Symptom (predicted)

A recruit hired from a town civilian (the `OVT_RecruitCivilianAction` path) after the BUG-118 fix
has a body with no persistence identity. `m_sBodyPersistenceId` stays empty, so every despawn or
save→restart cycle rebuilds the recruit from the fresh prefab in civilian clothes — the exact
symptom BUG-130 describes, but affecting even short absences and even owners online at shutdown,
and immune to BUG-130's reservation-model fix unless tracking is restored first.

## Root cause

The BUG-118 fix untracks all rebuild-on-boot AI, and town civilians are rebuild-on-boot AI:

- `OVT_TownController.SpawnCivilian` spawns an `SCR_AIGroup`, so every civilian passes
  `SCR_AIGroup.AddAIEntityToGroup` → `OVT_PersistenceManagerComponent.UntrackTransient`
  (`Scripts/Game/Modded/SCR_AIGroup.c`). Correct for civilians — they are BUG-118's leak.
- `OVT_RecruitManagerComponent.AddRecruit` (`:487`) then captures the body id with
  `CaptureRecruitBodyId(…, materialise: false)`. Its comment still assumes *"A civilian standing
  in a town is already tracked (Character_Base.et carries the native Persistence component), so
  this normally resolves immediately"* — **the BUG-118 fix made that assumption false.** An
  untracked entity answers an empty id, and nothing on the recruitment path re-tracks it.
- The `SCR_AIGroup.OnAgentAdded` recruit exclusion (entity→recruit mapping is set at `AddRecruit`
  `:479`, before the group add) only *prevents a further untrack*; it never re-tracks.
  `AttachRecruitBody`'s re-track (`:1432-1433`) runs only on the respawn flows, not on initial
  recruitment.
- The remaining safety net is `SyncRecruitPositions` (`PreShutdownPersist`, before every save) →
  `CaptureRecruitBodyId(…, materialise: true)` → native `PersistenceSystem.Save(entity)` on an
  **untracked** entity. Whether native `Save()` re-registers an untracked entity is unverified
  engine behaviour; the epic's recorded gotchas (`StartTracking()` lies; lazy registration lands
  frames later) argue against relying on it either way.

The tent path (`SpawnRecruit` spawns the recruit prefab directly, native `Persistence` component
registers it, joins the group via `AddAgent` where the exclusion protects it) should be
unaffected — which would make the defect look intermittent in play-testing: tent recruits keep
gear, civilian recruits lose it.

## Fix (proposed)

In `AddRecruit`, after the entity→recruit mapping is written (`:479`) and before
`CaptureRecruitBodyId`, re-track the body explicitly — the same guarded idiom
`AttachRecruitBody` already uses:

```
if (!OVT_PersistenceTracking.IsTracked(characterEntity))
    OVT_PersistenceTracking.Track(characterEntity);
```

Mind the BUG-118 timing facts: the civilian's `UntrackTransient` may still be sitting in the
retry queue when recruitment happens (lazy registration), so the queue must not release an entity
that has since become a recruit — either drop the queue entry on re-track, or have the queue
re-check the recruit exclusion at release time. Update the stale comment at `:484-486` while
there.

## Verification

Local, no restart needed for the first half: recruit a town civilian, then print
`OVT_PersistenceTracking.IsTracked(body)` / `GetPersistentId(body)` — expected today: untracked,
empty id. Then the BUG-130 decode-savepoint loop across a restart proves the gear half. BUG-118's
own fix notes already flag the owed play-test: *"dismiss/despawn a recruit, restart, respawn it —
gear should still come back… no automated case covers a recruit joining a group."*

An Init-tier case is cheap and worth adding with the fix: spawn a civilian group member the way
towns do, run `AddRecruit` on it, assert the body ends tracked (mirror of
`OVT_TEST_Init_Persistence_TransientAINotTracked`, which proves the civilian half). Proven able
to fail by omitting the re-track.

**Runtime-verified 2026-08-09 (user play-test, with BUG-130's fix):** a civilian recruited on the
test server logged a **non-empty** body UUID at despawn (`Despawned recruit: …3c5c13 (reserved
body 019fe4d9-…)`) — the direct observable this bug predicted would be empty — and after a server
restart came back `restored from its stored body, gear intact`, confirmed in-game. Closed.

## Fix (implemented 2026-08-09)

- **`OVT_PersistenceManagerComponent.CancelUntrackTransient(IEntity)`** (new static, next to
  `UntrackTransient`) — withdraws any pending entry for the entity from the transient-untrack
  retry queue, for entities promoted into a must-stay-tracked category after spawning as
  rebuild-on-boot AI. Only the queue is undone; an already-executed release is the caller's to
  reverse with `Track()`.
- **`OVT_RecruitManagerComponent.AddRecruit`** — after the entity→recruit mapping is written and
  before `CaptureRecruitBodyId`: `CancelUntrackTransient(characterEntity)` +
  `if (!IsTracked) Track(characterEntity)` — the same guarded idiom `AttachRecruitBody` already
  uses on the respawn flows. The stale "a civilian standing in a town is already tracked" comment
  replaced with the lazy-registration truth (the id materialises at the pre-save sync or the
  despawn `Save()`).
- Tent path unchanged and unaffected (prefab registers natively, `IsTracked` short-circuits).

**Test:** `OVT_TEST_Init_Persistence_RecruitedTransientCharacterIsRetracked` (Init tier — Fast
40 / All 74): spawns a group through the BUG-118 chokepoints, waits until a member is
meaningfully untracked (tracked control character proves registration landed — same honesty
device as `OVT_TEST_Init_Persistence_TransientAINotTracked`), recruits it via the public
`AddRecruit()`, asserts the body ends tracked again. **Proven able to fail:** with the
`CancelUntrackTransient()`/`Track()` pair commented out it reports *"The recruited body is still
untracked after 901 polls…"*; re-enabled, green. Fast 40/40 and All 74/74 green after the change.

The queue-race half (civilian recruited while its untrack entry is still pending) is covered by
`CancelUntrackTransient` but is not deterministically assertable — the queue resolves within ~1 s
of civilian spawn, and the test world cannot force a recruit into that window.
