## Summary

Once a player uses **"Don't show tips again"** on a tutorial popup, there is **no way to re-enable tips from inside the game**. The flag is persisted per machine and survives every restart, so the only remedy is hand-editing `ReforgerGameSettings.conf` in the profile directory.

## Root cause — the UI that hosts the toggle becomes unreachable

Traced through source, not inferred:

1. The toggle lives on the **modal popup** and calls `SetTipsDisabled(true)` — `Scripts/Game/UI/Context/OVT_TutorialContext.c:601`
2. `m_bTipsDisabled` early-outs delivery **before** `m_Entry` is ever set on the context — `Scripts/Game/Components/Controller/OVT_TutorialComponent.c:408`
3. `HasEntry()` returns `m_Entry != null` — `Scripts/Game/UI/Context/OVT_TutorialContext.c:248-251`
4. The **Tips** main-menu entry is `SetEnabled(false)` when `!HasEntry()` — `Scripts/Game/UI/Context/OVT_MainMenuContext.c:182-187`

So: disable tips → no entry is ever delivered → `HasEntry()` is permanently false → the Tips button is permanently greyed → the modal, which hosts the only toggle, can never be opened again.

`m_bTipsDisabled` is persisted by `OVT_TutorialSettingsAccessor`, so this is not session-scoped — it is permanent for that machine across all campaigns and servers.

## Note: the persistence layer is fine

`OVT_TutorialSettingsAccessor.Reset()` (`Scripts/Game/Global/OVT_TutorialSettingsAccessor.c:155-160`) already writes an empty store with `tipsDisabled = false`, and an Init-tier case already proves both halves round-trip to disk. **Its only caller today is that test.** The defect is purely that no UI path reaches it.

The Init case's own failure text anticipates this shape — *"which would also make 'Don't show tips again' impossible to turn off"* — but it is guarding the **persistence** layer, which works. The **UI** produces the same outcome by a different route.

## Impact

A player who dismisses tips once (easy to do accidentally on the first popup they see) loses the entire tutorial system permanently, with no in-game recovery. This affects the whole `new-player-experience` epic, since every feature in it delivers through this path.

## Suggested fix

An **ungated** main-menu entry that calls `OVT_TutorialSettingsAccessor.Reset()`. It must **not** be hosted behind the Tips entry, which is gated on the same `HasEntry()` check that fails — and which is additionally false on any fresh launch before a tip has fired.

Being fixed now alongside the "reset tutorial progress" feature request, since `Reset()` clears both the seen ids and the disabled flag in one call. Filed so the reasoning survives the fix.

## Discovered
