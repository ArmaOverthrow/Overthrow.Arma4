## How this was found

Code reading during `/discover-feature map/core` (2026-08-10), on the `new-map` branch after merge to `main` (`6b0169e4`). **Not observed at runtime** — no play-test since 2025-08-02. Filed as finding D4.

## Symptom (predicted)

Close the map while the cursor is resting on a location marker (so no `OnMouseLeave` fires), then reopen it and click an empty part of the map. Instead of dismissing the selection, the previous session's location is selected and its info panel opens.

A secondary effect: the dead element handler and its `OVT_MapLocationData` are kept alive by the strong reference until the next hover replaces them.

## Root cause

`m_HoveredElement` is declared as a strong reference:

```
// Scripts/Game/UI/Map/OVT_OverthrowMapUI.c:37
protected ref OVT_MapLocationElement m_HoveredElement;
```

`OnMapClose` clears the other per-session state but not this one:

```
// Scripts/Game/UI/Map/OVT_OverthrowMapUI.c:92-106
override void OnMapClose(MapConfiguration config)
{
    super.OnMapClose(config);                 // vanilla destroys the icon widgets and clears m_mIcons
    m_MapEntity.GetOnMapZoom().Remove(OnMapZoom);
    m_MapEntity.GetOnSelection().Remove(OnMapSelection);
    ForceHideLocationInfo();                  // clears m_bSelectionPinned + m_PinnedElement only
    m_aLocations = null;
    m_SelectedElement = null;                 // <-- m_HoveredElement is not cleared
}
```

`ForceHideLocationInfo` clears `m_bSelectionPinned` and `m_PinnedElement` (`:315-316`) but not `m_HoveredElement`. Normally `OnMouseLeave` clears it via `SetHoveredElement(null)` (`OVT_MapLocationElement.c:174`), but that only fires if the cursor actually leaves the widget — not if the map is closed underneath it (holstering the map gadget, death, another menu taking focus).

On the next map open, `OnMapSelection` branches on it:

```
// Scripts/Game/UI/Map/OVT_OverthrowMapUI.c:44-68
protected void OnMapSelection(vector selectionPos)
{
    if (m_HoveredElement)          // <-- stale non-null from the previous session
    {
        if (m_PinnedElement != m_HoveredElement)
        {
            m_PinnedElement = m_HoveredElement;
            m_bSelectionPinned = true;
            SelectLocation(m_PinnedElement);
            ShowLocationInfo(m_PinnedElement.GetLocationData());
        }
    }
    else { /* unpin + ForceHideLocationInfo */ }
}
```

So the "click on empty space → dismiss" path is unreachable until something hovers a live element and overwrites the stale reference.

## Fix (proposed)

Clear `m_HoveredElement` in `OnMapClose` alongside `m_SelectedElement`. Clearing it inside `ForceHideLocationInfo` would also work and is arguably more cohesive, but check that doing so does not break the hover flow — `OnMouseLeave` calls `SetHoveredElement(null)` *then* `HideLocationInfo`, so ordering matters.

While in this code, consider whether `m_HoveredElement` and `m_PinnedElement` need to be `ref` at all. Vanilla owns the element lifetime via `m_mIcons`; holding strong references here is what turns a stale pointer into a retained dead object.

## Notes

- The rewrite otherwise has a clean, symmetric open/close lifecycle and avoids all four of BUG-069's legacy defects. This is the one piece of per-session state that escapes the teardown.
- Related but distinct: `UpdateIcons` computes a `targetElement` (pinned-else-selected) and then calls `UpdateInfoPanelPosition()`, which ignores it and positions from `m_SelectedElement` only (`:113-126`, `:551`). Harmless today because pinning also selects; recorded as debt rather than a separate bug.
