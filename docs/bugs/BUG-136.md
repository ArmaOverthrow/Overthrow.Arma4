## How this was found

Code reading during `/discover-feature map/core` (2026-08-10), on the `new-map` branch after merge to `main` (`6b0169e4`). **Not observed at runtime** — no play-test since 2025-08-02. Filed as finding D6.

## Symptom (predicted)

Anything that changes while the map is open is invisible until the map is closed and reopened: a town changing hands, a base being captured, a FOB being built or destroyed, garrison counts, ownership changes. With the map open in a moving vehicle, a future vehicle marker would sit at a stale position.

Low priority on its own — map sessions are usually short — but it is a **hard blocker for the Vehicle location type** (`map/location-types` G1), because vehicles move continuously and a frozen position marker is worse than no marker.

## Root cause

Population happens exactly once per map session:

```
// Scripts/Game/UI/Map/OVT_OverthrowMapUI.c:71-90
override void OnMapOpen(MapConfiguration config)
{
    ...
    InitializeLocationTypes();
    PopulateAllLocations();     // each type appends OVT_MapLocationData
    CreateLocationElements();   // one widget per record
    m_MapEntity.GetOnMapZoom().Insert(OnMapZoom);
    m_MapEntity.GetOnSelection().Insert(OnMapSelection);
}
```

The only per-frame/per-event work afterwards is `UpdateIcons` (repositioning) and `OnMapZoom` → `OnZoomChanged` → `UpdateDisplay`, which re-renders each element **from its existing `OVT_MapLocationData`**. Nothing ever re-reads the managers, and no element is added or removed mid-session.

The intended refresh hook exists but is never invoked:

```
// Scripts/Game/UI/Map/Core/OVT_MapLocationElement.c:443-446
void OnLocationDataChanged()
{
    UpdateDisplay();
}
```

A repo-wide grep for `OnLocationDataChanged` returns only this definition — no callers.

## Fix (proposed)

Decide the refresh model deliberately rather than bolting on a timer:

1. **Per-type opt-in polling** — a `m_fRefreshInterval` attribute on `OVT_MapLocationType`; the container re-runs `PopulateLocations` for opting-in types on that interval and reconciles the element set. Simple, and only the types that need it pay.
2. **Event-driven** — types subscribe to the manager invokers they care about (e.g. `OVT_OccupyingFactionManager.m_OnBaseControlChanged`) and call `OnLocationDataChanged()` on the affected element. Cheaper at rest, more wiring per type.

Either way the container needs a way to **add and remove** elements mid-session, not just refresh existing ones — a FOB built while the map is open has no element to update.

Note the interaction with **BUG-135**: any reconciliation that destroys elements must also clear `m_HoveredElement`/`m_PinnedElement`/`m_SelectedElement` if they point at a destroyed element.

## Notes

- This is arguably "not implemented" rather than "broken", but it is filed as a bug because the hook exists, implying the behaviour was intended and simply never wired.
- `map/location-types` G1 (Vehicle) is blocked on this being resolved.
