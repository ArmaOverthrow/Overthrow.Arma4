## How this was found

Code reading during `map/location-types` Phase 3 (2026-08-10), recorded as finding **N4** / **core D8** and deliberately deferred (K9) because it is a `map/core` contract gap, not a location-type defect. **Re-verified against the working tree 2026-08-11** before filing. Never observed at runtime — the symptom is a *missing* behaviour, which no play-test flags as an error.

## Symptom

1. **A priority FOB is not always visible.** Marking a FOB as priority (`isPriority`) changes the info-panel row and nothing else. It disappears at the same zoom threshold as an ordinary FOB, which is the opposite of what "priority FOB for enhanced map visibility" (`OVT_ResistanceFactionManager.c:31`) promises.
2. **No individual location can differ from its type.** Every `OVT_MapLocationType` has exactly one zoom threshold for every record it produces. The per-record data bag supports floats (`OVT_MapLocationData.SetDataFloat` `:100` / `GetDataFloat` `:70`), so a type author will reasonably assume writing a per-location zoom works. It compiles, it runs, and it does nothing.

## Root cause

Both consumers of the zoom threshold read the **type**, never the record:

```
// Scripts/Game/UI/Map/Core/OVT_MapLocationElement.c:296-300  (ShouldUseSmallIcon)
float currentZoom = m_MapEntity.GetCurrentZoom();
float visibilityZoom = m_LocationType.GetVisibilityZoom();
return currentZoom < visibilityZoom;

// Scripts/Game/UI/Map/Core/OVT_MapLocationElement.c:480-484  (SetVisible)
float currentZoom = m_MapEntity.GetCurrentZoom();
float visibilityZoom = m_LocationType.GetVisibilityZoom();
zoomVisible = currentZoom >= visibilityZoom;
```

`GetVisibilityZoom()` (`OVT_MapLocationType.c:401-404`) returns the type's `m_fVisibilityZoom` attribute, set per type in `Configs/Map/OverthrowMap.conf` (fourteen entries, `:7` … `:177`). A repo-wide grep for a per-location visibility key finds **no reader** — the only other mention of `m_fVisibilityZoom` is the Workbench title decorator (`OVT_MapLocationType.c:604-607`).

FOB and House previously wrote such a key. Those writes were **inert** and were removed by `map/location-types` Phase 3, which left the reason in place of the code:

```
// Scripts/Game/UI/Map/LocationTypes/OVT_MapLocationFOB.c:37-41
// NOTE: no per-location "visibilityZoom" is written. OVT_MapLocationElement reads only the
// TYPE-level GetVisibilityZoom() (:315, :498), so a per-record key is inert - priority FOBs
// are NOT always visible today. The element-side fix belongs to map/core and is filed
// separately (implementation.md N4 / K9); the dead writes are removed here so nobody reads
// them as working behaviour.
```

(The `:315`/`:498` in that comment are pre-BUG-136 line numbers; the two call sites are now `:298` and `:482`.)

## Fix (proposed)

Make the element prefer a per-record override and fall back to the type:

1. Add a `VISIBILITY_ZOOM` constant to `OVT_MapDataKeys` (`Scripts/Game/UI/Map/Core/OVT_MapDataKeys.c`) so the key has one spelling.
2. In `OVT_MapLocationElement`, resolve the threshold once — something like a `GetEffectiveVisibilityZoom()` helper that returns `m_LocationData.GetDataFloat(OVT_MapDataKeys.VISIBILITY_ZOOM, -1)` when non-negative and `m_LocationType.GetVisibilityZoom()` otherwise — and use it in **both** `ShouldUseSmallIcon` (`:298`) and `SetVisible` (`:482`). A sentinel is needed because `0` is a legitimate value meaning "always visible" (Town, Base and RadioTower all use it).
3. Restore the FOB write behind the new key: `0` when `fob.isPriority`, otherwise nothing (`OVT_MapLocationFOB.c` `PopulateLocations`, and delete the NOTE comment). House's old write copied the type value and should stay deleted — it was a no-op by construction.
4. Document the key in `map/core`'s contract table (`docs/features/map/core/context.md`) alongside `m_fRefreshInterval`.

Both call sites are hot — they run per element on every zoom change — so the helper must stay a map lookup and a compare, with no manager access (`map/location-types` Q-7).

## Notes

- **Scope check before fixing:** `SetVisible` is also where `ShouldShowLocation` runs, and BUG-136's refresh reconciliation now re-enters this path on a 2–5 s timer. A change here is felt by every marker on the map, not just FOBs.
- This is the last of `map/core`'s seven discovery findings (D1–D7 were filed as BUG-133…BUG-137); D8 was found later, from outside the feature.
- Low priority because the only shipped victim is the priority-FOB flag, whose other effect (the info-panel row) works.
