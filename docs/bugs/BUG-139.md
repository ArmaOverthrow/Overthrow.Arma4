## How this was found

Code reading during `map/location-types` Phase 5 (2026-08-10), recorded as finding **N5**. The FOB/Camp info panels needed a garrison row; the row was made conditional on `> 0` instead of being dropped, precisely because the data is unreliable. **Re-verified against the working tree 2026-08-11**, which turned up a second half the original finding missed (see "The in-session half"). Not observed at runtime — a garrison row that silently does not render looks like a design choice.

## Symptom

Any consumer asking "how big is this FOB's garrison?" gets **0**, in two distinct situations:

- **On every remote client, always.** The record exists (name, position, owner, priority all arrive), the garrison does not.
- **On the server too, for any garrison bought this session.** Only a garrison restored from a save populates the list.

Today the only consumer is the map info panel, which hides the row when the count is 0 (`OVT_MapLocationFOB.BuildInfoRows`, and the Camp equivalent), so the visible effect is a **missing row**, not a wrong number. That is a deliberate mitigation, not a fix — the next consumer to trust `fob.garrison.Count()` gets a confidently wrong answer.

## Root cause

Two independent gaps in `Scripts/Game/GameMode/Managers/Factions/OVT_ResistanceFactionManager.c`.

**1. Garrison is not in any replication payload.**

`RplSave` (`:1231-1258`) writes five fields per camp and five per FOB — `persistentId`, `name`, `location`, `owner`, `isPrivate`/`isPriority`. `RplLoad` (`:1260-1300`) reads the same five. Neither `garrison` (the `ResourceName` prefab list, `:19` / `:36`) nor `garrisonEntities` (`[NonSerialized()]`, `:17` / `:34`) is written.

The incremental broadcasts carry no garrison either: `RpcDo_RegisterCamp` (`:1102`, handler `:1307`) and `RpcDo_RegisterFOB` (`:1135`, handler `:1325`) take `pos, name, playerId, persistentId`. Grepping every `Rpc(` call in the file (`:463`, `:655`, `:1102`, `:1135`, `:1142`, `:1390`, `:1424`, `:1504`) finds **no garrison-related RPC at all** — there is no path, JIP or incremental, by which a client learns of a garrison.

**2. The in-session half — `garrison` is not populated when a garrison is bought.**

All three buy paths (`AddGarrison` `:951`, `AddGarrisonCamp` `:982`, `AddGarrisonFOB` `:1013`) insert into **`garrisonEntities`** only:

```
base.garrisonEntities.Insert(group.GetID());
```

The only writer of `garrison` is `ApplyPersistedGarrison` during a save load (`:273`, `:296`). So `fob.garrison.Count()` is 0 on the authoritative server as well, for the whole session in which the garrison was purchased — it becomes non-zero only after a save/load cycle. Persistence itself is unaffected: `OVT_ResistanceManagerSerializer.WriteGarrison` (`:188`) snapshots the **live entities** (`camp.garrisonEntities`, `:116`; `fob.garrisonEntities`, `:137`) and falls back to the stored list, so garrisons do survive a save. It is only the in-memory `garrison` field that is misleading.

## Fix (proposed)

Pick a scope deliberately — these are separable and the cheap one may be enough.

**Minimum (makes the field honest, server-side):** in all three `AddGarrison*` paths, insert the resolved `ResourceName` into `base.garrison` next to the `garrisonEntities` insert, and remove it in the corresponding despawn/removal path. Then `garrison` means "prefabs this base has" on the server at all times, and the serializer's fallback path stops being the only writer.

**If clients need the count** (which is the question that produced this bug — a map panel that wants to say "Garrison: 3"):
- Add the count to `RplSave`/`RplLoad` for JIP, and
- Add a broadcast for changes. The cheapest shape is a small `RpcDo_SetGarrisonCount(vector pos, int count)` alongside the existing `RpcDo_SetPriorityFOB` (`:655`) pattern, sent after each add and each loss. Replicating the full `ResourceName` list is the wrong trade — a count is what every known consumer wants, and the prefab names are server-side spawn detail.
- Note the ordering hazard: `RplLoad` runs before the client has any FOB records of its own, so the count must ride **inside** the existing per-record loop, not as a separate list.

**Also worth deciding:** garrison losses. `garrisonEntities` holds `EntityID`s of `SCR_AIGroup`s that can be wiped out; nothing observed decrements either list when that happens, so a count — replicated or not — will drift upward over a long session. Whatever counts, should recount.

## Notes

- `OVT_FOBData` is five meaningful fields (`:22-37`); there is **no** FOB upgrade or build state to display beyond what is listed here. A panel wanting richer FOB detail has nothing to read.
- The map panels currently hide the row at 0 rather than print "Garrison: 0". Keep that guard even after a fix — it is correct for a FOB that genuinely has no garrison.
- Consumers to re-check when this is fixed: `Scripts/Game/UI/Map/LocationTypes/OVT_MapLocationFOB.c` and the Camp type both read `garrison.Count()` into `OVT_MapDataKeys.GARRISON_COUNT`.

## Closed 2026-09-03 (bug audit)

Obsolete. Commit cb6c9945 (resistance/high-command) removed FOB and camp garrisons. `RplSave`/`RplLoad` in `OVT_ResistanceFactionManager.c` carry no garrison data, and `OVT_MapLocationFOB.c` writes no garrison row. The cited `AddGarrison*` and `WriteGarrison` paths are gone. Shipped in v1.5.0.
