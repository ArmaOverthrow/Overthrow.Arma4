## How this was found

Code reading during `map/location-types` Phase 6 (2026-08-10), recorded as finding **N6** plus an addendum covering two more instances of the same pattern in the same file. The shop price-indicator was written to compute town stock with its own null-safe loop **specifically to avoid calling `GetTownStock`**, and the missing guards were deferred to `economy/shops` rather than fixed from a map feature. **All three re-verified against the working tree 2026-08-11.** Not observed at runtime — nothing has yet called these from a client on a large map.

## Symptom (predicted)

On a client, a script error and an aborted calculation whenever an entity referenced by `RplId` is not currently resolvable — a shop or port that has not streamed in, has streamed out, or whose `RplComponent` has not yet arrived. The consequences differ per site:

- `GetTownStock` → the caller gets nothing; on the server this sits inside `GetSellPriceAtOffset` (`:563`), i.e. inside every price the game quotes.
- `DistanceToNearestPort` → same, one line later (`:566`).
- `GetShopByRplId` → wherever it is called, including from `CheckShopInit` (`:1813`) at world init.

Because all three feed one expression (`:567`), a single unresolvable id anywhere in a town's shop list is enough to take out that item's price.

## Root cause

All three are the same shape: the result of a lookup that is **documented as nullable** is dereferenced immediately.

**1. `GetTownStock` (`Scripts/Game/GameMode/Managers/OVT_EconomyManagerComponent.c:601-611`)**

```
foreach(RplId shopId : m_mTownShops[townId])
{
    OVT_ShopComponent shop = GetShopByRplId(shopId);
    stock += shop.GetStock(id);   // <-- GetShopByRplId is documented "or null"
}
```

**2. `GetShopByRplId` (`:435-440`) — the addendum**

```
RplComponent rpl = RplComponent.Cast(Replication.FindItem(shopId));
if(!rpl) return null;
IEntity entity = rpl.GetEntity();
return OVT_ShopComponent.Cast(entity.FindComponent(OVT_ShopComponent));   // <-- entity may be null
```

The `rpl` null check is present; the `entity` one is not. An `RplComponent` whose entity has been deleted or not yet attached returns null from `GetEntity()`.

**3. `DistanceToNearestPort` (`:846-858`) — the addendum**

```
foreach(RplId id : m_aAllPorts)
{
    RplComponent rpl = RplComponent.Cast(Replication.FindItem(id));
    float distance = vector.Distance(pos, rpl.GetEntity().GetOrigin());   // <-- two unguarded derefs
```

No check on `rpl`, and none on `rpl.GetEntity()`.

The reason this has not bitten yet is that the price path has historically run server-side, where every id resolves. It becomes reachable the moment client code asks the economy manager anything positional — which is exactly what a map info panel does.

## Fix (proposed)

Guard each site; all three are one-line changes and none changes a result on the server.

```
// GetTownStock (:605-609)
OVT_ShopComponent shop = GetShopByRplId(shopId);
if(!shop) continue;
stock += shop.GetStock(id);

// GetShopByRplId (:437-439)
IEntity entity = rpl.GetEntity();
if(!entity) return null;
return OVT_ShopComponent.Cast(entity.FindComponent(OVT_ShopComponent));

// DistanceToNearestPort (:849-856)
RplComponent rpl = RplComponent.Cast(Replication.FindItem(id));
if(!rpl) continue;
IEntity entity = rpl.GetEntity();
if(!entity) continue;
float distance = vector.Distance(pos, entity.GetOrigin());
```

**Do not** change the return contracts: `GetTownStock` skipping an unresolvable shop, and `DistanceToNearestPort` keeping its documented `-1` for "no ports resolved", are both the right answers for a client with partial state. Callers already handle a negative distance as "unknown" (`map/location-types` finding N7).

Worth a sweep in the same pass: `CheckShopInit` (`:1813-1814`) calls `GetShopByRplId` and immediately writes `shop.m_iTownId` with no guard, and `RegisterGunDealer` (`:1257-1263`) dereferences `FindEntityByID` without one. Same file, same pattern.

## Notes

- **This is not a hypothesis about the future.** `map/location-types` shipped a duplicated null-safe town-stock loop inside `OVT_MapShopPriceIndicator` *because of* this bug, and its acceptance criteria include a grep proving it never calls `GetTownStock` (Q-4). Fixing this makes that duplication removable.
- All three are on paths that run per item per panel refresh, so the guards must stay branch-cheap — no logging inside the loops.
- No test tier can see this: the autotest world resolves every id, which is precisely the condition under which the bug is invisible.
