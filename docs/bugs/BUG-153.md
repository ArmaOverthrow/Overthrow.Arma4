## Symptom

Four GUIDs each appear on **two** `CustomStringTableItem` blocks in the master string table:

    {5D5C558A6E391A20}
    {5D86A310C893DBDE}
    {5D86A310C893DBDF}
    {A1B2C3D4E5F60003}

Verified against the committed file (`git show HEAD:Language/localization_Overthrow.st | grep -oE 'CustomStringTableItem "\{[0-9A-F]+\}"' | sort | uniq -d`), pre-existing before `map/map-layers` touched the file.

**Where:** `Language/localization_Overthrow.st` — the editable master. ❌ **Do not touch `localization_Overthrow.<lang>.conf`** — those are Workbench-generated exports; their `Ids{}`/`Texts{}` blocks are neither parallel nor same-length, and hand-editing has corrupted all six before.

## Why nothing has broken yet, and the actual risk

There are **zero duplicate `Id`s** in the file. Lookups resolve by `Id`, so the duplicated *resource GUIDs* are unreferenced at runtime. The risk is Workbench-side: a resource-database collision on re-import or export, resolved arbitrarily, silently losing one member of each pair.

## Fix shape

Reissue four GUIDs, then verify with a **clean Workbench load and export regeneration** — a user action by nature, cheap to fold into any Workbench session. The dedup grep above is the acceptance check.

## Provenance

Found by `map/map-layers` Phase 6 (2026-08-11) — full write-up in `docs/features/map/map-layers/findings.md` (F5). Filed against `dev-ops` because the string table is project-wide, not a map artefact.
