## Symptom

BUG-134 bound the info panel's close button to `OverthrowCloseInfoPanel` on `keyboard:KC_C` **and `gamepad0:b`**, added to `MapContext` (vanilla priority **50**). Vanilla's `GadgetMapContext` sits at priority **55** and its `MapEscape` also binds `gamepad0:b` with `InputFilterDown`. Higher priority wins, so on a controller pressing **B** over the map very probably fires `MapEscape` (close the map) and **never reaches `OverthrowCloseInfoPanel`** — leaving the panel's close affordance **keyboard-only**, on a fix whose whole point was that the panel could not be dismissed.

**Where:** `Configs/System/chimeraInputCommon.conf` (Overthrow) — the `Action OverthrowCloseInfoPanel` block's `gamepad0:b` `InputSourceValue` and the `ActionContext MapContext` `ActionRefs +{ }` delta. Colliding declaration: vanilla `chimeraInputCommon.conf` — `ActionContext GadgetMapContext`, `Action MapEscape`.

## Why the repo's checker did not catch it

`check-input-conflicts.py` exits 0 on this tree: the collision is **cross-context** (two contexts, two priorities, two files) and the checker compares within a context; `MapEscape` is also one of the base game's ~197 **inline** `ActionContext` actions in its blind spot. A clean checker exit is necessary and **not sufficient** — priority ordering has to be reasoned about by hand.

## Confirm before designing a fix

On a pad: open the map, hover a marker to pin the info panel, press **B**. If the *map* closes rather than the *panel*, confirmed. The analysis is a code reading — vanilla declares `MapEscape` **twice** with different filters (`InputFilterDown` in `GadgetMapContext`; `InputFilterClick` with `Visible 0` in `CommandPostMapContext`), so the resolution is not certain from the config alone. Note the 2026-08-13 gamepad pass of the map reported all green without specifically probing this — it survived a keyboard-and-mouse play-test once already for exactly that reason.

## Provenance

Found by `map/map-layers` Phase 4b (2026-08-11) — full write-up in `docs/features/map/map-layers/findings.md` (F6).

## Audit 2026-09-03

The mechanism in the title is wrong. Vanilla `GadgetMapContext` has Flags 0x2 with no exclusive bit, so priority alone does not shadow (BUG-156 proof). Both actions fire. `MapEscape` uses `InputFilterDown` and closes the map on press. `OverthrowCloseInfoPanel` uses `InputFilterClick`, fires on release, and `SCR_InputButtonComponent.OnInput` (`:731`) returns early because the root is no longer visible. The symptom is the same: B closes the map, not the panel. Play-test owed: SP, gamepad, open the map, pin an info panel, press B.

## Closed 2026-09-03 (play-test passed)

Play-test in SP with a gamepad passed on 2026-09-03: with an info panel pinned on the map, B closed the panel as intended. The symptom does not reproduce on the current build. The record was filed from a config read and never reproduced.
