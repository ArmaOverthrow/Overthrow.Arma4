## FIXED 2026-08-18 — and the mechanism was not the one this report guessed

The re-investigation revised both halves before fixing anything:

1. **The place tip is NONMODAL** (`placeFirstPlaceable.conf`: `m_ePresentation NONMODAL`, one page), so it is presented by `OVT_TutorialInfo` (the HUD overlay) — which contains **no focus code at all**. `OVT_TutorialContext.FocusFirstButton` (this report's named culprit) never ran in the reported scenario; "until the tip times out" was the tell, since only the HUD overlay has a 20 s timeout.
2. **"The tip appears despite IsBlockingPopups" is by design, not a race.** `place-first-placeable` is one of the entries with `m_bShowOverUI 1` (the 2026-08-11 change set) — the blocking-UI veto is deliberately waived so a tip about a screen draws over that screen. Nothing to fix; the half of this report that called it undiagnosed is answered.
3. **The real d-pad-dead mechanism:** the HUD tip's two prompts are `ButtonWidgetClass` (WLib_NavigationButtonSmall) widgets on `EHudLayers.ALWAYS_TOP` — the one layer above every menu. They are focusable, and when the menu underneath has no explicitly focused widget the workspace's gamepad focus lands in that two-button island, from which d-pad navigation cannot reach the menu below. When the tip retires, the island vanishes and navigation recovers — exactly the observed "wait for the timeout".

**The fixes:**
- `OVT_TutorialInfo.CacheWidgets` now sets `WidgetFlags.NOFOCUS` on both prompt buttons. Neither is ever driven by focus — they fire from their bound inputs and the mouse — so nothing is lost and the focus island is gone.
- The capture/restore this report asked for was implemented anyway, where it does belong: `OVT_TutorialContext.OnShow` captures `GetFocusedWidget()` before `FocusFirstButton()` takes it, and `OnClose` restores it (null-guarded both sides). Any modal tip shown while a menu holds focus now hands focus back on close.
- Related, found during the same investigation: merge `7fea0cfa` (2026-08-11, two days before this report) had **dropped `OverthrowTutorialMenuContext` and `OverthrowTutorialHudContext` from `Configs/System/chimeraInputCommon.conf`** while keeping all five `OverthrowTutorial*` actions — so every tutorial binding in the modal was dead at the time this was observed. Both contexts are restored.

**Play-test confirmation owed:** on gamepad, open the place menu on a fresh campaign — the place tip must draw over it AND the d-pad must keep driving the menu the whole time; and a modal tip closed over an open menu must leave that menu's focus where it was.

## Symptom (observed on gamepad, 2026-08-13)

Opening the place menu triggers the place tutorial tip; while it shows, the place menu cannot be driven with the d-pad — the player has to wait for the tip to time out before selecting anything.

## Mechanism, two halves

1. **Focus is taken and never returned.** `OVT_TutorialContext.FocusFirstButton()` calls `workspace.SetFocusedWidget` on the tip's Next/Dismiss button — deliberately, so a pad player can dismiss a tip shown over open gameplay. But it runs unconditionally, including when a menu already holds focus, and `CloseLayout` restores nothing: after the tip closes (or times out) the menu's focus is gone, not merely interrupted.
2. **The tip shows over the place menu at all, despite a mechanism meant to stop it.** `OVT_PlaceContext.IsBlockingPopups()` returns true on `m_bIsActive || m_bPlacing || m_bRemovalMode` precisely so tips don't fight placement. A tip triggered BY the menu opening evidently evaluates before `m_bIsActive` is set (or the blocking check happens only at trigger time and the open event races it) — undiagnosed; instrument the trigger path to confirm the ordering.

## Fix shape

- In `FocusFirstButton`, capture `workspace.GetFocusedWidget()` first and restore it in `CloseLayout` (null-guarded — the previous widget may be gone). That alone fixes the stranding for every tip over every menu.
- Decide the display policy for tips triggered by menu opens: either defer them until the menu closes (extend the `IsBlockingPopups` contract to cover the open race), or show them without taking focus when a menu context is active (focus theft is only needed over open gameplay, where nothing else holds focus).
- Regression check: a tip over plain gameplay must still take focus, or a pad player cannot dismiss it at all — that is why the steal exists.
