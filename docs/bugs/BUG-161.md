## Symptom

**As a remote client on a dedicated server:** clicking Buy in a shop delivers the item(s) into your
inventory, but your balance does not change and the shop's stock corner does not decrement. Repeatable
indefinitely — the shop is an infinite free vending machine, bounded only by the client-side
`PlayerHasMoney` check, which passes forever precisely because nothing is ever taken.

**As a listen-server host (or in single-player):** the Buy button does nothing at all — no item, no
debit, no stock change.

Vehicle buying at a vehicle shop is **not** affected; it charges and decrements correctly.

## Mechanism

`OVT_PlayerCommsComponent.RpcAsk_Buy` is an `RplRcver.Server` handler, i.e. it executes **on the
authority**. Inside it (pre-fix, at `:422-423`):

```c
Rpc(RpcAsk_TakePlayerMoney, playerId, actualCost);
Rpc(RpcAsk_TakeFromInventory, shopId, id, successfulPurchases);
```

Both targets are themselves `RplRcver.Server` handlers. **An `RplRcver.Server` RPC marshalled by the
authority is delivered to nobody** — the engine does not loop a request back to the sender (the
BUG-045 / BUG-052 / BUG-088 family; the project's standard `if (Replication.IsServer()) { direct call }
else { Rpc(...) }` idiom exists for exactly this reason). So neither the debit nor the stock decrement
has ever happened, for any caller, while the item spawn/insert loop immediately above them ran
normally.

`RpcAsk_BuyVehicle` at the same time called **the identical two handlers directly**, not through
`Rpc()`. Somebody fixed the vehicle path and left the item path behind.

The listen-host half is one level up and is the same defect: `OVT_ShopContext.Buy()` reached the
monolith through `OVT_Global.GetServer()`, which on a server returns the **game-mode's** copy of the
component, and then called `Rpc(RpcAsk_Buy, ...)` unconditionally — again an `RplRcver.Server` request
sent by the authority, so `RpcAsk_Buy` never ran at all for a host. (Same class as the lock/unlock
finding recorded as P2-5 in `docs/features/core/controller-migration/context.md`.)

Two places in the tree had already reached this conclusion for the *stock* half without connecting it
to the money: `OVT_ShopTransactionComponent.RestockShop` and `OVT_VehicleRequestComponent.TakeFromShopStock`
both open-coded the `m_aInventory` mutation with a comment saying `OVT_ShopComponent.AddToInventory` /
`TakeFromInventory` "is not a server-side call path".

## Scope of the exploit

- **Reachable by any unmodified client**, with no tooling: it is what the Buy button does.
- Bounded only by the client's `PlayerHasMoney(cost)` check, so a player with any positive balance can
  buy an unlimited amount of everything the shop stocks (stock never decrements either, so the "sold
  out" gate never trips).
- Combined with selling — which **does** credit money correctly (`OVT_ShopTransactionComponent`) — this
  is an unbounded money printer: buy for free, sell for cash.

## Fix (landed 2026-08-14, Phase 4 of `core/controller-migration`)

`RpcAsk_Buy` is deleted. Its replacement is
`OVT_ShopTransactionComponent.RpcAsk_BuyItems(RplId shopId, int id, int num)`, on the per-player
`OVT_OverthrowController`, which:

- takes the money with a **direct** `economy.DoTakePlayerMoney(playerId, actualCost)`;
- decrements the stock with a **direct** `shop.TakeFromInventory(id, successfulPurchases)` —
  `OVT_ShopComponent.AddToInventory` / `TakeFromInventory` are plain server-side mutations plus
  `StreamInventory()` as of the same change, instead of forwarding to a client→server ask;
- branches its public entry point on `Replication.IsServer()`, so a listen host executes the handler
  in-process instead of sending a request to itself.

It also gains two bounds the original never had: `num` is clamped to 1..100 (every unit is spawned
unconditionally, so an unbounded `num` was an unbounded server-side spawn loop — the same reasoning as
BUG-033 on the import path) and `id` must pass `IsValidResourceId`.

## Verification owed

Code-derived verdict; **not yet confirmed at runtime**. The controller migration's single MP play-test
(implementation.md §6, step 2) is the confirming step: buy 1 item and check the balance changes by
exactly the shown price and the stock corner decrements; buy 5 with room for 3 and check the partial
notification plus a 3-unit charge. Until that runs, close nothing.

## Player-facing consequence

This is a **visible economy change**: items that were free now cost money, and shops can now sell out.
Per implementation.md §9, that makes a docs/wiki pass required at P10 rather than optional.

## Closed 2026-08-14 — also fixed on `main`

The `v1.5` fix above is unchanged. On `main` (where the monolith still exists) the same defect was
closed in place alongside BUG-164: `RpcAsk_Buy` now calls `RpcAsk_TakePlayerMoney` and
`RpcAsk_TakeFromInventory` **directly** instead of `Rpc()`-ing them, exactly as `RpcAsk_BuyVehicle`
always did, and `Buy()` gained the `Replication.IsServer()` direct-call branch so a listen host runs
the handler in-process. Confirmed by play-test on a listen host: the balance drops by the shown
price and the stock corner decrements. Compile clean, All group 142/142.
