**Discovered during resistance/recruit-ux planning (R11 in that feature's implementation.md §10) — filed as its own bug, not fixed by that feature (scope).**

`OVT_PlayerCommsComponent.RpcAsk_DismissRecruit` (`Scripts/Game/Components/OVT_PlayerCommsComponent.c:2018-2059`) acts on the recruit id supplied in the payload with **no check that the sender owns the recruit** — no sender resolution, no `m_sOwnerPersistentId` comparison. Any connected client can dismiss any other player's recruit, permanently destroying it (grief vector).

**Shape of the fix:** the rename handler at `OVT_PlayerCommsComponent.c:1994` shows the minimal in-place validation shape. The better fix is migrating dismiss (and the other legacy recruit RPCs — `RpcAsk_RecruitCivilian`, `RpcAsk_RecruitFromTent`, `RpcAsk_RenameRecruit`) onto `OVT_RecruitCommandComponent` on `OVT_OverthrowController`, which recruit-ux created with the correct pattern: derive the actor via `ResolveOwningPlayerId()`, re-validate ownership against the recruit record, never trust a player id from the payload (see `RpcAsk_SetRecruitInactive` there as the template).

Related precedent: BUG-051 (unvalidated recruit RPCs — recruit/tent paths), BUG-052 (client-local rename, fixed).
