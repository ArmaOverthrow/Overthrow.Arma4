## How this was found

Code inspection during the 2026-08-14 disguise-icon investigation (perceived-faction `FULL_OUTFIT` behaviour).

## Problem

`OVT_PlayerWantedComponent.CheckUpdate` intended to force the vanilla outfit-faction
initialization "on first run" by calling `SCR_CharacterFactionAffiliationComponent.InitPlayerOutfitFaction_S()`
whenever `GetCharacterOutfitValues()` returned 0. But an outfit with no faction-scored
clothing — the default Overthrow civilian state — keeps that count at 0 forever, so the
1 Hz server tick re-called it every second for every player, recruit and active civilian.

`InitPlayerOutfitFaction_S` is not idempotent-cheap: each call does
`Rpc(InitPlayerOutfitFaction)` (RplRcver.Broadcast), clears and re-walks the character's
inventory on the server **and every client**, and re-inserts invoker subscriptions on the
perceived-faction manager (`GetPerceivedFactionOutfitTypeChanged().Insert(...)`, which
`ScriptInvoker.Insert` dedupes, so no leak — but the walk and the wire traffic are real).

## Impact

Steady-state network and CPU waste proportional to character count — one reliable broadcast
RPC + full inventory walk per second per character wearing civilian clothes. Invisible in
single player, real on a populated dedicated server.

## Fix

`Scripts/Game/Components/Player/OVT_PlayerWantedComponent.c`: a server-side
`m_bOutfitFactionInitDone` flag makes the tick request initialization at most once. The
flag is only set once `SCR_PerceivedFactionManagerComponent.GetInstance()` is non-null —
initializing before the manager exists would leave the affiliation component permanently
unscored (vanilla `InitPlayerOutfitFaction` early-returns with a warning and there is no
vanilla retry for non-players).
