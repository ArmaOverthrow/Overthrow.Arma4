**User play-test report (2026-08-14, Phases 1–8 pass of recruit-ux):** setting a recruit inactive worked, but the parked recruit repeated spoken orders out loud and visibly glitched/twitched in place.

**Cause:** `PlaceRecruitInInactiveGroup` gave the inactive group a **defend waypoint** (garrison precedent, decision D9). The defend behaviour continuously re-manages the group — cover selection, stance changes, order barks — which on a parked roadside recruit is a perpetual audible/visible re-order loop.

**Fix (2026-08-14):** the defend waypoint is replaced with a plain **wait waypoint** (`SpawnWaitWaypoint(position, INACTIVE_HOLD_WAIT_SECONDS)`, timer 86400 s — effectively infinite for a session-scoped group that is rebuilt from records on every boot). In-repo precedent that waiting AI still returns fire: town patrols wait at points via the same waypoint type (`OVT_TownController.c:175`) and engage when attacked. Waypoint ownership/lifetime unchanged (marker component deletes it with the group). Compile clean; rides the recruit-ux working tree (uncommitted).

**Play-test to confirm:** park a recruit → no repeated barks, no twitching; shoot near it → it still returns fire (feature F2).
