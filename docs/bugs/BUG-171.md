**Found investigating a user report during recruit-ux Phase 9** ("tent recruits seem to spawn ~100 m away"). The spawn is provably correct — `RpcAsk_RecruitFromTent` refuses a `tentPos` more than 20 m from the requester and spawns at `tentPos + "2 0 2"`, and nothing afterwards teleports the body (grep over `SCR_AIGroup.c` and `scripts/Game/Groups/` for SetOrigin/Teleport variants: zero hits).

**The recruit walks.** `Idle.bt:71` → `Idle_ReturnToFormation.bt` moves an idle AI to its formation slot at RUN speed from any distance, uncapped — and that slot is anchored on the **slave group's index-0 agent**, not the player, because Overthrow never calls `SetFormationDisplacement` (`SCR_AIUtilityComponent.c:288`, `:296-320`). So a freshly hired recruit sprints toward wherever your *existing* recruits happen to be standing, which from the tent can be a long way, and reads as a spawn bug.

Vanilla knows about this: `SCR_FollowGroupCommand.c:38-42` carries a hotfix comment ("*bots will try to regroup somewhere in the middle, far away*") for its own command path — but `AddAIToSlaveGroup`, the call Overthrow uses, has no such fix.

**Falsifiable check (one minute):** it should only happen when the player already has active recruits out, and the new recruit's destination should be on/near them. With zero active recruits, the newcomer should stay at the tent.

**Fix directions to evaluate:** call `SetFormationDisplacement` so the formation anchors on the player; or issue an explicit follow/move-to-player order on hire; or re-anchor when a recruit joins the slave group. Phase 9's spawn placement hardening is unrelated and already shipped.
