## Symptom

Nothing is visibly wrong in normal play — this is an exploit, not a malfunction. A modified client
could:

- empty **another player's locked truck** into its own vehicle or into a crate, from anywhere on the
  map (`RpcAsk_TransferStorage`);
- vacuum every container within a **client-chosen radius** around a **client-chosen position** into a
  vehicle it does not own (`RpcAsk_CollectContainers`);
- loot the battlefield into somebody else's vehicle, with an unbounded search radius
  (`RpcAsk_LootBattlefield`);
- dump any container in the world into the resistance warehouse (`RpcAsk_TransferToWarehouse`);
- drive the FOB undeploy collection sweep against arbitrary entity pairs (`RpcAsk_UndeployFOB`).

The radius arguments are also a cheap **server-side denial of service**: the value goes straight into
a world sphere query on the authority, and nothing bounded it.

## Mechanism

`OVT_ContainerTransferComponent` is the **oldest** component on `OVT_OverthrowController` — it predates
the §3.4 validation ladder that `core/controller-migration` applied to the ten components it migrated in
P2–P8. All six of its `RplRcver.Server` handlers were the same shape:

```c
[RplRpc(RplChannel.Reliable, RplRcver.Server)]
protected void RpcAsk_TransferStorage(RplId fromId, RplId toId, bool deleteEmpty)
{
    if (!Replication.IsServer()) return;

    StartOperation("#OVT-Progress-TransferringItems");
    ...
    OVT_Global.GetInventory().TransferStorageByRplId(fromId, toId, config, GetCallback());
}
```

`Replication.IsServer()` and nothing else. In particular the handler never asked **who was calling**:
it did not resolve `ResolveOwningPlayerId()`, so it could not check proximity, could not check the
`OVT_PlayerOwnerComponent` lock on either end, and could not name the caller in a log line. Every
constraint that made these operations look safe lived on the **client**:

- `OVT_LoadStorageAction` / `OVT_UnloadStorageAction` pick the nearest vehicle within 15 m of the
  container and refuse when a driver is seated — client-side only, and the lock they test is the
  **container's**, never the vehicle's;
- `OVT_LootIntoVehicleAction` and `OVT_VehicleMenuContext.PutInWarehouse` gate on nothing but the
  entity the menu was opened on.

A user action's gates are not authority. This is the same finding class as BUG-087 (vehicle lock),
P5-4 (`DeleteCamp` was an arbitrary-entity delete), P7-2 (possession took any RplId) and P8-4
(`DeliverMedicalSupplies` emptied any vehicle from anywhere) — with the aggravating detail that this
component was never audited at all, because P2–P8 audited only what they *moved* and P10's sweep
checked only `Rpc()` arity and routing (which is how it found the listen-host defect P10-3 fixed in the
same folder).

## Fix (landed 2026-08-14 on `v1.5`, pre-migration component validation audit)

All six handlers now follow the §3.4 ladder, using the nearest migrated component
(`OVT_FOBRequestComponent`) as the idiom:

1. `if (!Replication.IsServer()) return;`
2. request shape — `radius` bounded (`COLLECT_MAX_RADIUS` 100 m, `LOOT_MAX_RADIUS` 50 m); the only live
   callers send 75 m and 25 m, so no legitimate request is refused
3. `ResolveCallerPlayerId()` — the caller comes from the controller entity the request arrived on,
   never from the payload
4. every `RplId` resolved with a null bail
5. `CallerMayReach()` on **both ends** of the transfer: the caller's character within
   `TRANSFER_MAX_DISTANCE` 30 m, and `PlayerMayUseVehicleFor()` — the shared "unlocked, or locked and
   yours" rule the trunk-sell, upgrade and FOB-deploy seams already apply
6. delegate to `OVT_InventoryManagerComponent` exactly as before

`OVT_ContainerTransferComponent` cannot extend `OVT_ControllerRequestComponent` (it needs
`OVT_BaseServerProgressComponent`'s progress plumbing, and EnforceScript has no multiple inheritance),
so `ResolveOwningPlayerId()` and `PlayerMayUseVehicle()` gained **static forms** on the request base and
the instance methods now delegate to them. One body each, two hierarchies — no new copies of the rules
T1.6 spent two sessions de-duplicating.

Rejections are reported on two channels (Q9): a `LogLevel.WARNING` line naming the caller, the request
and the reason, plus `SendOperationError()` **when no operation is running**. That second channel is not
for the player — `OVT_ProgressInfo` only makes its widget visible from `OnProgressStart`, and every
rejection happens before `StartOperation` — it is for `OVT_ResistanceFactionManager`, which latches
`m_pCurrentDeploymentSource`/`Target` for the duration of a FOB operation and clears the latch from
`m_OnOperationError`. Without it, a refusal on the FOB path would wedge FOB deploys for every player
until the session ended. It is skipped while an operation *is* running so a rejected request cannot
cancel the bookkeeping of a different transfer still in flight.

**No behaviour change for a legitimate request.** The two server-side callers
(`OVT_ResistanceFactionManager.DeployFOB` / `UndeployFOB`) run on the acting player's own controller
behind the FOB seam's own 15 m + `PlayerMayUseVehicle` gate on the same vehicle, and the vehicle the
manager spawns is created unlocked (`OVT_VehicleManagerComponent.SpawnVehicleMatrix` sets an owner but
never `SetLocked(true)`), so every gate added here is one the request already passed.

**One capability is deliberately removed**, and it is the exploit: a locked vehicle's cargo can no
longer be moved by a player who does not own it. `OVT_UnloadStorageAction` tested the *container's*
lock and never the vehicle's, so standing at a crate next to somebody's locked truck used to empty it.
That is the same rule `RpcAsk_SellVehicleCargo` already enforces on the same vehicles.

**The one place that rule may be felt in friendly play** is Loot Into Vehicle at *someone else's*
locked truck — a put, not a take, and arguably a gift rather than theft. It is gated anyway because the
migrated seam already applies `PlayerMayUseVehicle` to a receiving vehicle
(`RpcAsk_TakeFromWarehouseToVehicle`, P3), and one rule that all five paths share is worth more than a
per-path exception. If the play-test shows a legitimate co-op loot being refused, **relax that single
call site** (`RpcAsk_LootBattlefield` → proximity only) rather than removing the rule from the shared
helper — same disposition P7-2 recorded for `POSSESS_MAX_DISTANCE`.

## Verification owed

Code-derived; **not yet confirmed at runtime.** Play checks that confirm it:

1. **Regression, listen host and dedicated client:** Load Storage and Unload Storage between an ammo
   box and a truck parked next to it; Loot Into Vehicle at a truck's rear door; Put In Warehouse from
   the vehicle menu inside a warehouse's radius. All must behave exactly as before.
2. **Regression, the path most at risk:** deploy a mobile FOB and undeploy it again. The cargo must
   transfer and the progress bar must run to completion — a refusal here would show as a FOB that
   deploys but never transfers, followed by `FOBOperationInProgress` on every later attempt.
3. **The rejection, from a second client:** park a truck, lock it, and have the other player stand at a
   crate beside it and use Unload Storage → refused, with
   `[OVT_ContainerTransferComponent] Rejected transfer storage request from player N: one end of the
   transfer is locked to another player` in the server log and no items moved.
4. **The proximity rejection:** not reachable from the UI (the actions require you to be at the
   container); the log line is the evidence if it ever fires.

## Main-branch note

The same component with the same bare-forward handlers ships on `main`. This is exploit-class (needs
a modified client), so per the BUG-164 precedent it is the maintainer's call whether to hotfix `main`
or let 1.5 supersede it. The v1.5 fix does not port mechanically — it leans on
`OVT_ControllerRequestComponent` static helpers that do not exist on `main`.

## Closed 2026-09-03 (bug audit)

Fixed by commit 8f0594e2 (security audit of controller components). `OVT_ContainerTransferComponent.RpcAsk_TransferStorage` (`:113-135`) resolves the caller and checks reach on both ends, bounds the loot search radius (`:194`), applies the vehicle permission (`:283`), and logs a rejection (`:310`). Shipped in v1.5.0. The seam test checks only that the component exists.
