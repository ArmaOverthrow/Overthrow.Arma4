**FIXED 2026-08-16 — both halves of the fix shape applied; ⚠️ unobserved in MP (the only place it manifests).** `OVT_MapLocationBase.PopulateLocations` now treats the entity as optional — a null lookup falls back to the "Military Base" name instead of skipping the marker — and `CheckBaseAndSetFaction` assigns `baseData.entId = entity.GetID()` so client records resolve their entity (and real name) once `SetClientBaseFactions` has run. Gates: compile exit 0 / 6057 files, Fast 125 OK, All 166 OK. **Verification owed in the two-client session** (folded into map/map-layers' open I-2…I-4 rows): client sees base markers for both factions, captured base shows resistance icon/colour and real name, fast travel to a captured base works from the client.

**Player report (dedicated server; not seen in SP):** captured bases have no icon on the map and cannot be fast-travelled to.

**Root cause — the marker is skipped for EVERY base on a client, captured or not.** `OVT_MapLocationBase.PopulateLocations` resolves each base through `GetGame().GetWorld().FindEntityByID(base.entId)` and `continue`s when the entity is null (`Scripts/Game/UI/Map/LocationTypes/OVT_MapLocationBase.c:38-40`). But `entId` is `[NonSerialized()]` and has exactly **one writer in the whole tree**: `CheckBaseAdd` (`Scripts/Game/GameMode/Managers/Factions/OVT_OccupyingFactionManager.c:1027`), reached only from `InitializeBases()`, which only runs on the server — `Init()` returns early on clients (`:193-198`). The client's `m_Bases` records come from `RplLoad` (`:1557-1568`), which fills only `location`, `faction`, `id`. So on every dedicated-server client, `entId` is invalid, the lookup returns null, and **no Overthrow base marker is created at all** — no icon, no info panel, no fast-travel destination. The entity lookup exists only to read `controller.m_sName` for the marker label.

Players attribute it to *captured* bases most likely because enemy-held bases still read as "present" via other cues (restricted-area rings, garrison presence); the code path skips both factions equally.

**Why the two-client gates missed it:** `legacy-retirement` 7c and `location-types` V-rows verified selection, travel verbs, and the N1 house-privacy isolation; no row asserted "a base marker exists on the pure client's map."

**Listen host is NOT affected** for this defect (`Replication.IsServer()` is true there, so `InitializeBases` runs and `entId` is set) — the report's "possibly listen-host as well" would have to be a client *of* a listen host, which has the same hole.

**Shape of the fix (either is sufficient, both are cheap):**
1. Stop requiring the entity: in `PopulateLocations`, when `FindEntityByID` fails, still create the `OVT_MapLocationData` from `base.location`/`base.faction` with the "Military Base" fallback name instead of `continue` — the marker, icon colour, isOccupying flag and fast-travel eligibility need nothing from the entity.
2. And/or set `entId` client-side where the client already touches each base entity: `CheckBaseAndSetFaction` (`OVT_OccupyingFactionManager.c:223-248`, the `SetClientBaseFactions` sphere-query callback) has both the entity and the matched `OVT_BaseData` in hand — one line `baseData.entId = entity.GetID();` restores the name lookup too. Note the 1-second `CallLater` means a map opened in the first second still needs fix 1's fallback.

**Verify with the still-open map-layers I-2…I-4 two-client session:** client sees base markers for both factions, captured base shows the resistance icon/colour, and fast travel to a captured base works from the client.
