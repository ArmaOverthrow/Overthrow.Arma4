**FIXED 2026-08-16 — both halves of the fix shape applied; ⚠️ unobserved in MP (the only place it manifests).** `RpcDo_RegisterCamp` now carries the owner persistent-id string (resolved once, server-side) plus `isPrivate`, assigned verbatim on the client exactly as the JIP stream does — signature changed on both ends together (`vector, string, string, string, bool`; the runtime `playerId` param is gone, `player.camp` is resolved from the owner string). Defensively, the map filter and `CanFastTravel` in `OVT_MapLocationCamp` now treat an empty `owner` or an empty local id as "identity unknown — show/allow" rather than "someone else — hide/refuse"; safe because `ResolveFastTravelDestination` re-derives eligibility server-side from the server's own records and refuses with `BAD_DESTINATION`. `CanRespawn`/`IsCampEligible` deliberately untouched — that predicate runs on the server too, and loosening it would change real enforcement. Gates: compile exit 0 / 6057 files, Fast 125 OK, All 166 OK. **Verification owed in the two-client session** (folded into map/map-layers' open I-2…I-4 rows): place a camp on client A while B is connected, toggle private, confirm A keeps it and B loses it; relog A and confirm it survives via JIP.

**Player report (dedicated server; possibly clients of a listen host; not seen in SP):** camps sometimes don't appear on the map.

**The filter that hides a camp:** `OVT_MapLocationCamp.PopulateLocations` skips a camp when `camp.isPrivate && camp.owner != currentPlayerID` (`Scripts/Game/UI/Map/LocationTypes/OVT_MapLocationCamp.c:22`). That is intended for *other* players' private camps. It wrongly hides a camp whenever the client's copy of `owner` (or the local player id) is wrong — and there are two client-only ways to get there, both timing-dependent, which matches "sometimes":

1. **`RpcDo_RegisterCamp` does not transmit the owner — each client re-derives it** (`Scripts/Game/GameMode/Managers/Factions/OVT_ResistanceFactionManager.c:1315-1330`): the server sends the runtime `playerId` and the client calls `GetPersistentIDFromPlayerID(playerId)`, which returns `""` for any id not yet in the client's replicated table (`OVT_PlayerManagerComponent.c:530-537`). The table arrives via its own component's RplSave/RPC stream — cross-component ordering is not guaranteed, so a camp registered around a join/registration window lands with `owner == ""` on that client **permanently** (nothing ever repairs it; the correct owner only exists in the server record and in the JIP snapshot the client already consumed). If that camp is, or later becomes, private (`RpcDo_SetCampPrivacy`, `:1456`), the filter hides it on that client for everyone — including its owner.
2. **The local player id itself can resolve to `""`** — `GetCurrentPlayerID()` → `OVT_Global.GetLocalPersistentId()` → the same table, same race on the local player's own mapping. Then *every* private camp is hidden on that client (`"" != owner`), and `CanFastTravel` refuses them too.

Server-side (and SP/listen-host-hosting player) records are always correct, which is why the bug is client-only.

**Note also (adjacent, same RPC):** `RpcDo_RegisterCamp` does not transmit `isPrivate` either — benign today only because both sides default to public; a future default change or a server-side private-at-creation path would desync silently.

**Shape of the fix — stop re-deriving, transmit the truth:**
1. Change `RpcDo_RegisterCamp` to carry the owner **persistent id string** (resolved once, server-side, in `RegisterCamp` where `persId` is already in hand, `:1091`) plus `isPrivate`, and assign them verbatim on the client — exactly what the JIP path (`RplSave`/`RplLoad`, `:1246-1290`) already does correctly. Wire-format change: update both ends together (Rpc arity/typing is a compile-check blind spot — BUG-090).
2. Defensively, the map filter could treat `owner == ""` as "unknown, show it" rather than "not mine, hide it" — a camp wrongly shown is a far smaller failure than a camp wrongly hidden (the server still enforces travel/respawn eligibility on its own records).

**Verify** in the two-client session alongside BUG-176: place a camp on client A while B is connected, toggle it private, confirm it stays on A's map and disappears from B's; relog A and confirm it survives via JIP.
