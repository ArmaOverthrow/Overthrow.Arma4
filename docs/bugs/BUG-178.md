## Symptom (player report, listen host, 2026-08-16)

> "another thing thats been happening only to me (who is hosting the server through the game) is that when I try to place/build something, it doesnt turn off the overthrow (U) menu, not allowing me to adjust the placement or continuously place posters. works fine for everyone who joined"

The host picks Place (or Build) from the main menu, picks an item, and the **main menu is still on screen** over the placement ghost. Rotate/next-prefab/confirm behave as if the menu still owns the input. Joined clients are unaffected. It only appears once at least one other player is in the world, and gets one menu worse per additional player.

## Root cause

`OVT_UIManagerComponent` is a component on `Character_Player.et`, so **the host has one instance per player character in the world** — its own and every remote player's. It subscribes to `SCR_CharacterControllerComponent.m_OnControlledByPlayer` (`OVT_UIManagerComponent.c:35`) and acts on it unconditionally.

That invoker fires on the host with `controlled = true` for **remote** players' characters. The base game documents this exact misfire and guards against it in `SCR_GadgetManagerComponent.OnControlledByPlayer` (vanilla `scripts/Game/Components/Gadgets/SCR_GadgetManagerComponent.c:666-672`):

```c
if (System.IsConsoleApp())	// hotfix for this being called on DS when other players control their characters
    return;

if (controlled && owner != SCR_PlayerController.GetLocalControlledEntity()) // same as hotfix above but for hosted server, if we get controlled=true for entity which isnt ours, discard
    controlled = false;
```

Overthrow had no equivalent, so `AfterControlledByPlayer` ran the full local-player setup for every remote character on the host:

- `RegisterInputs()` on all ~17 contexts of that extra instance → the host's `OverthrowMainMenu` action now has **N+1** `ShowLayout` listeners, so one press of U creates N+1 pixel-identical main-menu layouts stacked on the workspace.
- Clicking `Place` runs `CloseLayout()` on **only the instance whose button was clicked** (`OVT_MainMenuContext.c:216-220`); the other roots stay in the hierarchy.
- Each surviving root's context is still `m_bIsActive`, so `OVT_UIContext.EOnFrame` (`:126-128`) keeps calling `ActivateContext("OverthrowMenuContext")` every frame. That is the input theft — the menu context fights `OverthrowPlaceContext`, which `OVT_PlaceContext.OnFrame` activates for the ghost.
- `SetEventMask(owner, EntityEvent.FRAME)` on remote characters, plus `gameMode.OnPlayerSpawnedLocal(...)` (`:185`) with the **remote** player's persistent ID — so every join also re-armed the host's client-local `PLAYER_SPAWNED` tutorial trigger.

The same code path also misfires on a **dedicated server**, where the invoker fires for every player: the DS was registering UI input listeners and ticking 17 UI contexts per player, and arming a tutorial trigger for a machine with no local player.

## Fix

`Scripts/Game/Components/Player/OVT_UIManagerComponent.c` — adopt vanilla's discard at the top of `AfterControlledByPlayer`:

```c
if (controlled && owner != SCR_PlayerController.GetLocalControlledEntity())
    controlled = false;
```

Only the `controlled = true` branch is discarded, exactly as vanilla does — unpossess must still tear down our *own* character's contexts, and by that point `GetLocalControlledEntity()` is no longer that entity. The check sits in the `CallLater(0)`-deferred `AfterControlledByPlayer` rather than in the invoker handler, so possession has definitely settled before it is asked.

No separate `System.IsConsoleApp()` guard is needed: a dedicated server has no local player controller, so `GetLocalControlledEntity()` returns null there and every remote possession is discarded by the same line.

`tools/compile-check.sh`: OK.

## Acceptance check (manual — no automated gate can see this)

Two machines. Host a listen server, have a second player join, then on the **host**:
1. Press U — exactly one main menu appears (before the fix: two).
2. Place → pick a poster → the main menu is gone, the ghost is up, rotate keys respond, and confirming places posters continuously.
3. Repeat via Build.
4. Confirm the joining player is unaffected, and that the host does not get the welcome tutorial re-armed each time someone joins.
