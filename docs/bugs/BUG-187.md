> ID note: filed as **BUG-183 on main** (2026-08-20); renumbered to BUG-187 when merged into v1.5, which had already claimed BUG-183…186 during earlier merge renumberings.

Reported from a Workbench SP session 2026-08-20 as two symptoms that looked unrelated: _"I see `[Overthrow] Reserved 1 offline player body/bodies` every now and then, but I'm in single player"_ and _"when loading this save I spawned in my home, not where I saved"_.

## Symptom

After continuing a save, the player is prepared as a **brand-new player** — new home assigned, starting car and cash granted, fresh civilian body at the new home — while their real progress (money, XP, home, stored body with gear, owned vehicle) sits unreachable in the save. The reservation sweep then hides their real stored body forever as an "offline player's" body, logging `Reserved 1 offline player body/bodies` in a single-player session where nobody can be offline.

## Root cause

The engine's backend can transiently answer the per-player identity lookup with the **NULL UUID** instead of an empty string. In the affected session the engine's own player update already carried it:

```
### Updating player: PlayerId=1, Name=Aaron Static, IdentityId=00000000-0000-0000-0000-000000000000
```

The zero form is **non-empty**, so it defeated two guards that only test for the empty string:

- vanilla `SCR_PlayerIdentityUtils.GetPlayerIdentityId()` fires its name-hash fallback only on `uid.IsEmpty()` (`ArmaReforger/scripts/Game/Utilities/SCR_PlayerIdentityUtils.c:21`) — the zero id sails past it;
- `OVT_Global.GetPlayerUID()` returned any non-empty identity verbatim, and `OVT_PlayerManagerComponent.SetupPlayer()` validated only `persistentId.IsEmpty()`.

So the whole campaign was keyed to `00000000-…`: the `OVT_PersistedPlayer` record, house ownership, the vehicle registry row (`owner: 00000000-…` in the load log), and the stored-body id. Decoding the savepoint proved it — the player's real identity (`d13d3018-…`) appears **nowhere** in the blob; the zero UUID appears 6 times. On the next session the backend answered correctly, the real identity had no record, and `FinalizePlayerPreparation` took the new-player branch. The zero-keyed "player" can never be online (`OVT_PlayerData.IsOffline()` is `id <= 0` and no runtime player ever maps to the zero id), so `ReserveOfflinePlayerBodies()` reserved its self-spawned body — correct behaviour applied to orphaned data.

This is the documented UUID trap (`""` vs `"0000…"` — always `IsNull()`, never `==`) biting at the identity seam.

## Fix

Three layers, 2026-08-20:

1. **`OVT_Global.GetPlayerUID()` treats a NULL-UUID identity as "no identity" and recovers one** (`RecoverNullIdentity()`): on a non-dedicated session the host's own player gets the local authenticator identity (`BackendAuthenticatorApi.GetIdentityId()` — the same profile identity a healthy session returns, so campaign keys match across sessions); failing that, the name-hash UUID vanilla derives for an _empty_ identity is reproduced verbatim (that fallback is unreachable when the backend answers the zero id rather than an empty string). A dedicated server never synthesises — it returns empty ("not ready"), which every caller already handles.
2. **Tripwire:** `SetupPlayer()` refuses a NULL-UUID persistent id outright, so no future caller can re-open the corruption class.
3. **Adoption:** a save already written under the flake is recovered on load — `TryAdoptNullIdentityRecords()` re-keys the zero-keyed data (player record, real-estate ownership incl. warehouses, vehicle registry, recruits, loadouts, camps/FOBs via per-manager `RekeyPlayerPersistentId()`) to the local host player's real identity, only on a non-dedicated session, only for the host's own player, and only when that identity has no record of its own yet.

`ApplyPersistedPlayers()` keeps a zero-keyed record (dropping it would delete the progress from the next save) and logs a WARNING naming it, so a dedicated server that somehow loads one says so once per load.

## Test

`OVT_TEST_Init_Persistence_NullIdentityRekey` (Init tier): SetupPlayer refuses the zero id; rekey moves player/real-estate/vehicle/recruit/camp data cleanly and never clobbers an existing record. **Proven able to fail** with the tripwire disabled (red on "created a player record keyed to the zero id"). Init 26/26, All group 182/182, compile clean (6064 files).

Not automatable, verified by play-test instead: `GetPlayerUID()`'s recovery chain (needs the live backend to answer the zero id) and the adoption guard chain (needs a real connected local player). Recovery for a save that was ALSO continued under a healthy session before this fix (so both a zero record and a real-id record exist) is deliberately out of scope — adoption skips it because silently merging two records is a decision only the player can make.

## Residual finding (separate, unfixed)

Something re-sets the VISIBLE flag on a reserved (hidden) character during a session — the sweep re-reserved the same orphan body 7 times in ~50 minutes, twice 8 s apart; two of the seven correlate tightly with opening the GM editor. `OVT_PersistenceReservation.IsReserved()` reads VISIBLE off the entity, so whatever re-sets it makes a reserved body flicker back into view on the authority until the next sweep. Harmless in this instance, but on a server with a GM-using admin it would apply to genuinely offline players' bodies. Un-pinned; probe recorded in the session notes.
