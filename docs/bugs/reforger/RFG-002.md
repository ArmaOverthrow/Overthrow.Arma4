## Summary

`SCR_PlayerControllerGroupComponent.RequestJoinGroup()` (`scripts/Game/Groups/SCR_PlayerControllerGroupComponent.c:830-833`) is nothing but `Rpc(RPC_AskJoinGroup, groupID)` — an `RplRcver.Server` RPC. That only travels when the caller is a **proxy**. Vanilla calls this method from server-side code in at least two places, where the RPC is marshalled by the authority and goes nowhere, so the join simply never happens.

## Steps to reproduce (dedicated server — verified live on the private-group path)

1. Run a dedicated server. Player A creates a **private** group and is its leader.
2. Player B requests to join it (Request Join in the group menu).
3. Player A approves the request.

## Observed

Nothing happens: player B stays in their old group. Worse, player B **is** sent the `GROUPS_REQUEST_ACCEPTED` notification (`:564`), so both players believe the join succeeded.

## Expected

Approving the request moves player B into the group (or reports a failure).

## Analysis (script citations, 1.7.0.54)

`RPC_ConfirmJoinPrivateGroup` (`scripts/Game/Groups/SCR_PlayerControllerGroupComponent.c:544-565`) executes on the server (`RplRcver.Server`) and at `:560` calls:

```c
playerComponent.RequestJoinGroup(group.GetGroupID());
```

`RequestJoinGroup` (`:830-833`) is:

```c
void RequestJoinGroup(int groupID)
{
    Rpc(RPC_AskJoinGroup, groupID);   // RplRcver.Server RPC sent BY the server → dropped
}
```

The engine does not loop an RPC back to the machine that sends it, so on the authority this call is discarded and `RPC_AskJoinGroup` (`:873`) never runs. `:564` then sends `ENotification.GROUPS_REQUEST_ACCEPTED` regardless.

Second server-side caller, by inspection: `SCR_GroupsManagerComponent.RejoinPlayer` (`scripts/Game/Groups/SCR_GroupsManagerComponent.c:1143-1174`) calls `playerGroupCompoment.RequestJoinGroup(...)` twice on its reconnect-rejoin path, which should be dead on a dedicated server for the same reason.

Related, same code path: `RPC_ConfirmJoinPrivateGroup` never re-checks `IsFull()` before approving, so an approval into a group that filled up after the request feeds straight into the `MovePlayerToGroup` defect reported separately (RFG-001) and strands the requester groupless. Also minor: `SCR_GroupTileButton.SetupJoinGroupButton` (`:703-765`) only re-evaluates join-button visibility on `RefreshPlayers`, so a stale enabled Join button can be pressed for a group that has since filled — combined with the above, silently.

## Suggested fix

Make `RequestJoinGroup` authority-aware:

```c
void RequestJoinGroup(int groupID)
{
    if (Replication.IsServer())
        RPC_AskJoinGroup(groupID);
    else
        Rpc(RPC_AskJoinGroup, groupID);
}
```

And have `RPC_ConfirmJoinPrivateGroup` verify `IsFull()` (and group existence) before approving/notifying.

## Workaround used in Overthrow

`Scripts/Game/Player/Modded/SCR_PlayerControllerGroupComponent.c` overrides the non-RPC wrapper with exactly the branch above, fixing every server-side caller at once while staying byte-identical for clients.
