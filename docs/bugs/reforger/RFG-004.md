## Summary

The persistence system's config rules (`PersistenceConfigRule`) look like a scriptable extension point: the class is visible to script and a subclass with an overridden `IsMatch` compiles and binds in an `EntityPersistenceConfig` `.conf` without any error. But the engine **never calls a script-defined rule** — only the native generated rule classes (e.g. `PrefabPersistenceConfigRule`) are evaluated. A scripted rule silently never matches, so the config it guards is silently never selected.

## Steps to reproduce

1. Subclass `PersistenceConfigRule` in script, override `IsMatch`, add a `Print` in it.
2. Bind the rule in an `EntityPersistenceConfig` in a persistence configuration `.conf` (any priority).
3. Load a world where entities should match; also force re-matching via `ReloadConfig()` on candidate entities.

## Observed

`IsMatch` is called **zero** times — measured across a full world load, initial tracking of ~hundreds of characters, and 300 forced `ReloadConfig()` re-matches with instrumentation. No warning or error is emitted anywhere; the config is simply never chosen.

## Expected

Either scripted rules are evaluated like native ones, or binding a scripted rule class in a persistence config is rejected loudly (config-load error / log warning) and the limitation is documented.

## Impact

Any mod feature built on a scripted match rule fails silently with "entities just don't persist" as the only symptom, which is expensive to diagnose (ours took an instrumented run to prove the rule was never reached).

## Workaround used in Overthrow

**There is no working workaround — only an avoidance.** Scripted rules were abandoned entirely and every Overthrow persistence config now matches through one of the three native conf matchers (`Configs/Systems/Persistence/Overthrow.conf` uses `ComponentClassPersistenceConfigRule` five times). Where no native matcher can express the condition, the feature is redesigned around the gap: `core/damage` appended a field to an existing serializer rather than add a config, and `virtualization/core` has its manager re-create AI groups from its own registry because no matcher can name "this runtime group".

The original replacement — runtime `GetConfig()` → mutate `m_bSelfSpawn` → `SetConfig()` — **was itself abandoned on 2026-08-04 and is now banned.** `SetConfig()` marks the configuration SCRIPTED, a scripted configuration is serialized with an EMPTY store name, and the loader resolves configurations by store name: across eleven save files, 17 scripted records produced 17 empty store names and zero readable ones. It never worked and it poisons the save (`OVT_PersistenceTracking.MarkForSelfSpawn` survives only as a documented tombstone with no callers, guarded by an inverted autotest).

**Standing cost:** AI corpses still do not survive save/continue (BUG-018). Player corpses come back only as a side effect of the player config's `SelfSpawn 1`.

## Retest on 1.8.0.10 (2026-08-25) — NOT FIXED

BI reported this resolved in 1.8. It is not. Measured against build 24548213 (1.8.0.10) with a
purpose-built probe, since the defect is invisible in the extracted scripts —
`PersistenceConfigRule`'s generated surface is byte-identical to 1.7.0.54 (`GetTypePriority`,
`NativeCompare`, `IsNativeMatch` + the three `event protected` callbacks), so only a runtime
measurement can settle it.

**Probe.** A bare `OVT_TEST_ProbePersistenceConfigRule : PersistenceConfigRule` overriding both
`IsMatch` (counts calls, always returns false) and `GetTypePriority` (counts calls, returns
`GetNativeTypePriority()`), bound as the `Rule` of a `Priority 1` `EntityPersistenceConfig` in
`Configs/Systems/Persistence/Overthrow.conf`. Always-false at the lowest priority means the rule can
never win a match, so the probe cannot change behaviour under either outcome. An Init-tier autotest
then forced 50 `PersistenceSystem.ReloadConfig()` re-matches on the game-mode entity and printed the
counters.

**Result:** `forced re-matches accepted=50/50 scripted IsMatch calls=0 GetTypePriority calls=0`.

Two controls make that zero mean "never called" rather than "never asked":

1. **The rule really is instantiated from the conf.** Renaming the bound class to a nonexistent one
   produced `DEFAULT (E): Unknown class 'OVT_TEST_NoSuchRuleClassXyz' at offset 5643` — twice per run.
   The real class name produced no such error, so the engine resolved and constructed it.
2. **The matching pass really ran.** `ReloadConfig()` returned true 50/50 times on a tracked entity.

Also confirmed the client read the working tree, not a pak: the addon farm's
`Overthrow.conf` contained the probe entry and no `data.pak` exists in the repo.

**Conclusion:** on 1.8.0.10 the engine still never dispatches to a script-defined
`PersistenceConfigRule` — not `IsMatch`, and not `GetTypePriority` either. Every workaround listed
above stays necessary. Reply to ARMD-13 with this measurement.
