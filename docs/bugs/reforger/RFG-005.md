## CANCELLATION NOTE:

This is the intended behaviour of the base-game arsenal in Conflict etc modes. The real problem here is actually RFG-006 that doesnt allow modders to override it.

## Summary

On any world using the persistence system, physical items a player deposits into an arsenal box (`ArsenalBox_Base.et` descendants, including the Game-Master-spawnable `E_ArsenalBox_*` prefabs) are **written to no save record at all** and are gone on the next load. There is no error, no warning, and the box itself restores fine — just empty. Server admins who spawn arsenal boxes via Game Master and use them as squad storage lose everything deposited, every restart, reproducibly.

## Steps to reproduce (reproduced locally, two-boot dedicated server)

1. Dedicated server with persistence/saving active.
2. Spawn `E_ArsenalBox_US` (Game Master), spawn a few loose items (e.g. `PaperMap_01_folded`), put them into the box.
3. Save (or let autosave run), restart the server, load.

## Observed

The box restores and contains **0 items**. Zero errors anywhere in the log. Decoding the save blob confirms the box's record exists but not one of the deposited items' persistence ids (nor their prefab GUIDs) appears anywhere in the save — the items were written nowhere.

Live-server impact that led here: an admin restocked a GM-spawned arsenal box with ~600 items ("50 sniper mags, 100 MG mags, 50 flares, 200 FAL mags, 50 smoke grenades, 100 pistol mags, 50 grenades") across multiple sessions; all lost on every restart.

## Analysis (config citations, 1.7.0.54)

The matched persistence config for these prefabs is `Configs/Systems/Persistence/Configuration/Storage/Arsenal.conf`, whose serializer list is:

```
ComponentSerializers {
  SCR_ArsenalComponentSerializer
  FactionAffiliationComponentSerializer
}
```

— **no `BaseInventoryStorageComponentSerializer`**. For a vanilla arsenal that is presumably intentional (arsenal stock is virtual), but the box also has real physical storage players can put things in. Because inventory items are saved as nested children of their container's record (Item.conf: `StorageRoot` false, `ParentHandling ACCEPT`), an item whose container never serializes its storage exists in **no record at all**: the item's own root write is suppressed and the box writes no children. Silent, total loss by construction.

## Expected

One of:

1. `Arsenal.conf` includes the storage serializer so deposited physical items survive (arsenal stock can stay virtual);
2. arsenal boxes refuse player deposits when persistence is active; or
3. at minimum a load/save-time warning that a populated storage is being dropped, so admins can discover the trap before losing gear.

## Control experiment

The identical two-boot run with a crate matched by a config that **does** include `BaseInventoryStorageComponentSerializer` round-trips all items with identical ids, clean — confirming the serializer list is the entire difference.

## Note for the fix

A mod cannot repair this itself: an override config targeting the same prefab is never selected over vanilla's (reported separately as RFG-006), and appending the serializer at runtime via `SetConfig` corrupts existing records. Only a vanilla-side change can close the trap.
