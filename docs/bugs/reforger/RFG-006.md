## Summary

When a mod supplies an `EntityPersistenceConfig` whose rule matches a prefab that a **vanilla** persistence config also matches, the vanilla config is always selected, regardless of the mod config's `Priority` and regardless of match specificity. This makes it impossible for a mod to adjust how a vanilla-covered prefab persists (e.g. to add a missing serializer), even though the config format looks designed for exactly that.

## Steps to reproduce

1. Create a mod persistence config for `ArsenalBox_Base.et` (or a concrete descendant like `E_ArsenalBox_US.et`) with the same `PrefabPersistenceConfigRule` shape as vanilla's `Storage/Arsenal.conf` plus one extra serializer (`BaseInventoryStorageComponentSerializer`).
2. Register it in the mission's persistence settings; set `Priority` high (tested 30000) and low (tested 1); try both the base prefab and a deeper concrete-prefab match.
3. Spawn the box on a persistent server, save, decode/inspect the save.

## Observed

In every tested combination the box's record lands under the **vanilla** config (vanilla's collection, vanilla's serializer set). The mod config is never selected; `Priority` visibly does not decide the competition, and a more specific prefab match does not either. No log output indicates which config won or why.

## Expected

Either documented, deterministic override rules (mod-over-vanilla for the same prefab, or Priority-ordered competition), or a diagnostic that states which config matched an entity and why, so modders can see the competition result at all.

## Impact

Combined with RFG-004 (scripted rules never consulted) and the fact that runtime `SetConfig` re-writes make existing records unreadable, there is **no working path** for a mod to alter persistence behaviour of a vanilla-matched prefab. Concretely, this blocks any mod-side fix for the arsenal-box data loss (RFG-005).

## Upstream response (2026-08-19) and analysis

BI dev on ARMD-14:

> "While there are some edge cases that we are fixing, in general, adding new rules with higher priority should work. Perhaps you had existing save data locally while making the changes? Once registered, an instance remembers which configuration it was created with and keeps it over its lifetime. So if you want to test rule changes, you should first clear local data between runs."

What our records support and don't (analysed against BUG-116 §"Fix attempts tested and REJECTED", the persistence feature docs, and the test rig):

- **The confound was genuinely present.** All override variants ran on the local `OverthrowDS` profile via `tools/launch-server.sh`, and that profile carried an existing playthrough cycled through many prior BUG-116 restart experiments. Nothing in our notes records clearing `.save` between variants. We cannot exclude their theory from our records.
- **But the test entity was freshly spawned.** The box under test was GM/script-spawned *during* the test session, with the override config registered before world load. Under "an instance remembers the configuration it was created with", a brand-new instance should have competed rules at registration and taken the higher-priority config. Instance-lifetime stickiness only explains our result if something broader is cached in local data — e.g. the configuration registry itself is frozen into the playthrough when first created. That question was put back to BI in our reply (posted 2026-08-19).
- **Priority had no observable effect in either direction** (30000 vs 1 identical), which reads more like "the mod config was never in the competition" than "it lost" — consistent with either the stale-registry theory or one of the "edge cases" BI mentions.
- Our own docs independently concluded rules are only evaluated at tracking time (persistence tasks.md, corpse entry), so the sticky-instance semantics themselves are not in dispute.
- Untested variant: `ReloadConfig()` on the box after registering the override (documented to re-evaluate rules; our only re-match data is from the scripted-rule side, RFG-004).

## Second upstream response (2026-08-19): the selection algorithm, stated

BI dev on ARMD-14, in reply to our stale-registry question:

> "In general first priority is checked, no matter what rule type. higher number wins. some vanilal rules have higher than 30k by default. set your test to 9999999 or something to be sure nothing is higher. if two rules have the same prio then prefab wins over component that wins over entity class filter. if they are still the same type they are compared by the individual filter as a final tie breaker. if that is the same the order in which the rules are declared in the config wins."

So the documented algorithm is: **config `Priority` (higher wins) → rule type (prefab > component > entity class) → individual filter comparison → declaration order.** This matches the native API surface (`PersistenceConfigRule.GetTypePriority()` / `Compare()` in the generated scripts; config `Priority` is a conf-only field, not exposed on the script class — its unset default is invisible from script).

Checked against the 1.8.0.10 extraction, this explanation does **not** obviously account for our result:

- Highest explicit vanilla priority anywhere under `Configs/Systems/Persistence/` is **33000** (`Character/Player.conf`, `Character/Equipment.conf`, `Equipment/Radio.conf`), then 32510 (`Weapon/Tripod.conf`) — so "vanilla goes above 30k" is real, but none of those match an arsenal box.
- The config that actually beat us, **`Configuration/Storage/Arsenal.conf`, declares no `Priority` at all**, and nothing in its inclusion chain (`Group/Entities/Storages.conf` → `Common.conf`) adds one. Under "higher number wins", an explicit 30000 should beat an unset default — unless the default is very high, which we cannot see from script. The tie-breakers (both rules are `PrefabPersistenceConfigRule`; declaration order would favour vanilla, loaded first) only engage at *equal* priority, i.e. only if our explicit `Priority` never took effect — which loops back to the stale-local-data / edge-case question.
- Their advice is still cheap to follow: the retest below now uses **9999999**.

Incidental 1.8 findings recorded while checking (re-verify citations at retest):

- 1.8's `Storage/Arsenal.conf` gained `SCR_ResourceComponentSerializer` — but still **no `BaseInventoryStorageComponentSerializer`**, so RFG-005's physical-deposit loss is unchanged in 1.8.
- A second, apparently unreferenced `Configuration/Arsenal.conf` (without the resource serializer) exists alongside the bound `Configuration/Storage/Arsenal.conf`; only the latter is pulled in via `Storages.conf`.
