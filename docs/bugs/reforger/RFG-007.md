## Summary

Two measured failure modes of `PersistenceSystem.RequestSpawn`, found while building a load-time cleanup that spawned stored records batch-wise in order to delete them:

1. **Endless retry against a live instance.** A `RequestSpawn` that touches a record whose instance is already in the world (e.g. a self-spawned character) does not fail fast — the engine retries the collision several times a second, forever, never completing and never invoking the callback. One boot produced **1,194** `[PERSISTENCE] Attempted to deserialize meta data for an already existing id …` errors from this alone.
2. **Wedged saves.** Even on collections guaranteed to have no live stored instance (AIGroup/AIWaypoint), a batch of requests intermittently never invoked its completion callback and **blocked every subsequent save for the whole session** — in 2 of 4 measured boots both the autosave and the shutdown save were lost, silently from the player's perspective.

## Steps to reproduce

1. On a world with persistence active and a save containing records for entities that self-spawn on load, call `RequestSpawn` for a record whose instance is already live → observe the error repeating several times per second indefinitely (failure mode 1).
2. Batch-`RequestSpawn` a few hundred records of a collection (AIGroup/AIWaypoint) shortly after load, then trigger saves for the rest of the session → intermittently the requests never complete and every later save request produces no save point (failure mode 2; reproduced in 2 of 4 boots).

## Expected

- `RequestSpawn` on an already-instantiated record fails fast with a scripted error result (the id collision is detectable up front), instead of retrying forever.
- A spawn request that cannot complete must not block unrelated save requests; if the system serialises spawn-vs-save, a stuck request needs a timeout.

## Additional diagnostics note

The `already existing id` error line itself names the rejected item's id and prefab but **not the container/record it was being restored into**, and it is emitted as `DEFAULT (E)` with no mod context. When hundreds fire in a burst during a load (which is exactly how id collisions present — see our public data-loss investigation), the missing container id is half of the colliding pair and the half no log supplies. Adding it would make these storms diagnosable from a single log.

## Workaround used in Overthrow

The sweep was removed entirely and replaced with spawn-side untracking; legacy orphan records are left in old saves as bounded dead weight. (`Scripts/Game/GameMode/Managers/OVT_PersistenceManagerComponent.c`, NOTE at :128-138 records both measurements.)
