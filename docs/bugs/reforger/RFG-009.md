## Summary

`Rpc()` is declared with untyped defaulted parameters:

```c
proto protected void Rpc(func method, void p0 = NULL, ... void p7 = NULL);
```

(`scripts/GameLib/generated/Components/GenericComponent.c:27`; same in `GenericEntity`, `WorldSystem`, `WorldController`.)

Because every parameter is `void` with a default, calling an `[RplRpc]` method with the wrong number or wrong types of arguments **compiles without any warning**, and at runtime the RPC **silently fails to deliver** — no VME, no log line, nothing on either end. The result is a replicated feature that simply doesn't work, with no signal pointing at the call site.

## Real-world cost (measured in our mod)

A server→owner progress RPC was invoked with four arguments against a three-parameter `[RplRpc]` method. It compiled clean and the progress UI never updated for **any** player — host or remote — for as long as the component existed. Nobody connected the dead feature to the call shape; it was found only by hand-comparing arities during an unrelated fix.

## Steps to reproduce

1. Declare `[RplRpc(RplChannel.Reliable, RplRcver.Owner)] void RpcDo_Test(int a, int b, int c)`.
2. Call `Rpc(RpcDo_Test, 1, 2, 3, 4)` from the server.
3. Compiles clean; at runtime the receiver never gets the RPC and no error is emitted anywhere.

## Expected / requested

Any one of these would eliminate the class of bug:

1. **Compile-time**: validate the argument list against the `func` target's signature (the target method is statically known at the call site).
2. **Runtime**: when marshalling an RPC whose argument list does not match the target's parameters, emit a script error naming the method.
3. At minimum, document the hazard prominently in the RPC modding docs.

The same blind spot applies to `ScriptInvoker.Invoke(...)`; the typed `ScriptInvokerBase<func>` pattern shows the compiler can check these when the signature is carried in the type, which is what makes (1) look feasible for `Rpc()` too.
