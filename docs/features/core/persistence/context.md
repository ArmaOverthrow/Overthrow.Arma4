## Important Decisions

### v2-1: Conf-first architecture (2026-08-02)
Collections/bindings/states are .conf-defined (engine constraint — `PersistenceCollection` sealed). Overthrow ships `Configs/Systems/Persistence/Overthrow.conf` inheriting vanilla `Common.conf`, and registers `SCR_PersistenceSystem` through the existing GUID-override of `ChimeraSystemsConfig.conf`. Supersedes v1's "12 collections from script" (impossible) — start with **one** `Overthrow` collection; add more only on demonstrated need (e.g. spawn-request filtering).

### v2-2: Global save via SaveGameManager (2026-08-02)
`SaveGame()`/`AutoSave()` = `RequestSavePoint()`; `HasSaveGame()` = cached async `GetSaves` + save-created/deleted events; `WipeSave()` = async `Delete`/`Purge`. No `TriggerSave` exists. UI must report the real outcome (fixes the unconditional `#OVT-Saved` lie, `OVT_MainMenuContext.c:262-271`).

### v2-3: Inherit vanilla Common.conf (2026-08-02)
Gets characters/vehicles/items/doors/AI-groups/storage persistence for free (EPF's character/vehicle SaveData had vanilla equivalents all along). Risk logged: watch for fights with Overthrow systems after Phase 2; scope with rules if needed.

**RESOLVED in Phase 3 (2026-08-02).** The risk was real for exactly two categories. AI groups and AI characters are self-spawned by vanilla AND rebuilt by Overthrow's own managers, which would have doubled every garrison and patrol on a continued campaign; both are now scoped out with `SelfSpawn 0` overrides of vanilla's config GUIDs (plus the two AI waypoint configs, which would otherwise leave orphan waypoints behind). Everything else — vehicles, items, doors, structures, compositions — is kept, because no Overthrow system rebuilds it. Per-category reasoning in tasks.md; the mechanism (override a vanilla config by GUID, change one field, inherit its rule and serializers) is the same one Phase 2 used for the game-mode config.

### v2-5: Overthrow owns the lifecycle of everything it can rebuild (2026-08-02, Phase 3)
The dividing line for "should this entity persist?" is not "is it important" but **"does an Overthrow system already rebuild it from manager state?"**. If yes, persisting it duplicates it — AI groups, AI characters, deployment units. If no, persist it — placeables, buildables, base compositions, the deployment marker itself, vehicles, items, buildings. Apply this test to any new world entity before adding it to `Overthrow.conf`.

### v2-4: Dedicated purge must be neutralized (2026-08-02)
`SCR_BaseGameMode.c:723-747` wipes session storage and purges the playthrough at game-mode end on dedicated servers unless keep-session-data/`-keepSessionSave`. Without handling this, a persistent-campaign server deletes itself on restart. Phase 1 task.

### Kept from v1 (still valid)
- **Big-bang migration** on `vanilla-persistence`, breaking change, no save conversion.
- **Stored-vs-derived split** (player-manager): `[NonSerialized]` skill-effect outputs are rebuilt after load, never persisted — the test suites depend on this.
- **Persistent string player-ID keying** stays; UUIDs only where entity references demand them.

## Gotchas & Learnings

- **Binary save context**: write order == read order; `WriteDefault` still writes in binary; guard optional shape with `CanSeekMembers()`. Versioning is manual (`WriteValue("version", 1)` first).
- **UUID is a string subclass**: `""` vs `"0000…"` — always `IsNull()`, never `==`.
- **No `GetOnAfterLoad()`** — watch `GetOnStateChanged()` for `ACTIVE`.
- **`GetSaves` is always async** — hence the HasSaveGame cache design.
- **EnforceScript**: no generic methods (use `OVT_ComponentFinder<Class T>`), no ternaries, `notnull`/`out` in overrides must match base exactly.
- **Conf GUIDs are hand-generated** for new files — collisions/malformed shapes fail silently; the Init-tier "system ACTIVE" test is the tripwire.
- `.scripts/` save tools still point at EPF's `.db/Overthrow` layout — do not "fix" them until the real save location is observed (Phase 6).

## Session Notes

### 2026-08-05 — MP play-test round 1: THE RESTART IS THE BOUNDARY, and `SelfSpawn` is the only thing that crosses it

**The single fact that explains most of this session.** A save point commits the STORAGE, so a record released with `Save()` + `StopTracking(keepData)` really is written to disk — measured, by decoding the blobs. But a LOAD only instantiates records whose configuration says `SelfSpawn 1`; everything else is dropped and is absent from every later save point. Measured across a real restart boundary in the Workbench profile: 215 records in savepoint000, **12** in savepoint001. All 148 Character records were gone, including one an `OVT_PlayerData.m_sBodyPersistenceId` still pointed at. **In-session round trips prove nothing about restarts** — which is exactly why the automated spine (in-session re-apply) stayed green while the dedicated server lost bodies.

Root cause for the player body: Overthrow inherits `Common.conf`, where the player-character config `{64ECE6462993EA13}` is `SelfSpawn 0`. **Vanilla re-enables it for missions in `Mission.conf:18-24` and Overthrow never did.** Fixed by overriding that GUID with `SelfSpawn 1` in a new `Player` group in `Overthrow.conf` — the same one-bit-by-GUID idiom the AI group uses in the opposite direction.

**`MarkForSelfSpawn` is dead and is now disabled — this was BUG-018's third failed fix, and the mechanism was never going to work.** `PersistenceSystem.SetConfig()` marks the config SCRIPTED; a scripted config is serialized with an **empty store name**, and the loader resolves configs BY store name. Across eleven save files: 17 scripted records, 17 empty store names, **zero** readable. Those are the `Unable to locate configuruation ''` / `Attempted to deserialize meta data without configuration` errors in the user's startup log — three of them, three corpses. So the flip never brought a corpse back AND poisoned the save with records the engine errors on every load. Vanilla has no `GetConfig`/`SetConfig` call site anywhere. The kill hook is now empty and says so; the Init case that used to assert the flag is inverted into a guard against reinstating it (`OVT_TEST_Init_Persistence_CharacterConfigNeverSelfSpawns`). **Player corpses now come back anyway**, as a side effect of the player config's `SelfSpawn 1`. BUG-018 stays open for AI corpses only.

**Player position is now guaranteed independently of the body.** `OVT_PlayerData.m_vLastKnownPosition`/`m_vLastKnownAngles`, server-only, captured wherever the body id is captured *and deliberately even when capturing the id fails*, persisted by `OVT_PlayerManagerSerializer` **version 3**, cleared on death (death still sends you home), adopted only when the live record has none. `GetCreationPosition()` prefers it over home. So a lost character record now costs the gear it was carrying and nothing else.

**The vehicle registry was never persisted at all** — `m_mPlayerVehicleIds`/`m_mSpawnedVehicles` were memory-only, so after any restart nothing knew which vehicles belonged to whom. A locked vehicle is released 60 s after its owner logs out, so it is not a world entity at save time either: the user's car was unrecoverable by two independent mechanisms. New `OVT_VehicleManagerSerializer` (+ conf binding) persists one row per owned vehicle — id, owner, **prefab, transform, lock state** — refreshed by `SyncVehicleRecords()` from `PreShutdownPersist` and once more inside `ReleaseVehicle()` before the delete. `NOT_FOUND` now **rebuilds** from that row instead of dropping the registration; the old "never mint a car" rule is kept in spirit, because the row is Overthrow's own record that this player owned this prefab here — contents are lost, the vehicle is not.

**Save duplication: one of each pair was ours, the other is the engine's.** Only one `Save point created` per pair (that print is our operation callback, which the engine's saves never reach). Reforger 1.7 runs its own periodic autosave and its own shutdown save — `AR-Settings_Autosave_Interval` exists as a user setting with **zero** implementation in any script or config, and the mission header defaults `m_eSaveTypes` to all four types. Not "fixed" by removing ours (that would depend on a server setting we do not control); instead `OnGameEnd()` is now guarded, because it demonstrably fires **twice** — the second pass arrived after vanilla's `HandleOnGameModeEndSaveData()` had disabled saving, wasting a whole `PreShutdownPersist()` sweep and logging `Cannot save`. Also fixed in the autosave target search: `ESaveGameType` is a **bitmask** (`==` should be `&`) and the search had no playthrough filter, so it could overwrite a previous playthrough's autosave.

**Five layout files had no committed `.meta`** (`CampMenu`, `RecruitListItem`, `LoadoutListItem`, `RenameRecruitDialogContent`, `SaveLoadoutDialogContent`), so their GUIDs existed only on the author's machine — hence `Wrong GUID/name for resource … CampMenu.layout` on the server. Metas added carrying the GUIDs the prefab/config already reference (no collisions; the two stale script attribute defaults for `RecruitListItem` re-pointed to match). ⚠️ **Not verifiable locally**: this environment does not reproduce the error even with a meta deleted, because the resource database already holds the registration. Needs a Workbench open + a clean build to confirm.

Verified: compile clean (5905 files), All **56/56** green. Two new round-trip cases (player last-known position, vehicle registry) and the inverted corpse guard were each **proven able to fail** and the method recorded in their headers.

### 2026-08-03 — BUG-018 FIXED: the engine never consults scripted conf rules; corpse self-spawn now set via SetConfig

**The corpse-rule design was dead on arrival, and now that is a measurement, not a suspicion.** A new Init-tier case (`OVT_TEST_Init_Persistence_DeadCharacterConfigSelfSpawns`) spawns a recruit character, kills it and watches its matched config. Authored red against the live defect, its instrumented runs split the suspects cleanly: the controller DID report the character dead (timing suspect eliminated), `ReloadConfig()` returned true 301/301 times (tracking/hook suspects eliminated), and `OVT_DeadCharacterPersistenceConfigRule.IsMatch` was called **ZERO times** — across world load, the initial matching of every tracked character, and 300 forced re-matches. Every rule vanilla binds in any .conf is a native generated class; the scripted `IsMatch` event is dead code on the conf path. The 2026-08-02 note below ("The ethos, stated and then finished") stands corrected on this point.

**The replacement uses the API pair vanilla exposes for exactly this:** `OVT_PersistenceTracking.MarkForSelfSpawn(entity)` — `GetConfig()` → flip `m_bSelfSpawn` → `SetConfig()` — called from the game mode's existing character-killed hook. The matched config's collection/serializers/self-delete are kept; only the one bit changes; it lands on the death frame (0 polls). Deleted: the rule class, its `Overthrow.conf` block (Priority 36000), and the one-frame re-ask. **New invariant, load-bearing:** `ReloadConfig()` RESETS a scripted config, so nothing may re-match a marked corpse — both doc comments say so.

**The same case also pins the opposite catastrophe:** it fails if a LIVE character's config self-spawns (Phase 3's no-double-AI invariant). All group now 44/44. The true quit-and-continue half of 12c stays a manual play-test item, as ever.

### 2026-08-03 — Findings #4 and #5: ammo-box VME (vanilla 1.7 landmine, modded guard) + chooser stays open on Continue

4. **VME during `DistributeInitialResources` on a new campaign** (`NULL pointer ... SCR_InventoryStorageManagerComponent.OnItemAdded` via `OVT_BaseUpgradeComposition.FillAmmoboxes`). NOT a migration bug — a vanilla 1.7 landmine: `OnItemAdded` ends with `m_Storage.GetWeaponStorage()` (1.7.0.54, `SCR_InventoryStorageManagerComponent.c:539`) and `m_Storage` is only assigned for owners carrying a `CharacterInventoryStorageComponent` (`:2141`), so ANY item inserted through a non-character manager is a guaranteed VME. Overthrow does exactly that when stocking base-composition ammo boxes through the box's own manager. Fix: `modded class SCR_InventoryStorageManagerComponent` (`Scripts/Game/Modded/SCR_InventoryStorageManagerComponent.c`, precedent: 5 existing modded classes) — characters route through `super` untouched; a manager with null `m_Storage` runs vanilla's body minus the broken line (bandage census kept; the weapon-storage comparison can never match without a weapon storage). Guard protects every insertion path into boxes, not just FillAmmoboxes. Side effect on the user's current campaign: the VME aborted the initial build-out mid-way; later resource ticks resume it, no restart needed.
   **"Are we filling boxes wrong?" (user question, answered by inspection):** the API is vanilla's own idiom (`SCR_PlayerArsenalLoadout` fills storages with `TrySpawnPrefabToStorage` the same way), and a box MUST have a manager to be filled programmatically. The wrongness is which manager CLASS sits on box prefabs: `SCR_InventoryStorageManagerComponent` is written as the CHARACTER manager, but vanilla itself ships it on crates (`CO_DropOffCrate_Weapons_US.et`) and Overthrow's `OVT_AmmoBox_Base.et` carries it too. Vanilla never trips the bug because nothing vanilla inserts through a box's own manager. No class swap attempted: vanilla has no neutral container manager (only Vehicle/Arsenal variants with their own semantics), the crash box lives inside a vanilla composition we don't own, and changing the manager on a storage players actively use risks UI regressions. 💳 Possible future ticket: audit `OVT_AmmoBox_Base`'s manager class choice.
5. **Chooser stayed open after "Continue Save"** — the v1 behavior kept the layout up so a failed load wouldn't strand the player. Now: `CloseLayout()` immediately, then `LoadLatestSave()`, with a call-queue watch (`CheckContinueOutcome`, 1s poll) that re-shows the chooser only if the load fails (`IsLoadInProgress()` false + diagnostic). The re-shown chooser is mouse-driven, so it stays clickable even though the handler stopped driving frame updates when the menu closed.

### 2026-08-03 — Finding #3: Restart was hijacked by the auto-continue → replaced with a "Continue Save" menu button

User: Reforger's pause-menu "Restart" just reloaded the save. Root cause: `RequestScenarioRestart()` boots the scenario FRESH, and a fresh boot is stateless — script cannot distinguish Restart from Play (verified in retail: `SCR_ScenarioRestartComponent` → `GameStateTransitions.RequestScenarioRestart()`, no restart signal anywhere; vanilla's own model is that a fresh boot never auto-loads and "Continue" is an explicit player action). So the earlier fix's silent auto-continue was the wrong UX — it made starting over impossible.

**Final design (SP/listen host), refined per user UX feedback ("isolate continue/new-game on its own screen"):** on a fresh boot with a save present, a dedicated **chooser screen** shows instead of the campaign-setup menu — logo + "Continue Save" / "Start Game" buttons (`UI/Layouts/Menu/ContinueGameMenu.layout`, GUID `{6B0F11B0AA01C001}`, new `.meta`; hand-authored, mirrors StartGameMenu's skeleton). Picking Start Game swaps to the full campaign-setup menu in the same frame (`m_bNewGameChosen` keeps the chooser from returning); picking Continue calls `LoadLatestSave()` and deliberately does NOT close the layout (success replaces the world; failure leaves the player on the chooser, diagnostic in console). Implemented as **two layouts, one context**: `OVT_StartGameContext.ShowLayout()` is overridden to swap `m_Layout` (start-menu layout captured into `m_StartMenuLayout` on first call) before `super.ShowLayout()` — no prefab edit needed because `m_ChooserLayout` is an `[Attribute]` whose defvalue points at the new layout, and the prefab only overrides `m_Layout`/`m_sContextName`. Both buttons ride the 1.6-era infrastructure that survived the EPF removal intact: actions `OverthrowContinueSave` (keyboard C / gamepad X) and `OverthrowStartGame`, both already in the `OverthrowStartContext` input context; label keys `OVT-ContinueSave`/`OVT-StartGame`. The handler's seed-wait is kept (the chooser-vs-menu decision must not be made on a stale HasSaveGame false) and bounded at 600 frames; the handler's earlier auto-`LoadLatestSave` and failure-watch are removed. An intermediate iteration (Continue button inline in the start menu) was built and then replaced by this; StartGameMenu.layout is back to stock. **Dedicated keeps the automatic continue** — no UI there, and a server campaign persisting across restarts is the design (finding #2's `DecideDedicatedStart` unchanged). Verified: compile clean, All 42/42.

Resulting UX matrix: new world → campaign-setup menu · fresh boot + save → chooser (Continue Save / Start New Game) · scenario-menu "Continue" (launched from savepoint) → straight into campaign, no menu · Restart → chooser, Start New Game = start over (old saves remain until newer savepoints supersede them) · dedicated → auto-continue.

### 2026-08-03 — Play-test findings #1 and #2 fixed: pre-start spawn stole the home; the continue path had no caller

User's first two live findings, both root-caused and fixed, compile clean + All 42/42 green:

1. **"Spawned but not in a house" (new game).** The pre-start-menu placeholder spawn (`GetCreationPosition`, home unset) called `FindSafeSpawnLocation`, which **permanently wrote the fallback street position as the player's home** (`SetHomePos` in all three branches). By the time Start Game ran `FinalizePlayerPreparation`, the home was non-zero, so the starting-house assignment — and with it `SetOwner`, `SpawnStartingCar` — was skipped entirely. Fix: `FindSafeSpawnLocation(…, bool updateHome = true)`; the zero-home placeholder branch passes `false` so the home stays unset until Start Game assigns the house. The compromised-home branch still re-homes (intended).
2. **"Stuck on the start camera" after save + relaunch (F5).** On a fresh world boot with a save present, `IsPlayingLoadedSave()` is false so the game mode waits for the start menu — and `OVT_PlayerStartMenuHandlerComponent` saw `hasSave` and deliberately showed nothing. **`LoadLatestSave()` — documented as "the production continue path" — had zero callers.** Dead end, camera forever. Fix: the handler now (a) waits for the new `IsSaveCacheSeeded()` flag before deciding (the HasSaveGame cache is async; deciding on a stale false would offer a new campaign over an existing one — clients/dedicated skip the wait since their manager never seeds), then (b) save exists → `LoadLatestSave()` (world transitions into the savepoint → `RestoreStartedCampaign` path), no save → start menu as before. A failed load falls back to showing the menu (watched via `IsLoadInProgress()`/`GetLastLoadDiagnostic()`).
3. **Same gap fixed for dedicated servers** (was checklist item 20 waiting to fail): the EOnInit dedicated branch used to `DoStartNewGame()` immediately on every boot not launched from a savepoint — generating a fresh campaign OVER an existing one, which the next autosave would bury. Now `DecideDedicatedStart()` polls the seed (bounded, ~10s), continues via `LoadLatestSave()` when a save exists, else starts new; `CheckDedicatedContinue()` falls back to a new game if the load fails. `StartNewDedicatedGame()` uses the RestoreStartedCampaign two-sided pattern (flag + immediate schedule if post-process already ran) because the decision can now land after `OnWorldPostProcess`.

**Caveat for the user's re-test:** the save from the first run carries the polluted home (a street position). Item 1 must be re-tested on a NEW campaign; the old save will still spawn at the street spot after a continue — that's the old data, not a fix failure.

### 2026-08-02 — The ethos, stated and then finished: players and corpses

**User's requirement, verbatim:** *"Neither players or recruits should respawn with the gear they died in — Overthrow carries complete loss. However recruits and players should obviously survive a save/load round trip with full gear until they die. And their bodies as well, so gear can still be reclaimed."* The recruit half shipped in the previous session. Two things were still wrong, and they are the mirror image of each other.

**A player who saved and continued lost everything, without dying.** `CreateCharacter()` always spawned `m_rDefaultPrefab` at the player's home. The fix is the recruit fix with the nouns changed: `OVT_PlayerData.m_sBodyPersistenceId` (server-only, never in the JIP payload), captured by `SyncPlayerBodyIds()` from `PreShutdownPersist` and between the existing `Save()`/`Untrack` pair on disconnect, persisted by `OVT_PlayerManagerSerializer` **version 2** (appended last, version 1 blanked, adopted only when the live record has none), and restored by `RequestPersistedPlayerBody()` → `OnPlayerBodySpawned()` → `AttachRestoredPlayerBody()` with a pending set and a 15 s watchdog. The stored body brings its own transform, so "continue where you saved" came free.

**Two decisions inside that are worth remembering.** `OnCharacterCreated()` is NOT re-run on a restored body: read it, and it is entirely a DRESSING routine (civilian loadout into the loadout slots, first-spawn starting items) — running it would fight for the same slots and hand out starting items twice. The only thing it does that still applies is clearing `firstSpawn`, done directly. And the collection handle is a NEW field, not `SCR_SpawnLogic.m_CharacterCollection`: that vanilla field is the switch that reroutes player spawn through an async `RequestLoad` on the controller, and Phase 1 discovered the hard way that populating it stops `DoSpawn_S`/`SetupPlayer` from ever running.

**Death is enforced in exactly one line, and it is the design:** `OnPlayerKilled_S` clears the stored id before scheduling the rebuild. Everything else — every failure route in the async restore — also clears it and falls back to the old synchronous fresh spawn, so the worst outcome anywhere in this feature is the behaviour that shipped yesterday.

**Corpses: `SelfSpawn 0` was hiding a second, opposite bug.** Dead characters were being saved (every character is tracked) and never spawned back, because they were still matched to the AI config Phase 3 set `SelfSpawn 0` on to stop LIVE AI doubling. Nothing rebuilds corpses, so by decision v2-5 they belong in the save. `OVT_DeadCharacterPersistenceConfigRule` (the ONE script-extensible config class) matches `GetCharacterController().IsDead()` and a standalone `EntityPersistenceConfig` at `Priority 36000`, `SelfSpawn 1`, gives them the Character collection and vanilla's six character serializers.

**The config was made STANDALONE deliberately, against a vanilla precedent for the alternative.** `Configuration/Character/Player.conf:2` proves a derived conf CAN replace an inherited rule (it re-declares `Character.conf`'s rule GUID `{61BCBE987C36E159}` as a `PlayerPersistenceConfigRule`). Inheriting would have been DRYer — but if the replacement silently failed, the inherited prefab rule would match every character at Priority 36000 with `SelfSpawn 1` and **every AI in the campaign would self-spawn on load**, the exact catastrophe Phase 3 exists to prevent. A standalone config fails benignly: the rule does not match, corpses do not come back, nothing else moves. That asymmetry decided it.

**The re-match hook exposed a false comment in the codebase.** `OVT_SpawnLogic` claimed vanilla's `SCR_SpawnLogic.OnPlayerEntityChanged_S` re-matches the corpse via `ReloadConfig`. It does not, in Overthrow: that method is only reached through `SCR_RespawnSystemComponent.EmitPlayerEntityChange_S`, which nothing in Overthrow calls (`HandoverToPlayer` calls the game mode's own empty `OnPlayerEntityChanged_S`, and passes `previousEntity = null` anyway). So the game mode now subscribes its existing `m_OnCharacterKilled` invoker to a null-safe `OVT_PersistenceTracking.ReloadConfig()`, twice — immediately and one frame later — rather than betting on whether the damage manager's invoker or the character controller's life state updates first.

**Ethos guard, and the evidence for it:** a corpse restores as a corpse. Vanilla's own `SCR_SpawnLogic.c:422-424` refuses a persistence-restored character `if (character.GetCharacterController().IsDead())` — a check that would be meaningless unless the character serializers restore the dead state. The same test is used in three places on our side (the rule, the pre-handover guard, and the pre-capture guard in `CapturePlayerBodyId`).

**One residual risk, flagged rather than papered over:** whether the garbage system re-arms on a RESTORED corpse. `GarbageSystemState` is a vanilla persisted state Overthrow inherits, and `SCR_CharacterControllerComponent.OnDeath()` is what inserts a corpse in the first place — but `OnDeath` does not fire again on restore, so cleanup depends entirely on that native state carrying its timers across the save. It is native and opaque; it gets a play-test item (12c) instead of a guess. If restored corpses turn out to be immortal, the fix is an explicit garbage insert on the restore path, not a change to the config.
