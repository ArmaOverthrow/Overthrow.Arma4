## Phase 4: States & Player Edge Cases (8/8) ✅

- [x] ✅ **Player loadouts** — DECISION: **folded into `OVT_LoadoutManagerSerializer` (version 2), not a `PersistentState`.** A conf-declared `PersistentState` is a singleton per class; loadouts are per-player and variable in number, so states would mean N script-owned instances via `StartTracking()`, each with an id something has to remember and load back by hand — i.e. exactly EPF's design (id index in the manager + one row per loadout), which is *why* contents never came back (two halves that could disagree; the "lost id" fallback `ScanAndLoadFromEPF` was a stub returning false). Contents now travel in the same record as the index, so they cannot disagree. Vanilla precedent: `SCR_TaskSystemSerializer` writes `array<ref SCR_TaskSave>`. Nested item tree written through explicit `SerializationSave`/`SerializationLoad` on `OVT_PersistedLoadoutItem` (recursive children, properties map flattened to parallel arrays) — the shape every vanilla nested save class uses (`SCR_ScenarioFrameworkLayerSave`, `SCR_TaskSave`). **Also fixed on the way: the save path was dead** (`OVT_PlayerLoadout.Save()` → EPF → null DbContext → nothing was ever cached, so nothing could be persisted), and `DeleteLoadout()` left the name in the index. `OVT_PlayerLoadout` re-parented off `EPF_PersistentScriptedState` (also removes a client-side null-deref: `RplLoad` constructs these)
- [x] ✅ **Recruit body respawn** — **REVISED after user rejection of the gear loss (2026-08-02).** Lifecycle is unchanged and still owner-presence-driven: a recruit body exists only while its OWNER is in the game, so bodies are not respawned at campaign start but when the owner returns and has a group (`OnPlayerGroupCreated` → `RespawnRecruitsDelayed` → `RespawnPlayerRecruits`, the same hook EPF used). What changed is **which** body comes back. Despawn is now **save-and-release, not delete** (`ReleaseRecruitBody()`: `Save()` → capture id → `StopTracking(entity, removeData: false)` → delete — vanilla's `SCR_SpawnLogic.OnPlayerEntityCleanup_S:214-216` idiom, the one already used for locked vehicles), and respawn asks the persistence system for that exact character by id (`RequestPersistedRecruitBody()` → `PersistenceSpawnRequest{Collection = FindCollection("Character"), Include = {uuid}}` → `OnRecruitBodySpawned()` → `AttachRecruitBody()`). **Carried equipment therefore survives**: vanilla's AI-character config already serializes a character's whole inventory, and Overthrow's `{64EACAC5BFDB31EC}` override only turns off `SelfSpawn` — which is precisely why the manager has to ask. `OVT_RecruitData.m_sBodyPersistenceId` holds the id; `OVT_RecruitManagerSerializer` **version 2** persists it (appended last on `OVT_PersistedRecruit`; version 1 payloads default it to empty). Fresh-prefab spawn (`SpawnFreshRecruitBody()`, civilian loadout) is now only the FALLBACK, for a body that cannot be found. Idempotent on both halves: existing body never duplicated, and `m_aPendingBodySpawns` stops a second request racing the first async one. `SyncRecruitPositions()` (from `PreShutdownPersist()`, every save) now refreshes the id as well as the position, which is what makes recruits who were alive at save time come back armed
- [x] ✅ **Player body survives save/continue and reconnect** — **ADDED 2026-08-02 after the recruit revision; the player half of the same fact.** `OVT_SpawnLogic.CreateCharacter()` always spawned `m_rDefaultPrefab`, so a player who saved and continued lost everything they were carrying without dying — the opposite of the design ethos (death costs everything, a save costs nothing). Same three-part shape as the recruit fix: (1) `OVT_PlayerData.m_sBodyPersistenceId` holds the id, server-only, deliberately absent from `OVT_PlayerManagerComponent`'s hand-written `RplSave`/`RplLoad`; (2) it is captured in exactly two places — `OVT_PlayerManagerComponent.SyncPlayerBodyIds()` from `PreShutdownPersist` before every save (materialising the id with `Save()` when lazy registration has not handed one out yet), and `OVT_OverthrowGameMode.OnPlayerDisconnected` **between** the existing `Save()` and `Untrack(keepData)` (the only moment it is a pure lookup); (3) `OVT_PlayerManagerSerializer` is **version 2**, `bodyPersistenceId` appended LAST on `OVT_PersistedPlayer`, version 1 payloads explicitly blanked, and `ApplyPersistedPlayers()` adopts the stored id only when the live record has none — the same rule as the recruit serializer, so re-applying a save to a running campaign cannot overwrite the body the player is standing in. Restore is `CreateCharacter()` → `RequestPersistedPlayerBody()` (`PersistenceSpawnRequest{Collection = FindCollection("Character"), Include = {uuid}}`) → `OnPlayerBodySpawned()` → `AttachRestoredPlayerBody()`, with `m_aPendingBodySpawns` + a 15 s watchdog exactly as for recruits. **Position comes back with the body**, which is what makes "continue where you saved" true. `OnCharacterCreated()` is deliberately NOT re-run on a restored body (it dresses a NEW character — civilian loadout into the same slots, plus first-spawn starting items); the only thing it does that still applies, clearing `firstSpawn`, is done directly. **Death still costs everything:** `OnPlayerKilled_S` clears the id before the deferred rebuild, so a killed player always takes the fresh-civilian route. Every failure route (NOT_FOUND, null, dead body, timeout, non-UUID, owner left) clears the id and falls back to the old synchronous spawn — a player can never be left without a character. A brand-new campaign has no stored id, so the fresh path is unchanged and synchronous
- [x] ✅ **Corpses survive save/continue (gear reclaim)** — **ADDED 2026-08-02.** Dead characters were already serialized (every character is tracked via `Character_Base.et`'s native `Persistence` component) but matched a config with `SelfSpawn 0` — Overthrow's AI override `{64EACAC5BFDB31EC}` (added in Phase 3 so managers do not double LIVE AI) and vanilla's own `Player.conf`. So a corpse was saved and nobody spawned it back, and everything a dead player or recruit was carrying was unreclaimable after a continue. Per decision v2-5 (`does an Overthrow system rebuild it?` — nothing rebuilds corpses) they should persist. Three pieces: (1) `OVT_DeadCharacterPersistenceConfigRule : PersistenceConfigRule` — the one script-extensible config class — overriding `IsMatch(const IEntity)` with vanilla's own is-dead test, `ChimeraCharacter.GetCharacterController().IsDead()`; (2) a **STANDALONE** `EntityPersistenceConfig` `{6B0E7A40A1B2C3D4}` in the `Overthrow` group of `Overthrow.conf`, `Priority 36000`, `SelfSpawn 1`, `Collection {64EACAC5B77ED31B}` ("Character"), `ParentHandling "Ignore always"`, with vanilla `Character.conf`'s six component serializers copied verbatim (controller, hit zones, equipped weapons, inventory, compartment access, faction). **Standalone rather than inheriting `Character.conf` and replacing its rule**, even though vanilla has a precedent for that replacement (`Configuration/Character/Player.conf:2` re-declares `Character.conf`'s rule GUID `{61BCBE987C36E159}` as a `PlayerPersistenceConfigRule`): if that replacement silently failed, the inherited prefab rule would match EVERY character at Priority 36000 with `SelfSpawn 1` and every AI in the campaign would self-spawn on load — the exact catastrophe Phase 3 exists to prevent. A standalone config's failure mode is benign (rule does not match → corpses simply do not come back, i.e. today's behaviour); (3) a re-match on death, because rules are only evaluated at tracking time and vanilla's `ReloadConfig`-on-possession-change path (`SCR_SpawnLogic.OnPlayerEntityChanged_S`) is **never reached in Overthrow** — it is raised by `SCR_RespawnSystemComponent.EmitPlayerEntityChange_S`, and Overthrow's `HandoverToPlayer` calls the game mode's empty `OnPlayerEntityChanged_S` directly with `previousEntity = null`. `OVT_OverthrowGameMode` therefore subscribes its existing server-side `m_OnCharacterKilled` invoker to `OVT_PersistenceTracking.ReloadConfig(victim)` (new null-safe/untracked-safe helper), twice — now and one frame later — so the result does not depend on whether the damage manager's state-changed invoker or the character controller's life state updates first. **Corpses restore as corpses, not zombies:** vanilla's own `SCR_SpawnLogic.c:422-424` refuses a persistence-restored character `if (character.GetCharacterController().IsDead())`, which only makes sense because the character serializers restore the dead state
- [x] ✅ **Reconnect flow** — VERDICT: **inert, no action.** `SCR_PlayerReconnectDataSerializer.Deserialize` only re-arms anything if the state's character set is non-empty, and its `RemoveUnusedCharacters()` resolves saved character UUIDs with `FindById` — player characters are `SelfSpawn 0` (vanilla `Configuration/Character/Player.conf:5`, Priority 33000), so after a load nothing resolves and the sweep deletes nothing. The `SCR_ReconnectData` half returns immediately: `SCR_ReconnectComponent.GetInstance()` reads a static set only by that component's `EOnInit`, and **Overthrow's game mode prefab does not have the component** (grep: zero occurrences in the repo). Overthrow's own reconnection is persistent-ID-based in `OVT_PlayerManagerComponent` and never consults either. Not scoped out with a conf override because disabling a vanilla state carries more risk than the null case it guards; Phase 7 gets a "stay in-game >60 s after continuing" check instead
- [x] ✅ **Character controller state** — VERDICT: **vanilla already covers it, nothing to write.** Vanilla binds `CharacterControllerComponentSerializer` in `Configuration/Character/Character.conf:11`, which BOTH the player config `{64ECE6462993EA13}` and the AI config `{64EACAC5BFDB31EC}` inherit. `OVT_CharacterControllerComponentSaveData` never added a field: it overrode EPF's `ReadFrom` to store *only* stance and to deliberately drop the in-hands item ("until the EPF bug is fixed") — it SUBTRACTED from its base. Delete it in Phase 5
- [x] ✅ **`OVT_PlayerOwnerComponent` on vehicles** — `Overthrow.conf` now overrides vanilla's CAR config `{64C6B4937723DA61}` **and** HELICOPTER config `{64EE8D74EB8192BA}` by GUID, appending `OVT_PlayerOwnerComponentSerializer` to each `ComponentSerializers` block. Both are needed and only those two: Overthrow overrides vanilla's `Wheeled_Base.et {62F416029692CE40}` and `Helicopter_Base.et {CBD8C2393BE87581}` — the exact prefabs those two configs' rules match — and adds the component to them. Tracked vehicles (`TrackedVehicle_Base`) are untouched vanilla and carry no owner component
- [x] ✅ **Camp / FOB entity ↔ record re-linkage** — VERDICT: **the join works after a reload; no code needed, and no in-memory map exists to rebuild.** Both directions are computed fresh from persisted data every time: record→entity is a spatial query (`OVT_PlayerCommsComponent.DeleteCamp` queries 10 m around `camp.location` for `OVT_ManageCampAction`; `OVT_ManageCampAction` goes the other way with `GetNearestCampData(entity.GetOrigin())`, 15 m); entity→record is `camp.persistentId` + `OVT_PlaceableComponent.BelongsTo()` over a 75 m sphere (`CleanupCampObjects`, `OVT_ItemLimitChecker`). `persistentId` is restored by `OVT_ResistanceManagerSerializer` and `m_sAssociatedBaseId` by `OVT_PlaceableComponentSerializer`, so both halves of the key come from the same save. `RemoveCamp()`'s `camp.location == pos` compares the record's location with itself (the caller passes `camp.location`), so it does not depend on the restored entity transform at all. **Recorded caveat (pre-existing, not a regression):** placeable component fields are server-only — set on the server at placement, restored on the server by the serializer, never replicated — so the client-side `OVT_ItemLimitChecker` under-counts on a dedicated-server client both before and after a reload

- [x] ✅ **Implement `OVT_VehicleManagerComponent.RespawnPlayerVehicles()`** — was a deliberately empty stub whose doc comment claimed vanilla could not round-trip one instance in-session. **That claim was wrong** and the recruit-body fix had already disproved it: `PersistenceSystem.Save()` writes ONE instance's record immediately ("the entity can safely be deleted already after this") and `RequestSpawn()` fetches records back by id.   - **Collection VERIFIED, not assumed:** `"Vehicle"` — vanilla `Common.conf:11-14` names collection `{64C6B493421C8948}`, and `Common.conf:189-197` puts the Car `{64C6B4937723DA61}`, Tracked and Helicopter `{64EE8D74EB8192BA}` configs in it.
