# Resource Core — Requirements

**Epic:** logistics
**Created:** 2026-08-11

## Overview

`resource-core` is the data spine of the logistics epic: the config that defines what resources exist, the manager that serves those definitions, and the reusable ledger type that every resource holder in the game uses to track stock. It ships no player-facing gameplay on its own — its job is to settle the save format, the replication contract and the volume/weight maths *before* four sibling features start writing against them.

## Requirements

- A new resource config (e.g. `Configs/Resistance/resources.conf` + an `OVT_ResourcesConfig` / `OVT_Resource` class pair, following the `OVT_BuildablesConfig` shape) defines all resources. Adding, removing or re-pricing a resource must require **no** script change.
- Each resource definition carries at minimum: stable id/name, localized title, localized description, icon, **volume per unit in m³**, **weight per unit in kg**, `importable` flag, `illegal` flag and a base price.
- The MVP config ships four resources: **Timber, Cement, Steel, Hardware/Tools** — all legal and importable, priced so that a mid-game building costs a meaningful but achievable truckload.
- An `OVT_ResourceManagerComponent` singleton on the game mode owns the definitions and exposes lookup by id and by index, plus the aggregate maths (total m³ and total kg for a given set of resources). It is reachable through `OVT_Global` in the established manager pattern.
- A **reusable resource ledger type** (resource id → quantity) is the one representation of "some resources", used identically by truck cargo stores, crate piles and warehouses. It exposes at least: query a quantity, add, remove, enumerate non-zero entries, total volume, total weight, and a "would this fit in N m³" check.
- **Capacity belongs to the holder, not the ledger.** The ledger itself is uncapped; a truck component applies its own m³ limit. This is what lets crate piles be unlimited without a special case.
- The ledger must be replicable to clients and persistable through the vanilla persistence system, and must survive a save→load round trip with exact quantities. Choose the serialization shape here — sparse (only non-zero entries) is strongly preferred so adding a resource to config does not invalidate existing saves.
- Adding a new resource to config must not corrupt or shift existing saved stock (i.e. saves key on a stable id, not an array index).
- **Current price is per-resource state owned here, not a constant.** The config's price is the *base*; the live price drifts over time (`logistics/resource-trade` owns the drift behaviour). This feature owns where that value lives, how it replicates and how it persists:
  - Each resource carries a current price initialised to its base price on a new campaign.
  - Current prices **persist** — a drifted market that resets to base on load makes the whole mechanic pointless. Note there is no precedent to copy: Overthrow prices today are set once from config at init via `OVT_EconomyManagerComponent.SetPrice()` and are never saved.
  - Current prices replicate to clients (the port UI reads them) and are **server-authoritative** — the server drifts, clients display.
  - Keyed on stable resource id, and a resource added to config later starts at its base price rather than corrupting the saved set.
- All mutation is server-authoritative. Any client→server request path introduced here goes on a component of `OVT_OverthrowController`, never `OVT_PlayerCommsComponent`.
- Localization strings go in `Language/localization_Overthrow.st` only; runtime `.conf` exports are regenerated by the user in Workbench.
- Automated coverage: extend the **Logic** tier with world-free assertions for the ledger maths (volume/weight aggregation, fit checks, add/remove edge cases including removing more than held) and the **Init** tier with the manager resolving and the config populating. Each new case must be proven able to fail before it ships.

## Dependencies

- `core/persistence` — the `ScriptedComponentSerializer` pattern (version-first, positional binary context) and the `Configs/Systems/Persistence/Overthrow.conf` rule that binds a serializer to its component.
- `core/game-mode` — manager registration on `OVT_OverthrowGameMode` and `OVT_Global` accessor conventions.
- No sibling dependencies — this is the first feature in the epic and blocks all four others.

## Out of Scope

- Any holder of resources: truck cargo stores, crate piles and warehouse resource inventories are `resource-transport` and `resource-storage`.
- Any UI beyond what is needed to prove the data exists — no HUD, no menus, no user actions.
- **The price drift behaviour itself** — the tick, the random walk, the war-pressure bias and the difficulty multipliers all live in `logistics/resource-trade`. This feature owns only the storage, replication and persistence of the current-price value.
- Buying, selling, consuming or producing resources.
- Weight influencing vehicle handling — the field is defined and aggregated here, and deliberately goes unused epic-wide.
- Using vanilla `SCR_ResourceComponent` / `SCR_ResourceContainer` / `EResourceType` in the data path. `EResourceType` is a hard engine enum (`SUPPLIES`, `ELECTRICITY`) that a mod cannot extend.
