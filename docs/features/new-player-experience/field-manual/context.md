## The contract this feature owes downstream

**An entry's `m_sTitle` localization key IS its deep-link id.** `OVT_TutorialEntryConfig.m_sFieldManualTitleKey` holds it verbatim and `SCR_FieldManualUI.OVT_OpenEntryByTitle` matches it **exactly and case-sensitively**. The twelve frozen keys live in `implementation.md` §3.3 (I1) and `tutorial-content` copies that table verbatim. Renaming one does not error — the manual opens on its front page and logs a warning, which is the kind of failure nobody notices for three releases.

Retirement path, if ever needed: `m_bEnabled 0`. **Never recycle or rename a title key.** Body and header pieces (`_Text`, `_Text2`, `_Head`…) are *not* contracts and may be reworded, split or moved freely.

## Key Decisions

*The full set with rationale is `implementation.md` §5 (D1-D14). Recorded here are the ones a future reader will trip over.*

- **D6 — a placeholder entry still ships real content.** `SetAllEntriesAndParents` prunes an entry whose `m_aContent` is empty, then a sub-category left with nothing, then a category left with nothing. A content-free stub is not a stub, it is an *absence*: the tile never draws and the frozen link resolves to the front page.
- **D2 — two category levels only.** Root category → sub-category → entries, no deeper, and entries hung directly on the top-level category are never added to `m_aAllEntries` and are therefore unlinkable. All twelve entries live under a sub-category.
- **D5 — reuse the existing translated body keys.** `#OVT-FieldManual_MapInfo_Text`, `_FastTravel_Text` and `_Resistance_Text` each carry five translations. Moving the piece keeps them; minting a tidier id throws fifteen translations away.
- **D7 — every entry ships with the fallback tile image from creation.** The screenshot pipeline is an upgrade path, not a dependency.
- **D14 — no `&` in display strings.** Zero of the master stringtable's `Target_en_us` values contain one, so "Money & Trade" ships as "Money and Trade".

1. **The wiki's `real-estate` "Property Limits" section may describe a cap that does not exist.** It claims "soft limits on how many properties you can own" and that hitting one "prevents placing more properties". No ownership cap was found: `OVT_RealEstateManagerComponent`, `OVT_OwnerManagerComponent` and `RpcAsk_BuyBuilding` are all uncapped, and a repo-wide grep for `MaxOwned` / `maxHouses` / `propertyLimit` returns nothing. "Placing" also reads like placeables, not real estate. **Left in place** rather than deleted, because a negative cannot be proven across every server config path. Needs the user's call.
2. **The wiki's `getting-started` says there are THREE tutorial jobs; the epic says FIVE.** Left alone in Phase 2 by instruction (the section is handed off, not edited). **Phase 7C's handoff to `starter-jobs-retirement` must reconcile the count** rather than propagate either number.
   **Resolved 2026-08-08 (run 7C): the shipped number is FIVE.** All five configs exist (`Configs/Jobs/{findGunDealer,findShop,placeEquipmentBox,recruitACivilian,placeACamp}.conf`) and all five are registered in `OVT_JobManagerComponent.m_aJobConfigs` at `Prefabs/GameMode/OVT_OverthrowGameMode.et:30,34,36,38,40`. "Three" was wrong as a statement about the current game and is corrected on `getting-started`; it was however correct as history, because the three jobs added *in v1.3* were `placeEquipmentBox`, `recruitACivilian` and `placeACamp` (GUID series `65CD…`) while `findGunDealer` and `findShop` predate it (`5D9C…`). The `v1_3` release note's "3 new tutorial jobs" is therefore accurate and was left untouched. The finding is written into `starter-jobs-retirement/requirements.md` so that feature does not rediscover it. **No gameplay decision outstanding.**
3. **The town-stock half of shop pricing is very likely an integer-division bug.** `OVT_EconomyManagerComponent.GetSellPrice:550` computes `price + ((1 - (stock_level / max_stock)) * (price * 0.1)) + …` where **both `stock_level` and `max_stock` are `int`**. Integer division makes that term **+10% whenever stock is below the ceiling and +0% at or above it** — a binary step, not the smooth "prices move with the town" curve the design (and the shipped `economy-first-buy` tutorial tip) implies. Verified directly at `:537-556`. The manual therefore says "how well stocked the surrounding town is for that item" and quantifies nothing. **A float cast is probably the one-line fix, but that is a gameplay change, not a docs change.**
4. **Does a gun dealer stock ammunition for occupying-faction weapons?** `Configs/System/GunDealerConfig.conf` sets `m_bIncludeOccupyingFactionItems 0` on the AMMUNITION rules too, but whether a given calibre's prefab sits in the OF catalog (`ItemIsFromFaction`) is runtime data that cannot be resolved statically. The manual says only "Most equipment belonging to the occupying faction is not traded"; the wiki's existing "They will, however, sell ammo used in OF weapons" was **left untouched** rather than contradict an observed-behaviour claim that could not be disproved. Needs one in-game check.
5. **Wounding or killing anybody makes you wanted, with no witness and no faction check.** `SCR_CharacterDamageManagerComponent.WhenDamaged:15-40` escalates the instigator to wanted level 2 on *any* damage to *any* character, and `WhenDamageStateChanged:44-82` escalates to 3 on any kill. Neither path consults `m_bIsSeen`/`m_bTempSeen`, and neither checks the victim's faction, so hurting a civilian, a friendly recruit or another player in an empty field makes you wanted exactly as fast as shooting a soldier in a town square. Every other escalation path in `OVT_PlayerWantedComponent` is seen-gated. Documented as written ("violence needs no witness") on both surfaces, because that is what ships. **Whether the no-witness rule and the missing faction check are intended is a gameplay call.**
6. **Killing an occupying faction soldier makes wanted level 3 of everyone sitting in any vehicle within 5 m of the body.** `SCR_CharacterDamageManagerComponent.CheckVehicleSetWanted:106-131`, reached from the `IsOccupyingFaction()` branch at `:55-61`, walks every occupant of every vehicle in a 5 m sphere and escalates them, whether or not they took part. It is presumably a heuristic for "the shooter was in that car", but it also catches a passenger who parked next to a firefight. Documented in general terms; **needs a gameplay owner's call on whether the collateral case is wanted.**
7. **Wanted levels 1 and 5 are unreachable by escalation.** Every escalation site sets 2, 3 or 4; level 1 exists only as the last step of the decay tail, and nothing sets 5 even though `OVT_WantedInfo.UpdateWantedLevel:64-73` draws five stars. The old wiki text claimed aircraft would set 5 "if aircraft are added"; that was removed rather than kept as a promise. **Either the fifth star is dead UI or a trigger is missing.**
8. **`realEstateCostMultiplier` is dead config.**
9. **A camp's "away from bases" rule is never enforced.** The Camp placeable sets both `m_bAwayFromCamps 1` and `m_bAwayFromBases 1` (`Configs/Resistance/placeables.conf:37-40`), but `OVT_PlaceContext.CanPlace:267-280` **returns true** as soon as the away-from-camps check passes, so the away-from-bases branch below it is unreachable for camps. The server side does not close the gap either: `OVT_ResistanceFactionManager.PlaceItem:672-696` re-checks only item limits. A camp can therefore be placed right beside an occupying base, while a Mobile FOB deployed in the same spot is refused. The wiki's "cannot be placed too close to enemy bases" line was **removed** rather than kept, because it describes intent, not behaviour. **Is the base exclusion meant to apply to camps?** One-line fix if so (drop the early return), but it changes where existing camps may go.
10. **Recruits only earn experience against hardcoded faction keys.** `OVT_RecruitManagerComponent.OnAIKilled:702-709` awards XP only when the victim's faction key is exactly `"US"` or `"USSR"`. On a server whose occupying faction comes from a compatibility mod with any other key, recruits never level at all, silently. Documented on both surfaces as "killing occupying faction soldiers", which is the intent; **whether to compare against `GetOccupyingFactionData().GetFactionKey()` instead is a gameplay call** (the QRF scoring at `OVT_QRFControllerComponent.CheckUpdatePoints:121` already does exactly that).
11. **Special-ops teams sent at a camp or FOB do nothing when they arrive.** `OVT_OccupyingFactionManager.UpdateKnownTargets:1315-1360` adds every resistance camp and FOB as an `ATTACK` target, and `UpdateSpecops:1233-1257` spends reserves sending a team. `OVT_BaseUpgradeSpecops.OnUpdate:33-77` handles the BASE and BROADCAST_TOWER cases, but for a FOB or camp target it falls into the `else if(!inrange)` branch and simply clears the target; the source carries a literal `//To-Do: Destroy stuff if needed`. Both surfaces therefore say the occupying faction "sends troops out towards them" and stop there. **Is a camp or FOB supposed to be destroyable by the AI?**
12. **Recruit training is persisted, replicated and never set.** `OVT_RecruitData.m_bIsTraining` and `m_fTrainingCompleteTime` are written to and read from saves and carried through the recruit RPCs, but a repo-wide grep finds no site that ever sets `m_bIsTraining = true`. It is either an unshipped feature or dead weight in the save format; deliberately undocumented on both surfaces. Defined at `OVT_DifficultySettings.c:65` but applied nowhere — a repo-wide grep finds only its replication read/write. Deliberately undocumented on both surfaces. Either it should be wired up or removed; that is a gameplay decision, and a bug candidate rather than a docs one.
13. **Officer template loadouts are saved, flagged and replicated, but nobody else can ever see one.** `OVT_LoadoutManagerComponent.SaveOfficerTemplate:338-351` gates on `IsOfficer` and then calls `SaveLoadout(playerId, …, isOfficerTemplate: true)`, so the record is keyed under the **officer's own** persistent id with `m_bIsOfficerTemplate` set. But `GetAvailableLoadouts:1031-1062`, the only lister the equipment-box UI calls (`OVT_LoadoutsContext.c:109`), walks `m_mLoadoutIdMapping` and keeps a key **only when `keyPlayerId == playerId`**. It never consults `m_bIsOfficerTemplate` and never widens to other players' records, so an officer template appears in exactly one player's list: the officer who saved it. The UI's delete path compounds this by hard-coding `isOfficerTemplate` to `false` with the comment `// Assume personal loadout for now` (`OVT_LoadoutsContext.c:340`). The wiki previously claimed "these loadouts are available to all resistance members"; that claim was **replaced with a Known Limitation block** describing what ships, rather than deleted or left standing. **Is faction-wide template sharing an unfinished feature or an abandoned one?** Wiring it up means a second branch in `GetAvailableLoadouts` plus an owner-aware delete, both gameplay changes this feature is not entitled to make.
14. **A fifth difficulty preset, `Insane`, ships and is selectable, and had no documentation at all.** `Configs/Difficulty/Difficulty_Insane.conf` is registered in the preset array at `Prefabs/GameMode/OVT_OverthrowGameMode.et:74`, so `"difficulty": "Insane"` in `Overthrow_Config.json` resolves and works (`OVT_OverthrowGameMode.c:331-342` matches on `preset.name`). The wiki's `difficulty` page listed four levels and its `difficulty/settings` reference gave four columns. **Phase 7A's page-creation budget was zero**, so Insane was folded into the parent `difficulty` page as a section and given a full column on `difficulty/settings`, but it has **no sibling page** where `easy`/`normal`/`hard`/`extreme` each have one. **Decision needed: should `difficulty/insane` be created to match the other four, or is the parent-page section sufficient?** Creating it is one page and no code; it just needs authorising, since D11 capped this feature's creations at two and both were spent (`shops`, `skills`).
15. **The shipped default value of `discordWebHookURL` points at the retired GitHub wiki.** `OVT_OverthrowConfigComponent.c:48` seeds every auto-generated `Overthrow_Config.json` with the literal string `"see wiki: https://github.com/ArmaOverthrow/Overthrow.Arma4/wiki/Discord-Web-Hook"`. That page no longer exists: GitHub redirects it to the wiki home, which now reads only "This wiki has moved to http://wiki.armaoverthrow.com/" (checked 2026-08-08). So the first thing a new server owner reads in their own config file sends them to a stub. The `overthrow-config` wiki page documents this default verbatim and links correctly to `/discord-web-hook` alongside it, so the **wiki is not wrong**; the string in the code is. Fixing it is a one-line change to a shipped default in `Scripts/`, which run 7B is not entitled to make. **Should the default become `https://wiki.armaoverthrow.com/discord-web-hook`?**
16. **`getting-started` repeats the officer-loadout claim that open question 13 disproved, and run 7C left it standing.** Under "Loadout Manager System" the page says "**Officer Templates**: [Officers](/officer) can create faction-wide loadout templates" and lists "**Team coordination** through shared officer templates" as a benefit. Question 13 established that a saved officer template is keyed under the officer's own persistent id and that `GetAvailableLoadouts:1031-1062` only ever returns records whose key matches the requesting player, so no other resistance member can see one; `loadout-manager` now carries a Known Limitation block saying so. `getting-started` therefore contradicts `loadout-manager` today. It was **not** fixed here because run 7C's remit on this page was the two deferred facts (camp price, job count), and because the correct wording depends on question 13's unanswered gameplay decision: if faction-wide sharing is finished, the `getting-started` sentence becomes true and needs no edit; if it is abandoned, both pages should say the templates are personal to the officer who saved them. **One sentence to change either way, once question 13 has an answer.**

## Gotchas

1. **`FieldManualConfigRoot.conf` is a same-GUID delta, not a copy.** Changing its one element GUID to a vanilla one makes Overthrow's category *replace* the base game's Introduction (proven 2026-08-07: 5 categories instead of 6). It also never declares `m_aTileBackgrounds`, inheriting the base root's eight, and `SCR_FieldManualUI.c:253` calls `GetRandomElement()` on that array **unguarded**.
2. **The Init case asserts a floor, not a count.** `VANILLA_CATEGORY_FLOOR = 5`; the "141 entries" number lives in `DescribeRoot()`, a `Print` that runs before any assertion. Adding sub-categories and entries cannot turn it red, so nothing existing needs weakening (Appendix A.1).
3. **`SCR_FieldManualPiece_Image`, `_Separator` and `_LineBreak` are `insertable: false`** — hand-written into the `.conf` only; a Workbench user will not find them in the property dropdown. The shipped entry already hand-writes an `_Image`, so it is proven legal.
4. **`SCR_FieldManualConfigEntry` (non-`_Standard`) is `insertable: false` and its own title field says "Do NOT use".** All twelve entries are `SCR_FieldManualConfigEntry_Standard`.
