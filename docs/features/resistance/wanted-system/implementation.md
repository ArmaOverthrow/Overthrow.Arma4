# Wanted System - Implementation Plan (Retrospective)

**Status:** Implemented (Documented Retrospectively)
**Epic:** resistance
**Originally Implemented:** Overthrow legacy (pre-1.3.0); Undercover System icon added in v1.3.0
**Documented:** 2026-08-03
**Last Updated:** 2026-08-03

---

## Executive Summary

The wanted system is Overthrow's stealth/aggro layer: a GTA-style 0–4 star wanted level per character that governs whether the occupying faction (OF) treats you as a civilian, one of their own (disguise), or an enemy. It is implemented almost entirely inside a single per-character component, `OVT_PlayerWantedComponent` (810 lines), ticking at 1 Hz on the owning machine. Escalation comes from being *seen* doing something suspicious (armed, hostile uniform, base/radio-tower proximity, armed vehicle) or from server-side combat events (shooting, damaging, killing). De-escalation is a timed decay while unseen. The AI never learns about wanted levels directly — the component translates the level into a perceived-faction override that vanilla perception consumes.

**Note:** This is a retrospective implementation plan created by analyzing the existing codebase. The feature has already been implemented.

---

## Goals

### Primary Goals
- Let players move openly among the OF while unarmed/disguised, and make hostility an earned, legible state (stars + seen-eye + undercover icon HUD).
- Escalate on witnessed crimes and combat; decay over time when out of sight.
- Support disguises (wearing OF clothing) with a close-range blow-your-cover check.
- Make recruits and civilians participate in the same perception rules (recruits inherit their owner's stealth skill; civilians have the component dormant until recruited).

### Success Criteria
- [x] 5-level wanted scale (0–4 in practice) with witnessed-escalation and timed decay
- [x] Line-of-sight + engine-perception hybrid detection with stealth-skill distance scaling
- [x] Disguise via vanilla outfit-faction scoring; blown at close range or on violence
- [x] AI consumption via `SetPerceivedFactionOverride` (no AI changes needed for targeting)
- [x] HUD stars / seen-eye (opacity = visual recognition factor) / 3-colour undercover icon
- [x] Difficulty-tunable timeouts and ranges; fast travel blocked while wanted
- [ ] Disguise reduces effective wanted level (`GetEffectiveWantedLevel` stub, dead config fields)
- [ ] Recruits inherit the player's wanted level when grouped (designed, never implemented)
- [ ] Any test coverage (currently zero)

Component attachment: `Character_Player.et`, all recruit prefabs, and `Character_CIV.et` (town civilians — dormant until recruited). The `OVT_WantedInfo` HUD is also registered on `Wheeled_Base.et`, `Helicopter_Base.et` and `Turret_Base.et` so it survives entering vehicles/turrets.

### Data Flow

1. **Tick (1 Hz, owner machine)** — `CheckUpdate()`: snapshot `GetVisualRecognitionFactor()`; recalculate outfit faction → disguise classification; scan all AI agents within `5 + 250 × stealthMultiplier` metres (`FilterEntities` → alive + OF faction → `CheckEntity`); restricted-area checks (base within `baseCloseRange`, radio tower within hardcoded 20 m); decay timer; `CheckWanted()` applies the perceived-faction override; `BumpMe()` on change.
2. **Detection** (`CheckEntity`) — engine `PerceptionComponent` FRIENDLY target list answers "does this AI know about me"; a manual head-bone→head-bone `TraceMove` raycast answers "can it see me now"; escalation reason picked by state (hostile uniform / armed / armed vehicle / Mobile FOB).
3. **Combat events (server)** — the modded danger-reaction and damage-manager classes call `SetBaseWantedLevel(2/3)` directly and blow disguise.
4. **AI consumption** — `CheckWanted()`: disguised & level<2 → perceived as OF; level>1 → perceived as player faction (hostile); level<1 → perceived as `"CIV"`. Real `FactionAffiliationComponent` untouched so vehicle/compartment access keeps working. Plus direct component-presence checks in `SCR_ChimeraAIAgent`.
5. **HUD (client)** — reads the RplProps off the locally controlled character once per second; no events, no RPCs.

### Integration Points

- **skills epic:** `OVT_StealthSkillEffect` writes `OVT_PlayerData.stealthMultiplier` (1 − distanceMul); recruits read their **owner's** multiplier. `m_fDetectionTimeMul`/`m_fDisguiseBonus` are dead.
- **occupying epic:** `OVT_OccupyingFactionManager` provides `GetNearestBase`/`GetNearestRadioTower` for restricted-area checks and hosts the `m_OnPlayerLoot` invoker. Wanted level does **not** trigger QRF.
- **towns epic:** `RecordSuspiciousActivity()` (loot, disguise-blown) adds +0.1 to `OVT_TownData.areaHeat` — persisted but **read by no gameplay code** (dead-end sink; pinned by town logic tests).
- **resistance/recruits:** civilians' dormant component is enabled on recruitment (`RecruitCivilian`); recruit wanted state is independent of the owner (contra the AI-commanding design doc).
- **core/game-mode:** `OnPlayerSpawned` resets to 0 and disables the system for a 5 s grace period. No handling in `OVT_PersistentRespawnLogic`.
- **UI/map:** fast travel blocked at wanted > 0 (`OVT_MapContext`); `OVT_MapRestrictedAreas` draws the base/tower circles that mirror the proximity triggers (duplicating the hardcoded 20 m).

## Implementation Details

### Phase 1: Core wanted loop (COMPLETED)
- 4 `[RplProp]`s (`m_iWantedLevel`, `m_bIsSeen`, `m_fVisualRecognitionFactor`, `m_bWantedSystemEnabled` — the last declared `float` with an `m_b` name), 1 Hz `CallLater` tick gated by `GetRpl().IsOwner()`.
- `SetBaseWantedLevel(level, reason)` is monotonic-up with a 0→N notification; `SetWantedLevel` is the unconditional setter (decay, spawn reset).
- Decay: −1 level per `wantedTimeout` (30 s default) while unseen; level 1 uses `wantedOneTimeout` (120 s); being re-seen at level 1 jumps back to 2.

### Phase 2: Detection & disguise (COMPLETED)
- Hybrid perception + LOS raycast; distance formula `5 + m_fBaseDistanceSeenAt(250) × stealthMultiplier`; cheap early-out below 0.2 recognition beyond `10 × stealthMultiplier` m.
- Disguise = vanilla outfit-faction scoring resolves to the OF; a second 15 m (`disguiseDetectionDistance`) LOS sweep blows cover at close range.
- Armed vehicles (via `TRAIT_ARMED` editable-entity label) and the Mobile FOB (hardcoded prefab GUID) → level 4 and the vehicle itself is flipped hostile (`SetVehicleAsEnemy`).

### Phase 3: Combat escalation & lifecycle (COMPLETED)
- Server-side writers in modded damage-manager and AI-danger classes (shoot 2 / damage 2 / kill 3 / vehicle-adjacent kill 3).
- Civilian dormancy (`DisableCivilianWantedSystem` on town spawn, re-enable on recruitment); spawn grace; fast-travel gate; v1.3.0 undercover HUD icon.

### Phase 4: Designed but never landed (NOT STARTED)
- Disguise-based wanted reduction (`GetEffectiveWantedLevel()` stub; `baseDisguiseEffectiveness`, `wantedReductionMultiplier`, `detectionRangeMultiplier` authored in every difficulty config, read nowhere).
- Recruits inheriting the group leader's wanted level (`docs/archive/AI_Commanding_Design.md`).
- Any consumer for `areaHeat`.

## Key Technical Decisions

### Decision 1: Per-character component, not a manager
**Context:** Wanted state is inherently per-character (players, recruits, even dormant civilians), and AI needs a cheap "is this entity player-aligned" test.
**Implementation:** Every eligible character prefab carries `OVT_PlayerWantedComponent`; `SCR_ChimeraAIAgent` uses *component presence itself* as the marker ("has a wanted component ⇒ never an enemy unless wanted ≥ 1").
**Trade-offs:** No central bookkeeping or coordination; N components each walk the whole AI world per second (O(N·M)); town civilians carry live-but-dormant timers.

### Decision 2: Perceived-faction override as the AI interface
**Context:** Teaching AI behaviour trees about wanted levels would be invasive.
**Implementation:** `CheckWanted()` drives `CharacterPerceivableComponent.SetPerceivedFactionOverride()` (OF when disguised, player faction when wanted, `"CIV"` when clean); real faction affiliation is left alone so vehicle/compartment access keeps working.
**Trade-offs:** Elegant reuse of vanilla perception — but it feeds back into detection: once the override flips you hostile, you leave the AI's FRIENDLY target bucket, which is the only bucket `CheckEntity` scans (see Known Issues #1).

### Decision 3: Owner-machine execution with RplProp broadcast
**Context:** Detection needs the character's own perception-relevant state every second.
**Implementation:** Tick early-returns unless `GetRpl().IsOwner()`; state ships via `[RplProp]` + `Replication.BumpMe()`. For players the owner is the controlling **client**; server-owned recruits/civilians tick on the server.
**Trade-offs:** This makes the player's wanted level client-authoritative, while the damage/danger writers run on the server — two writers, one authority. RplProps only replicate server→client, so client-side bumps don't propagate; it *appears* to work because ownership transfer happens after `OnPostInit`, so the tick likely registers on both machines, doubling the scan cost and allowing transient divergence. `m_bIsDisguised` isn't replicated at all yet is read on both sides.

### Decision 4: Hybrid detection (engine perception + manual raycast)
**Context:** Engine perception knows *awareness*; the game needs *current line of sight* plus distance/stealth rules.
**Implementation:** Perception target lists gate the check, a reused `TraceParam` head→head `TraceMove` confirms LOS, `GetVisualRecognitionFactor()` gives a cheap early-out (and the HUD eye's opacity).
**Trade-offs:** Good fidelity per check; cost controlled by the 1 Hz cadence and distance culls, but the outer loop is still a full `GetAIAgents` walk (a `QueryEntitiesBySphere` alternative sits commented out).

### Decision 5: Escalate-only levels with timed decay, notification presets
**Context:** GTA-style legibility.
**Implementation:** Monotonic `SetBaseWantedLevel` + timer decay with a long level-1 tail; reasons are `SCR_SimpleMessagePreset` tags resolved via the notification manager (localization stays out of the component).
**Trade-offs:** Simple and predictable; but the timer doesn't reset on escalation and the level-1→2 re-escalation path skips notifications.

## Current State

### What's Working
- Full escalate/decay loop, disguises, armed-vehicle detection, HUD, difficulty tuning, fast-travel gate — the feature is playable and shipped (undercover icon since v1.3.0).
- Civilian dormancy and recruit stealth inheritance work as designed.
- Combat escalation (server-side writers) reliably raises the level even when the scan misses.

### Known Issues (filed 2026-08-03 as BUG-072…078)
1. **BUG-072 — FRIENDLY-bucket-only scan:** once wanted ≥ 2 the perceived-faction override moves you to the ENEMY bucket, which `CheckEntity` never queries — the seen-eye goes dark mid-firefight and decay ticks while you're being shot at; only combat events re-escalate.
2. **BUG-074 — `OnPlayerLoot` ignores its entity parameter:** on a listen host (server owns recruits/civilians) the host looting a body can make every *seen* recruit wanted level 2.
3. **BUG-073 — Client-authoritative player wanted level** + double-registered tick (server & client both likely tick), unreplicated `m_bIsDisguised`, `EnableWantedSystem()` never bumps replication.
4. **BUG-075 — Invoker leak:** `m_OnPlayerLoot.Insert` never removed in `OnDelete` — retains every wanted component ever created.
5. **BUG-076 — Decay timer never resets on escalation** (a 2→1→2 bounce leaves a 120 s timer on level 2); re-escalation at `:478` bypasses notifications.
6. **BUG-077 — Missing null guards:** `m_Percieve`/`GetAffiliatedFaction()` derefs in the tick, `OVT_MapContext` casts `m_Wanted` unchecked, HUD `UpdateSeen` widget null-unsafe.
7. **BUG-078 — BUG-013 residue:** clients read difficulty fields via a hand-rolled, unversioned JIP stream.

### Technical Debt
- **Performance:** two full `GetAIAgents` walks/second/component; `RecalculateOutfitFaction()` + a `map<Faction,int>` allocation every tick; dormant civilians still tick; repeated per-tick config/faction-key lookups.
- **Dead code:** `OVT_WantedInfoWidgets.c` (entire file), `GetEffectiveWantedLevel()`, `IsDisguisedAsFIA()`, `IsDisguisedAsSupporting()`, `IsWantedSystemEnabled()`, `m_iLastSeen`/`LAST_SEEN_MAX`, `skipNormalDetection`; dead difficulty fields (`baseDisguiseEffectiveness`, `wantedReductionMultiplier`, `detectionRangeMultiplier`) and dead stealth params (`m_fDetectionTimeMul`, `m_fDisguiseBonus`); `areaHeat` written/persisted but never read.
- **Hardcoding:** Mobile FOB prefab GUID, 20 m radio-tower radius (duplicated in `OVT_MapRestrictedAreas`), `"CIV"`/`"FIA"` faction keys, +5 m floor / 10 m early-out / 0.2 recognition threshold, 5 s spawn grace, 0.1 heat increment.
- **Type smell:** `m_bWantedSystemEnabled` is a `float`.
- **Localization:** uk_ua covers 6 of 11 wanted strings.

## Notes

**Discovered Information:**
- Wanted level is **not persisted** — by design or omission, players load in clean (and the spawn reset would zero it anyway). The only persisted trace is the never-read `areaHeat`.
- The component's presence doubles as a type marker for AI friend/foe logic — attaching it to a new character prefab has AI-behaviour side effects beyond the wanted mechanics.
- The HUD is registered on vehicle/turret prefabs purely so the display survives seat changes.
- Levels are magic ints (no enum); level 1 is a decay-only state never set directly.

**Retrospective Assessment:**
- The perceived-faction-override pattern is the standout design: full AI hostility integration with almost no AI code. The reuse of vanilla outfit scoring for disguises is similarly economical.
- The main structural weaknesses are the ambiguous owner-authority model (client-authoritative player state with server-side co-writers) and the O(N·M) world scans — both invisible in single-player testing, both consistent with the epic-wide "works hosted, degrades on dedicated" pattern.
- A half-finished "undercover v2" (effective-level reduction) is fossilized across config, skill effect and a stub getter; it should be either completed or excised.
